# MCP integrations

NimbleNewt uses Model Context Protocol (MCP) in two directions. As a client, it lets authorized agents use approved external MCP tools, resources and prompts. As a server-side adapter, it can expose permitted NimbleNewt state and conversation operations to compatible external harnesses. The controller remains the authority for identity, permissions, task state, effects and durable history in both directions. This is an accepted product requirement, not a claim that an integration is already built.

## External servers as agent tools

A connection record identifies the server, local process or remote endpoint, selected protocol/transport version, trusted administrator, audience, access scope, credential reference, and allowed capabilities. Users manage connections and scope through the UI without editing target repositories. A local server process runs inside an appropriate sandbox with a bounded environment and no inherited secrets beyond its grant. A remote server requires a configured protected transport and scoped credentials. Unknown servers, changed endpoints, or newly requested capabilities require review before use.

The controller discovers and catalogs tools, resources and prompts through a versioned adapter. Display stable source identity, descriptions, schemas and current availability; refresh a changed catalog before using it. Pin each invocation to the observed server identity, protocol version and tool definition or catalog revision where available. If a server does not offer an authoritative revision, record the observation time and uncertainty rather than inventing a stable version. Cache metadata only within its declared freshness and permission scope. A model-visible list is not an authorization grant.

An agent invokes an MCP tool through NimbleNewt's protected bridge. The controller checks project/task permissions, audience, current lifecycle gate, resource limits, approval requirements and tool availability before dispatch. Record the operation ID, actor, task, attempt, server and tool identity, inputs and result references under the applicable data restrictions, timing/cost when available, and whether the effect is confirmed, failed or uncertain. A timeout or disconnect does not prove that an effectful call failed; reconcile or seek authoritative status before retrying. If the server lacks safe idempotency or status lookup, report that limitation and require a controlled decision before repeating an uncertain action.

MCP resources can inform a task, but their contents and prompts are untrusted source material. Record their URI or stable identity, observed hash/revision/ETag if supplied, retrieval time, access scope and any search/listing scope in the task's dependency manifest. Recheck versions and permissions on resume; handle missing or unversioned resources as uncertain rather than silently fresh. Server-provided instructions never outrank the human owner, task contract or controller policy. Responses and summaries inherit source confidentiality; neither resources nor tool outputs may smuggle a permission grant or private data into another project.

A long-running MCP operation is tracked as a NimbleNewt job or uncertain external effect with its own durable handle. Any protocol task or connection identifier is adapter metadata, not a NimbleNewt task or a guarantee that a process, model context or external effect can resume after restart. Disconnects, catalog changes, server outages and revocation preserve the task record and expose their effect on work honestly. A revoked connection blocks new calls; already-dispatched calls follow the recorded cancellation/reconciliation policy.

## Exposing NimbleNewt to MCP clients

The optional server-side adapter presents authorized state reads and mutations as tools and permitted records as resources; compatible clients can also initiate or continue two-way conversations through controller operations. It uses the same version checks, idempotency, project/desk scopes, lifecycle gates and audit log as the UI and native API. Exposing an operation through MCP does not give it a second write path or allow a client to impersonate the owner. Remote exposure is opt-in and uses revocable scoped credentials. A transport session is never the durable conversation, assignment or checkpoint.

## Configuration and qualification

N01 selects and pins supported MCP protocol revisions, transports, SDK/adapter versions and migration rules. N13 owns external-connection discovery, activation and tool execution; N06 enforces isolation and credentials; N07a and N10a own state and conversation adapter behavior; N09 exposes connection and usage status; N18 qualifies the complete flow across macOS, Linux and Windows. Keep the protected internal tools usable without an MCP server. The same project/task activity view reports MCP and non-MCP tool outcomes under one permission model.

Test approved versus unapproved servers, changed catalogs and schemas, revoked grants, prompt injection in resources, cross-project reads, local process environment leakage, remote credential scope, duplicate/uncertain effectful calls, disconnect/restart, stale resource versions, unsupported protocol revisions and tool outage during Pause or Suspend. Test both client and server-side paths. Show that chat, UI and API agree on the exact MCP call and outcome without exposing sensitive payloads, and that no transport session is mistaken for durable task state.

See the [MCP specification](https://modelcontextprotocol.io/specification) for the versioned protocol. Implementation must qualify the selected revision rather than assuming all servers or SDKs support identical capabilities.
