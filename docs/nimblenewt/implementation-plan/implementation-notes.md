# Implementation notes and known limitations

Running record of limitations found while implementing task cards. Each entry names the card that should resolve it.

- **Install scripts (resolved in F03):** `.npmrc` sets `ignore-scripts=true`; `@google/genai` (a no-op preinstall) and `protobufjs` (postinstall) never run their scripts and all tests pass. Enabling any install script needs a reviewed change; the license inventory marks affected packages.
- **Minimum Node (F03):** `engines` requires Node >=22.19.0 and `@types/node` is pinned to 22.x. CI runs 22.19.0 and 24.21.0 on Linux, macOS and Windows. 
- **Database isolation is convention (F01):** the boundary check restricts package dependencies and imports, but does not forbid built-ins such as `node:sqlite` inside `pi-adapter`.
- **Offline guarantee (F03):** `scripts/offline-guard.mjs` is preloaded into every package test process and blocks non-loopback `fetch`, sockets, DNS and UDP; Worker threads and Node child processes inherit it. It is a tripwire, not a sandbox: non-Node child processes and native code are not covered. The Linux CI job therefore reruns the suite inside a network namespace (`unshare --net`).  A Node child started with an explicit `env` that omits `NODE_OPTIONS` runs unguarded; when F05 adds tool tests, check how Pi Durable spawns tool processes (the Linux namespace rerun covers it there).
- **Test-only dependencies (before the first test-only package):** the boundary check requires every imported package to be a runtime dependency. F05 added none; fix it so test files may import `devDependencies` when one is first needed.

## F05 notes and limitations

- **Results are recorded once, durably.** The first time a request's result is built it is stored in an adapter-owned Pi document (`nimblenewt.requests`, committed with the transcript) keyed by request ID; every later call returns that record. Results are built from an ID-range scan of the conversation history, not the active view, because compaction removes older entries from the view but not from storage. An unanswered request owns the entries up to the next user input.
- **Request-ID reuse is detected from a payload fingerprint** (SHA-256) stored before admission, so it works while the original is still queued and after compaction. A crash between recording and admission leaves a record for the same payload, so a retry with that payload succeeds and one with different content is conservatively rejected.
- **Growth:** the document holds one record per request, including tool outputs, in a single conversation-scoped document. Revisit (size limits, pruning, per-request storage) before long-lived installations.
- **Commands:** the adapter supports no commands yet, so every command request is rejected with `UnknownCommandError`. F06 adds branch, checkpoint and abort commands. `abort()` and `compact()` are minimal whole-conversation placeholders; F06c replaces `abort()`.
- **Unknown-tool detection depends on a Pi Durable 1.3.0 diagnostic code** (`tool_unavailable`). The runtime pin makes this safe; G03/upgrade qualification must re-check it. The code is also produced for tools that exist but are not offered to the model, so `unknown_tool` means "unavailable". It marks the request `failed` after the fact; Pi lets the run continue and later tool calls still execute. If F06/G02 need the run stopped, end it from the adapter's tool layer.
- **Tool errors are normal feedback:** a throwing tool yields an `error` outcome on a `completed` request.
- **Tool API:** tools receive `{ signal, callId }` and may declare `replay: "safe"` (default: interrupted calls are not re-run). F06's restoration tests must cover both.
- **Command `args`** are in the contract but unused until F06d.

## F06 split

F06 (checkpoints and cancellation mapping) has several independently verifiable units, so it is delivered as four pieces, each separately reviewed and committed. F06 is complete when all four pass; G02 follows.

- **F06a:** conversation handles, `whenBusy`, restart and fresh-process restoration, F05 review follow-ups.
- **F06b:** inquiry branch that leaves the parent context unchanged; selective update applied exactly once.
- **F06c:** cancellation, delivered as **F06c1** (abort mapping: abort during streaming and partial tool arguments, incomplete tool calls never execute, queued input survives cancellation and is readmitted only by the controller) and **F06c2**, itself delivered as **F06c2a** (the interrupted-work hold, plus the readmission follow-ups) **F06c2b** (the context decisions: update versus resume and the aborted-instruction behaviour) and **F06c2c** (branch lifecycle/retention).
- **F06d:** checkpoints and the typed controller boundary (retained commands require later controller readmission), delivered as **F06d1** (checkpoints: create, verify, restore) and **F06d2** (the controller-facing interface, audit events and one reviewed recovery step).

## F06a notes

- **API shape:** `PiAdapter.root()` and `PiAdapter.conversation(id)` return an `AdapterConversation` with `submit`, `recorded`, `lookup`, `abort` and `compact`. `submit`, `abort` and `compact` moved off `PiAdapter`. `recorded(requestId)` reads a stored result without waiting.
- **Busy policy:** `whenBusy` (`followUp` default, `steer`, `reject`) is part of a request's identity (fingerprint `v1:sha256:`, covering content and busy policy; extend it, and bump the version, when branch or entry options are added). `reject` on a busy conversation throws `ConversationBusyError`; the request was not admitted and the ID stays reusable.
- **Reopening storage does not run interrupted work, but almost any progress call does.** Pi's scheduler is harness-wide: besides `resume()`, `submit`, `abort`, `compact`, `Submission.wait` (so `result()`), `waitForTask` and `waitForIdle` on any conversation start it, which resumes every interrupted run in every conversation. `lookup(requestId)` is the read-only alternative: it returns a settled request's result (recording it the first time) or `undefined`, never waits, and never starts the scheduler. A controller recovering after a crash must use `lookup()` until it has decided what to do with interrupted work.
- **F06c acceptance item (hold):** provide a real hold. For example, list interrupted runs at open (Pi's `harness.inspect()` is read-only) and refuse progress calls until the controller chooses resume or abandon for each one. Decide the scope of `abort()` and `compact()` (hold versus resume) together with this.
- **Attribution rule:** a request owns the tool calls after its input and before the next input in the transcript, so a steered input starts a new segment and each call is counted once (the steered-in request owns calls after the steer). Requests merged into one run share the final answer text.
- **Crash semantics verified with a real SIGKILL** (Pi JSONL storage, child process): an interrupted tool declared unsafe is not re-run and the model is told it was interrupted; a `replay: "safe"` tool runs again. External effects remain at-least-once for safe tools; exactly-once is not claimed.
- **Fingerprint on old records:** a record without a fingerprint, or with another version prefix, matches any payload (implemented in F06b as `fingerprintsMatch`). Records written by the F05 commit (24019e5) hold an unprefixed SHA-256 and would conflict with `v1:` fingerprints; no data has been deployed. The rule going forward: compare only fingerprints with the same version prefix, and treat unknown formats as legacy.
- **No storage lock:** Pi's JSONL storage does not stop two processes opening one directory (for example a hung process plus its replacement). Worker ownership and leases (H cards, F06d) must provide fencing.
- **Branch requests (F06b):** inquiry-branch creation must be idempotent by request ID, and branch options belong in the fingerprint.
- **Open from the F05 review (non-blocking):** the single results document grows by about 6 KB per request in Opus's measurement (linear); move to per-request documents (`defineDocFamily`) and decide on bounded stored outputs before G02 long-run tests. `settings` exposes Pi's own settings type from the adapter package; consider narrowing it. G02 repeats the kill test on macOS and Windows; this piece's kill test runs on whichever OS CI uses (Windows detects death by non-zero status, not by signal).

## F06b notes

- **Inquiry branch:** `conversation.branch({ requestId, at? })` forks a child conversation (Pi `fork`, ownerless) from a completed-turn boundary. The child sees the parent's history up to that entry, shares nothing afterwards, and the parent's transcript is left exactly unchanged (tests compare full transcripts before and after, and check what each side's next model step sees). Branch creation is idempotent by request ID: the fork and its record are written in one commit (Pi runs the fork's `init` in the creating commit), so concurrent calls return the same branch and a crash cannot leave an unrecorded orphan. Naming a different `at` for an existing request ID is a conflict.
- **Fork point:** the latest completed-turn boundary (a final assistant answer, the last tool result of a fully answered tool round, or a compaction summary), resolved at first creation and then fixed. A turn still in progress is not part of the branch, so a "how is it going?" inquiry on a busy task sees the task as of its last completed turn, not its in-flight work. Forking inside a turn would leave a tool call without its result. If product needs the in-flight state, F06c decides between finish-and-hold and a parallel inquiry. `NoBranchPointError` when there is no completed turn; `InvalidBranchPointError` for an explicit `at` that is not a boundary.
- **Selective update:** `submit({ kind: "update", requestId, content, source? })` places the text in the parent as its own `nimblenewt.update` entry (provenance in the entry data), applied once per request ID (same dedupe, fingerprint and result machinery as inputs; the fingerprint covers kind, content, busy policy and source). Applying it starts a run, like any input. An update is a normal input to the model; there is no "silent" context edit.
- **Attribution:** input segments start at `pi.user` and `nimblenewt.update` entries.
- **`transcript()`:** read-only full history of a conversation (including compacted-out entries and inherited parent entries), for inspection and tests.
- **Bug found while testing:** a conversation with no adapter document yet made `recorded()`, `lookup()` and branch lookup crash on `undefined`; fixed and covered.
- **Not covered (F06c/F06d):** abort of an inquiry branch, queued input surviving cancellation, discarding or retaining a side conversation as policy, branch retention limits, and the controller-facing boundary.
- **Compaction and branches:** a compaction entry is a boundary, so the default branch of a compacted task gets the compacted context (summary plus recent entries), not the history the task no longer has. An explicit `at` before the latest compaction is allowed and gives the older, uncompacted history; that is deliberate (historical inquiries) and costs the full prefill and window of that history.
- **Retrying a branch request without `at`** returns the original fork point even if the task has since moved on; request a new branch (new request ID) for the current context.
- **Namespaces:** branch request IDs are stored apart from input/update request IDs, so one ID can be both without conflict. Controllers should still use distinct IDs per operation.
- **Decision for F06c/F06d (update vs resume):** `kind: "update"` currently fuses "apply the update" with "resume the task": it is an input, so it starts a run when the parent is idle. That clashes with the F06c hold and with "retained commands require later controller readmission". Decide between `applyAndRun` (today) and a place-only variant that adds the update to the transcript without asking the model anything (Pi's `write` submission with a model-visible entry, applied at the next boundary like a steer), so a controller can apply an update and resume later. Also decide on fixed framing of the update text for the model (for example "Update from inquiry <id>: ..."), since provenance lives only in entry data the model does not see.
- **F06c/F06d acceptance item (branch lifecycle):** `AdapterBranch` has no discard, close or retention operation, and ownerless branches survive parent aborts. Define discard/retain policy, a bound on accumulated branches per task, and how aborting a task treats its inquiry branches. Each fork also forks the adapter document.
- **Perf:** `branch()` scans the parent's whole history to find boundaries; it could stop at the newest compaction.
- **Compaction while an input is pending:** Pi also compacts while preparing a generation, so a summary can land after a still-unanswered input. That compaction is not a fork boundary (the branch would inherit the task's pending instruction); the default fork point is then the last answered turn, before the compaction, and the branch pays for the uncompacted prefix of that turn. A controller that wants the compacted context for an inquiry must wait for the turn to settle (finish-and-hold, F06c).

## F06c1 notes

- **`abort()` returns an `AbortReport`** `{ aborted, retained }`: requests that had started (stopped mid-run) and queued requests withdrawn before starting. Pi's `abort` withdraws queued inputs; the adapter keeps each request's payload (in the request record, until its result is recorded, or for good while it is retained) and marks the withdrawn ones `retained: true` on their `unanswered/aborted` result. Nothing of a retained request ran.
- **Retained requests never run by themselves.** `retainedRequests()` (read-only, survives restart) lists them in admission order with payloads; `readmit(id, newId)` submits one again under a new request ID, an explicit controller decision. Idempotent for the same new ID, refused (`AlreadyReadmittedError`) for another, and refused (`NotRetainedError`) for requests that had started or are unknown. A readmitted update stays an update, with its provenance. This is the "retained commands require later controller readmission" behaviour; F06d wires it to the controller's inbox.
- **Partial tool calls:** verified against Pi 1.3.0 with a slow faux stream: aborting while a tool call's arguments are still streaming leaves the request `unanswered/aborted`, the tool is never executed, and Pi omits the aborted assistant message from the next model request. The transcript keeps the partial assistant entry (stopReason `aborted`) with no tool result; it is not a fork boundary, so `branch()` right after such an abort throws `NoBranchPointError`.
- **Scope:** aborting a conversation does not abort its inquiry branches and vice versa (ownerless forks), tested. Whether aborting a task should also abort its branches is F06c2.
- **Payload growth:** payloads of retained requests accumulate until the retention policy (F06c2/F06d) prunes them; a readmitted request's payload is kept so readmission stays idempotent.
- **abort() starts Pi's harness-wide scheduler** (a progress call), so on a freshly reopened storage it resumes interrupted runs everywhere. The hold (F06c2) must gate it.
- **Readmission is claim-first.** `readmit` records the new ID in one commit (exactly one new ID can win, concurrently or across a crash) and then submits; the same new ID is idempotent. After a crash between the two steps the request no longer lists as retained, so the controller must repeat the call with the same new ID (F06d should surface "claimed but not yet admitted").
- **Known behaviour, F06c2 decision:** the input of a request that had *started* and was then aborted stays in the model's context on later runs (Pi drops only the aborted assistant message). Nothing re-runs it, but the model can see it and may act on it; only never-started requests are retained and need readmission. Options for F06c2: hide the entry with Pi's context-only edits, add fixed framing ("aborted by the user; do not continue unless asked"), or make it an explicit controller choice. A test pins today's behaviour so a change is deliberate.
- **Abort report caveats:** the report is the difference between aborted submissions before and after the call, so (a) two concurrent `abort()` calls can report the same IDs, (b) requests aborted by anything else in the window (for example Pi closing) are attributed to the call, and (c) the scans cost O(every aborted submission ever). An adapter-side record of aborts, or a cursor watermark, would fix (c).
- **Payload retention:** a request's payload is dropped only when a non-retained result is recorded, so requests nobody ever reads keep theirs. Fold into the retention policy (F06c2/F06d). The report covers only the conversation `abort()` was called on, and readmission links old to new only through `readmittedAs`; F06d will want the reverse link and original admission order.

## F06c2a notes

- **The hold.** Pi's scheduler is harness-wide and almost any progress call starts it, which re-runs every interrupted run. So on open the adapter inspects the storage (`harness.inspect()`, read-only); if any task or unsettled submission exists it holds (option `holdInterrupted`, default true). While held, `submit`, `abort`, `compact`, `readmit` and waiting on an unsettled result throw `InterruptedWorkError`; reads (`lookup`, `recorded`, `transcript`, `retainedRequests`, `branch`, `interrupted`) work and start nothing. A settled result is read from its record, not by waiting.
- **Controller flow:** `interrupted()` lists per conversation the live tasks, unsettled request IDs and whether it is abandoned; `abandonInterrupted([conversationId...])` marks every live task of those conversations for abandonment (Pi `abortTask` only marks; verified it neither runs anything nor starts the scheduler) and withdraws their queued submissions (which then stay available through `retainedRequests()` and `readmit()`); `releaseHold()` ends the hold and starts the scheduler, so everything not abandoned resumes (replay-safe tools re-run; others are reported to the model as interrupted). The abort handlers of abandoned work run at release, and their requests settle `unanswered/aborted`. `resume()` is replaced by `releaseHold()`. Without a hold, opening still runs nothing: the next progress call resumes everything, as before.
- **Granularity limit:** Pi cannot resume one conversation and keep another stopped. The only per-conversation choice is abandon; everything else resumes together at release.
- **Verified with real crashes** (child process SIGKILL, two conversations interrupted, one with a queued request behind it): nothing runs while held; abandoning the root leaves the branch's work untouched; after release only the branch's replay-safe tool re-runs and its request completes; the abandoned request settles `unanswered/aborted`; the queued request never reaches the model and is retained.
- **Readmission follow-ups (from the F06c1 review):** `readmit(id, id)` throws `InvalidReadmissionError`; a typed refusal at submit (new ID taken by a different payload, busy, held) gives the claim back so another new ID can be tried; other errors keep the claim (unknown outcome, retry with the same new ID).
- **Still open:** the hold is in-memory per adapter instance (a second process opening the same storage has its own); real ownership/fencing across processes belongs to the worker/lease cards. `abandonInterrupted` is not atomic across conversations (a crash midway leaves some marked; marking is idempotent, so repeat it).

## F06c2b notes: context decisions (defaults chosen here; owner may override)

- **Aborted instructions are framed by default.** Pi keeps the input of a request that started and was aborted in later model context as if it were live. The adapter now replaces it, *for the model only* (a Pi context edit), with the same text prefixed "[This request was aborted before it finished. Do not continue it unless asked again.]", once per request, and appends a `nimblenewt.aborted-input` entry; the transcript keeps the original. `PiAdapterOptions.abortedInputs: "keep"` restores the old behaviour. Rationale: after an abort the controller, not the model, decides whether to continue; a bare aborted instruction invites the model to resume it. Alternative considered: omit the input entirely (loses the fact that it was asked). Framing happens when the abort is observed: in `abort()`, when a result is read, and in `abandonInterrupted()` before release, so no run can start between the abort and the framing in the paths the adapter controls. A run that is already generating when the abort lands has already read its context.
- **Updates keep running by default, with a place-only form.** `submit({ kind: "update", ... })` still applies the update and resumes the task (an input). `run: false` places it as a Pi passive write with model messages: it is added to the transcript at the next turn boundary and the model is asked nothing, so a controller can apply an update and resume later (the shape F06d's readmission model needs). Its result is `{ status: "placed", entryId }`. `run` is part of the request's identity. A placed update is part of the task's context: it is a fork boundary (a branch taken after it sees it), it does not leave an input pending, and it does not cut a running request's tool calls out of its segment. The update text is still shown to the model as a plain user message; fixed framing of its provenance ("Update from inquiry <id>: ...") is not added yet, because the provenance lives only in entry data the model does not see; decide with F06d.
- **Hold notes from the F06c2a review:** a lone queued submission (including items left queued after a failed run, "queued items stay in the inbox until the next input") engages the hold on open, so controllers may see a hold after a model error with no crash; `abandonInterrupted` throws `NotHeldError` once the hold is released (afterwards it would be a late abort); abandonment marks tasks by conversation ID and does not yet follow ownership into conversations owned by tasks (a tool that spawns a subagent): not reachable through today's adapter, mark owned conversations transitively when tools gain that ability.
- **Still for F06c2c/F06d:** branch lifecycle (discard/retention/bounds), and presenting `interrupted()` -> decide -> `abandonInterrupted` -> `releaseHold` as one reviewed step with an audit trail.
- **Branches inherit the framing.** The `nimblenewt.aborted-input` entry only carries a context edit, so like a placed update it extends the preceding boundary: a branch taken right after an abort forks after the edit and sees the aborted instruction framed, as the task does (tested).
- **Submit waits for an abort in progress** (per conversation, within one adapter instance): `abort()` frames after Pi's abort resolves, and a `submit()` in that window would start a run that reads the input unframed, so submissions wait for the abort and its framing to finish (tested; the test fails without the wait). Handles from other adapter instances on the same storage are not coordinated.
- **Queued place-only updates are not withdrawn by `abandonInterrupted`.** They ask the model nothing. With no run left to reach a turn boundary, Pi keeps them queued until the next input places them; they are neither lost nor run behind the controller's back. (Conversation `abort()` also leaves queued writes alone: Pi: "queued writes stay".) A place-only update queued behind a running request is placed at that run's next boundary, so it joins that run's context mid-run, like a steer without a reply; controllers wanting it to wait for "between tasks" must submit it when idle.
- **Framing from `settle()`** (an abort the adapter did not start, first observed while another run is mid-turn) appends the edit directly in a commit instead of waiting for a boundary; it worked in every probe but Pi does not document that interleaving. `abort()` and `abandonInterrupted()` frame while the conversation is idle or held.
- **Growth:** the `framed` flag and `nimblenewt.aborted-input` entries add to the single results document's growth (see F05 notes).

## F06c2c notes: branch lifecycle

- **Policy:** branches are kept for review (nothing is deleted), but are bounded and closable. `listBranches()` lists a conversation's branches in creation order (request ID, conversation ID, fork point, discarded). `discardBranch(requestId)` marks the branch discarded in one commit (the parent's record and the branch's own document), then aborts whatever it is running (returning its `AbortReport`); after that the branch refuses `submit`, `compact`, `readmit` and nested `branch` with `BranchDiscardedError`, while its transcript, `lookup`, `recorded` and `abort` keep working. Idempotent; an unknown request ID is `InvalidBranchPointError`; refused while interrupted work is held (aborting would start the scheduler). Discard survives restart.
- **Bound:** `maxActiveBranches` (default 8) active (not discarded) branches per conversation; creating another throws `TooManyBranchesError`. The count is taken inside the fork's creating commit, so concurrent creators cannot exceed it (tested with six at once against a limit of two). Asking again for an existing request ID (even a discarded one, returned with `discarded: true`) is never refused.
- **Aborting a task does not touch its branches** and discarding a branch does not touch the task; to stop a task's inquiries the controller lists them and discards or aborts each (no cascade flag yet).
- **Not done:** deleting or archiving branch storage (each branch is a full conversation plus its adapter document, which grows with the single-document design noted under F05), automatic expiry, and per-branch budgets. Revisit with F06d's controller policies.
- **Discard vs submissions in flight (found in review, reproduced with a slow store):** a `submit()` that had passed the "is this branch discarded?" check could be admitted after the discard's abort finished and then run. Three layers now close it: (1) `discardBranch` marks, then waits for submissions in progress on that conversation (tracked per adapter instance), then aborts; (2) after Pi admits a submission the adapter re-reads the branch's document and, if it was discarded meanwhile, withdraws the submission and throws `BranchDiscardedError` (covers other adapter instances); (3) the claim commit refuses once the branch is marked. The test holds a submission between its claim and its hand-over to Pi through an internal test seam (`beforeAdmission`) and asserts no tool runs after the discard returns; it fails with all layers removed, and either (1) or (2) alone is enough. Pi's own `abort` already waits for a submission that is currently being admitted, which is why a merely slow store did not reproduce it; the window is before the call reaches Pi.
- **Discard cascades down the tree:** discarding a branch also discards its own branches (their work is aborted, nested reports merged). Discarding is not undoable.
- **Discarded work never resumes after a crash:** discard is mark-then-abort; a crash between the two used to leave a discarded branch with live tasks. `interrupted()` now reports `discarded` per conversation, and `releaseHold()` (now async) abandons the interrupted work of discarded conversations before starting the scheduler. Tested by marking a branch discarded in an interrupted storage and releasing.
- **For F06d:** checkpoints must say whether discarded branches are included; `discard`, like `abandonInterrupted`, should be a reviewed, audited controller action.

## F06d1 notes: checkpoints

- **What a checkpoint is:** a small JSON record `{ format: 1, conversationId, at, digest, runtimeVersion, contractsVersion }` taken after a completed-turn boundary (default the latest, with exactly the boundary rules of `branch()`, so a turn in progress or a pending input is never part of it). It holds no conversation content. The `digest` (`v1:sha256:`) covers every history entry up to and including `at`: id, kind, model messages, data, head marker and context edits, in id order with canonical JSON; not the writing task or conversation, so a fork's inherited prefix digests like its source.
- **`verifyCheckpoint` (conversation or adapter) is read-only and allowed while interrupted work is held.** It rejects with a typed reason: `unsupported_format`, `incompatible_runtime` (any other Pi Durable version or contracts version: there is no forward migration yet, so an upgrade invalidates old checkpoints explicitly; this is the compatibility rejection G03 builds on), `unknown_conversation`, `unknown_entry`, `not_a_boundary`, `history_changed`. Later turns and compaction do not invalidate a checkpoint, since the prefix is unchanged and compaction keeps older entries in storage. A store restored from a different or damaged backup with the same ids is caught by the digest (tested with a look-alike store).
- **`restoreCheckpoint(checkpoint, requestId)`** verifies, then branches the checkpointed conversation at `at` (`CheckpointRejectedError` otherwise; nothing is created on rejection). The result is a new conversation whose context is the task as it was, idempotent by request ID, subject to the branch limit and the usual branch rules. It does not roll the original back; the controller decides which conversation continues.
- **Limits, stated plainly:** a checkpoint is a reference, not an export. Restoring needs the same storage (or a faithful copy of it); there is no portable history export/import for a replacement worker with an empty store, which the worker/lease cards and G02's cross-worker recovery must add, probably as an artifact manifest of the history. The digest detects accidental change and mismatched backups, not an adversary who can rewrite both the history and the checkpoint (there is no signature). Workspace state (files, uncommitted changes) is outside this record: per the design, immutable artifact manifests own workspace checkpoints and the controller references both. The adapter's own request records are not part of the digest (results are re-derivable from the history).

## F06d2 notes: controller boundary, audit and recovery

- **Typed boundary (`@nimblenewt/contracts`):** `RuntimePort` and `ConversationPort` list everything a controller may do, using only contract types (no Pi types), so a controller does not depend on Pi Durable and another runtime could implement them. `PiAdapter implements RuntimePort` and `AdapterConversation implements ConversationPort`, checked by the compiler, and a test drives a task, a branch, a checkpoint and a restore through the port type alone. Controllers should depend on the ports, not on the adapter classes (`AdapterConversation` is exported as a type only). Deliberately off the port: `abandonInterrupted` / `releaseHold` (replaced by `recover`), and the test seams (`testHooks.beforeAdmission`, `markBranchDiscardedForTests`, `@internal` helpers).
- **Audit trail:** `PiAdapterOptions.audit` receives an `AuditEvent` after each controller-reviewed action has taken effect: `abort`, `readmit`, `discard_branch` (one event for the whole cascade, not one per nested abort), `restore_checkpoint`, `recover`. Ordinary submissions are not audited. The sink is awaited; if it throws, the error reaches the caller although the action has already happened, so a controller that must not lose records should make its sink durable and retrying. Events are emitted by the adapter instance that performed the action; audit across adapter instances or processes belongs to the controller.
- **`recover(decision)` is the one reviewed recovery step:** `{ abandon, reason, decidedBy }`. It refuses (`NotHeldError`, `InvalidRecoveryError`) unless interrupted work is held, a reason and a decider are given and every listed conversation actually has interrupted work, and a refused decision changes nothing. It then abandons the listed conversations (discarded branches are abandoned automatically), releases the hold, and emits one `recover` event carrying the decision and exactly what `interrupted()` showed. `abandonInterrupted` / `releaseHold` remain on the adapter class for low-level use. `releaseHold()` must be awaited.
- **Checkpoint compatibility (from the F06d1 review):** validity now depends on `format`, the digest algorithm and the runtime version, not on `contractsVersion`, which is informational; an unknown digest prefix is `unsupported_format`. G03 will need a runtime storage/history format identifier plus a migration table rather than an exact npm version; until then any other Pi Durable version is `incompatible_runtime`. Restoring a checkpoint taken before a later compaction brings back the full uncompacted history up to `at` (same window and prefill cost as an explicit `at` before a compaction, see F06b).
- **Restores and inquiries are limited separately:** `BranchInfo.kind` is `inquiry` or `restore`; `maxActiveBranches` applies to each kind on its own, so a burst of one cannot starve the other. Restoring from a discarded branch throws `BranchDiscardedError`, not `CheckpointRejectedError`.
- **For the controller (S09):** keep a checkpoint together with the workspace artifact manifest it belongs to as one controller-owned recovery point (`{ checkpoint, artifactManifest, requestIds }`); the adapter only knows the conversation half. Bridge the controller's inbox to `ConversationPort.submit` with the controller's own operation ID as the request ID; readmission is the only way a withdrawn command runs again.

## F06e notes: independent tasks, and gaps carried to G02/S09

- **`createTask({ requestId })`** (on `PiAdapter` and `RuntimePort`) starts a task with an empty context, separate from every other task and the root (the "task A/B context separation" G02 requires; before this the port could only fork from an existing context). It is a child record of the root conversation, built on the same machinery as branches: the conversation and its record are created in one commit, idempotent by request ID (also under concurrent callers: exactly one caller gets `created: true`), limited separately (`maxActiveTasks`, default 16; inquiries, restores and tasks each have their own count), listed by `listBranches()` with `kind: "task"` and `forkedAt: 0`, closed with `discardBranch(requestId)` (abort, close to new work, cascade), durable across restart, and audited (`create_task`, once per creation). One request ID cannot be a task and a branch or restore (`RequestIdConflictError` both ways). Tasks are ownerless: aborting the root or another task does not touch them. Creating a task starts nothing, so it is allowed while interrupted work is held. Each task starts on the adapter's configured model.
- **Equivalent mutant:** the early "already created" check in `createTask` is an optimisation; the atomic registration in the creating commit also returns the existing task, so removing the early check changes no behaviour.
- **Recovery after a crash in the middle of `recover()`** (probed by the F06d2 reviewer on the real-kill fixture): `abandonInterrupted` marks are durable, so if the process dies after abandoning and before releasing, the reopened adapter is held again with those conversations showing `abandoned: true`; a second `recover()` completes the job (the abandoned work is not re-run; the rest resumes). Consequences: an abandonment cannot be undone by a later decision, and the first decision's audit event is lost because `recover` emits only after releasing (the second event shows `abandon: []` with `abandoned: true` in its `found`, which is how the earlier decision surfaces). If that record matters, add a `recover_started` intent event; not done yet.
- **Audit semantics to know:** events are at-least-once (a retried `readmit` with the same new ID emits again; concurrent aborts can overlap in their reports); `at` is a wall-clock hint, so the controller's audit log should assign its own sequence; direct `abandonInterrupted` / `releaseHold` are not audited (they are off the port; use `recover`). Branch creation is not audited yet.
- **Gaps in the controller port (G02 or S09):** (1) waiting for a result after losing the handle needs `submit` of the same payload again or polling `lookup`; add `wait(requestId)` (storage lookup by request ID plus `submission.wait`, refused while held); (2) cancelling a single request (Pi `abortSubmission` for a queued one); (3) transcript paging (`from`, `limit`) before long runs; (4) a progress/event stream for the UI cards; (5) treat `submissionId` and conversation IDs as opaque in the port docs. `BranchPort` lacks `kind` (it is on `BranchInfo`).
- **`compact` is on the port (G02):** the design requires compaction to be explicit, and the milestone needs to compact through the controller-facing surface. It is not an audited action.

## F04a notes: the transactional controller storage contract

Lives in `packages/controller/src/storage/`. It defines what domain services may ask of storage and what every adapter must do, and provides the reference implementation and the shared conformance suite. **It does not touch a real database yet**: SQLite is F04b, PostgreSQL F04c, and the contract has so far been exercised only against `MemoryStorage`, which is the oracle the adapters are compared with. Whether the suite is strong enough for real concurrency, crashes and disconnections is what F04b-F04d must show; the suite's concurrency tests are meaningful on a real database, trivially satisfied by single-threaded memory.

- **One write primitive.** `applyOperation` takes everything a command changes (aggregate creates/updates/checks, audit entries, outbox messages, effect intentions, timers, timer cancellations) and commits it as one transaction or not at all, including the operation record itself. Checks run in a fixed order: input validity, existing operation (same hash replays, different hash is `idempotency_conflict`), epoch, revisions, then ID uniqueness. A repeat of an already committed operation is answered even after the epoch has moved on.
- **Identity.** `operationHash` covers actor, correlation, changes, audit, outbox, effects, timers and cancellations, and deliberately excludes the operation ID, epoch and issue time. Key order does not matter (canonical JSON).
- **Fencing.** The primary epoch starts at 0 (no owner; nothing is admitted), rises by 1 per `acquireEpoch`, and supports compare-and-set takeover. **Every write method takes the caller's epoch** (`applyOperation`, `claimDeliveries`, `retryDelivery`, `claimDueTimers`) and refuses a stale one with nothing written, so a deposed controller cannot claim, retry, complete or settle after a takeover; lease tokens only fence claimant against claimant. The one exception is a repeat of an operation that already committed, which is answered from the record. Aggregates use per-record revisions; `check` changes guard without writing. Lease expiry uses a caller-supplied `now`, so clock skew can at worst redeliver a message (receivers deduplicate by `deliveryId`); correctness against an old controller rests on the epoch, not the clock.
- **Reconciliation is part of the one write primitive.** Receipts (`completeDeliveries`), timer firings (`completeTimers`) and effect settlements (`settleEffects`) are fields of `OperationInput`, committed in the same transaction as the domain transition, audit and outbox entries of the handler, under the same operation ID, epoch check and idempotency. There is no separate "complete" call, so a crash cannot leave a receipt recorded and the task not moved; rerunning the handler with the same operation ID replays. Every effect settlement writes an automatic `effect.settled` audit record. A timer cancelled while claimed makes its holder's completion fail with `state_conflict` (cancellation wins; treat as superseded). A delivery already delivered with the same receipt is a no-op for any token.
- **Delivery.** Claims are leases with opaque tokens (the memory store's tokens are guessable: they fence honest mistakes, they are not a security boundary). Ordering within `(destination, orderingKey)` is strict commit order even across retries and priorities; unkeyed messages are independent. A late completion by the current token holder is accepted if nobody took over; completion by anyone else is `state_conflict`; a repeated completion with the same receipt is a no-op.
- **Ambiguous commits.** `commitOperation` is the only way domain code should submit an operation: it reruns `retryable` failures within a bounded budget and resolves `uncertain_commit` by asking `getOperation` for the stable ID, resubmitting only if the operation is absent. Only `applyOperation` can be uncertain; claims and completions are safe to repeat because leases expire and receipts are idempotent. `FaultInjectingStorage` scripts these failures for any adapter.
- **Rules for adapters (stated in `types.ts`).** Sequence numbers (audit `seq`, delivery `seq`) come from a counter row updated inside the operation's transaction, never a database sequence, because sequences allocate in statement order and leave gaps, which would let a later message of an ordering key become claimable before an earlier one commits; the throughput cost of serialising on that row is for F04d to measure. Bodies are stored as text or `json`, never `jsonb`. IDs and kinds compare in binary order (`COLLATE "C"`). A race on a unique key is mapped to `retryable` (operation ID, so the retry replays) or `duplicate_id` (delivery, effect, timer), never a raw driver error. The conformance suite includes raw concurrent submissions and racing IDs, which are only truly exercised on a real database; F04d must add a test where two operations commit in the opposite order to which they started and the delivery order must still follow commit order.
- **Representation.** IDs are ASCII (`ID_PATTERN`), timestamps are `YYYY-MM-DDTHH:mm:ss.sssZ` strings, integers are safe integers, bodies are canonical JSON text with the rules in `types.ts` (no undefined, NaN, -0, unsafe integers, cycles; depth 32; 256 KiB), absent optional fields are omitted (never `null`), reads return copies, listings sort by code point. Limits keep transactions short: at most 100 entries of each kind per operation.
- **No raw SQL in domain code.** `scripts/package-boundaries.mjs` now fails the build if SQL statements or database drivers (`node:sqlite`, `pg`, ORMs, and so on) appear anywhere except `controller/src/storage/sqlite/` and `controller/src/storage/postgres/`. This is a tripwire (upper-case SQL statement forms anywhere, the same forms in any case inside string and template literals, and a list of known drivers; prose in comments is not flagged, but a string that merely contains words like "select ... from" is, an accepted false positive), not proof; a domain service could still obtain a handle some other way, which the typed contract exists to prevent.
- **Not in the contract yet (later cards):** the domain aggregates' own schemas (F03/F05 and the domain cards), schema migration journals (F04), durability settings and busy handling (F04b), connection pooling and serialization retry (F04c), measured throughput and contention (F04d), backup and logical export (K01). **Query extension point:** `listAggregates(kind)` is the only query. S01/S02 will need to list by relation or state (tasks of a project, active assignments of a host); the planned extension is an `index` map of declared, typed fields on `create`/`update`, backed by an index in each adapter, added with the first domain card that needs it. Record kinds from the design's minimum-records table are stored as generic aggregates; their body schemas are not defined here.

## F04b notes: the SQLite controller storage adapter

`packages/controller/src/storage/sqlite/` (the only place besides `postgres/` allowed to hold SQL). Uses Node's built-in `node:sqlite` (no dependency; stability "active development", which prints an ExperimentalWarning on the supported Node versions). It passes the whole shared conformance suite (101 cases on this backend) plus SQLite-specific tests.

- **Explicit settings, read back and verified at open:** WAL journal mode (open fails if SQLite answers anything else, which also catches file systems that cannot do WAL), `synchronous = FULL` (the log is flushed before each commit returns: an acknowledged operation survives power loss, not just a process crash), foreign keys on, `trusted_schema` off, `journal_size_limit` 64 MiB (the WAL shrinks back after a spike; auto-checkpoint stays at SQLite's default), and a bounded busy timeout (default 5 s, at most 60 s). `settings()` reports them. These are per connection and re-applied on every open. Pi's own SQLite default (`synchronous = NORMAL`) is unaffected.
- **Write admission and short transactions.** Every write is one `BEGIN IMMEDIATE ... COMMIT`; a second writer waits at most the busy timeout and then fails as `retryable`, rolled back. Transactions contain only database work. Each method completes without yielding, so calls on one connection never interleave; contention comes from other connections and processes. Claims use one indexed query inside the write transaction; ordering uses a `NOT EXISTS` over open earlier messages of the same key, which is equivalent to the reference store's "head of the key" rule.
- **Sequence numbers** (audit, delivery) come from counter columns in the single `state` row updated in the same transaction, per the contract; no `AUTOINCREMENT`. Cost: every audited or outbox-writing operation serialises on that row (F04d measures it).
- **Failure classification.** Busy or locked is `retryable`. A constraint violation is `unavailable`, reported as an invariant violation with the extended result code: every write holds the database's only write lock (`BEGIN IMMEDIATE`) before it reads, so no one can have raced it to a unique key, and a violation means an adapter bug, schema drift or another program writing the file; it fails fast instead of being retried. (The contract's "operation-ID race is `retryable`" rule is for PostgreSQL under READ COMMITTED.) A failed `COMMIT` is `retryable` if it was only contention, otherwise `uncertain_commit` for `applyOperation` (resolve by operation ID) and `retryable` for claims. Other database errors are `unavailable`. No driver error escapes.
- **No network file systems.** `open` refuses `\\server\share` paths on every platform and `//server/share` on Windows only (on POSIX `//var/lib` is an ordinary path), and on Linux checks the directory's file system magic number and the mount table for NFS/SMB/CIFS/AFS/Ceph/9p/Lustre/GPFS/FUSE network mounts. The mount table is parsed with all octal escapes decoded. **This is best effort:** it cannot see a mapped network drive on Windows or a network mount on macOS, and a FUSE mount that hides its backing store looks local. The WAL check above is a second, independent net. The operator remains responsible; the PostgreSQL backend is the answer for shared storage.
- **Schema** layout 1 is created on first open and recorded in `PRAGMA user_version`; a newer version, an unknown database or a missing migration refuses to open without touching the file. The journalled migration runner (interruptible, downgrade-refusing) is card F04. Uniqueness of operation, delivery, effect, timer IDs and delivery sequence numbers, state values and revision/priority ranges are enforced by the schema as well as the code (tested against a raw connection).
- **Verified here:** the conformance suite; several OS processes racing to bump one counter (no lost update, gap-free audit and delivery numbers, one winner per revision); processes competing to claim deliveries (no duplicates, ordering chain respected); a writer SIGKILLed at six arbitrary points (never a partial operation, every acknowledged operation present, at most one in-flight operation extra, database accepts work and resolves the in-flight operation by ID); a process killed while holding the write lock releases it; a blocked writer fails as `retryable` within the bound and the database is unchanged. **Not verified:** power loss (it needs hardware or a VM; `synchronous = FULL` is the documented basis), Windows and macOS runs (they run in CI), a real network file system (only the refusal logic, with its limits), or throughput (F04d).

## F04c notes: the PostgreSQL controller storage adapter

`packages/controller/src/storage/postgres/` (SQL and the `pg` driver are allowed only here and in `sqlite/`). Runtime dependency: `pg` 8.23.1 (MIT, exact pin) with its small transitive set; test-only dependency: `embedded-postgres` 17.10.0-beta.17 (MIT; ships real PostgreSQL 17.10 binaries for Linux, macOS and Windows; the "beta" is the package's build tag, not the server's maturity). `@types/pg` for types. It passes the whole shared conformance suite (101 cases on this backend) plus PostgreSQL-specific tests against a **real server**, not a mock.

- **Concurrency model.** Writers run in parallel under READ COMMITTED; there is no global write lock. Correctness comes from row-level rules: the operation row is inserted first with `ON CONFLICT DO NOTHING`, so two submissions of one ID serialise on the key and the loser sees the winner's committed result (replay) or conflict; revisions are checked by conditional `UPDATE ... WHERE revision = expected`, creates by `INSERT ... ON CONFLICT DO NOTHING`, guards by `SELECT ... FOR SHARE`; delivery, effect and timer IDs by `ON CONFLICT DO NOTHING`. The primary-epoch row is read `FOR SHARE` by every writer and claimer, so a takeover (an `UPDATE`) waits for in-flight writers and everything after it sees the new epoch (tested: a takeover really does wait for a writer that already passed the fence, which completes under the epoch it held). Audit and delivery sequence numbers come from one counter row updated late in the transaction and held to commit, so they follow commit order with no gaps (tested under 60 concurrent operations); the cost is that every audit- or outbox-writing operation serialises briefly on that row (F04d measures it). Locks are taken in one fixed order (operation, epoch, aggregates by key, delivery rows, timer rows with completions and cancellations locked together, effect rows, new effects and timers by ID, the counter row, audit and new deliveries by ID), so the adapter's own transactions do not deadlock one another (tested: aggregates touched in opposite order, timers completed and cancelled crosswise, the same effect IDs or the same timer IDs inserted in opposite orders; delivery inserts happen under the counter-row lock, which already serialises them; any deadlock would show as a `retryable` outcome after the server's 1 s `deadlock_timeout`). PostgreSQL still detects a deadlock that arises from an outside session, and it is classified `retryable` (tested with a real server-detected deadlock). Sustained high-priority load can starve low-priority messages; that is inherent to the contract's rule and F04d should measure it. Serialization failures cannot occur at READ COMMITTED; they are classified `retryable` anyway. When an operation has several things wrong, the error reported is the first in the contract's order (changes, receipts, timer completions, settlements, duplicate delivery, effect, timer IDs; each in argument order), the same as the reference store and SQLite: PostgreSQL collects refusals while it takes locks in its own order and reports the first by that ranking (found by the parity test).
- **Claims** use `FOR UPDATE SKIP LOCKED` only to skip rows another claimant holds. The per-ordering-key rule is a `NOT EXISTS` over earlier undelivered messages of the same destination and key, evaluated on the claimant's snapshot: it can only hold a later message back, never let it overtake, and a concurrently claimed or completed head cannot make a successor claimable early. Tested with 12 concurrent claimants on a 10-connection pool: no delivery claimed twice, the chain yields only its head, every free delivery claimed.
- **Bounded pool, bounded waits, explicit settings.** At most `maxConnections` (default 10, at most 200) connections; waiting longer than `connectTimeoutMs` for one is `retryable` (tested). Every session runs with `lock_timeout` (default 5 s, tested), `statement_timeout`, `idle_in_transaction_session_timeout`, `synchronous_commit = on`, `READ COMMITTED` and the controller's own schema on `search_path`. At open the adapter reads back and verifies `fsync = on`, `full_page_writes = on`, `synchronous_commit = on` and the isolation level, and refuses a server that fails (tested against a second embedded server started with `fsync=off`). Minimum server version 14 was a code floor, not a support statement; **superseded by F04g: PostgreSQL 17 and above is supported (the adapter refuses older servers) and 14 to 16 are verified and reported, see [f04g-postgres-versions.md](f04g-postgres-versions.md).**
- **Failure classification** (driver errors never escape): deadlock, lock timeout, statement timeout, too many connections, pool wait and connection loss before COMMIT are `retryable` (the transaction never committed); connection loss **during** COMMIT is `uncertain_commit` for the operation primitive (resolved by operation ID) and `retryable` for claims; an unreachable server, bad credentials, missing database, disk full and any constraint violation (an invariant the adapter checks itself) are `unavailable`. Ambiguity is tested deterministically with a TCP proxy that cuts the connection at an exact statement: after the server processed COMMIT but before the answer (the operation is found committed and replayed, admitted once), before the server saw COMMIT (nothing committed; resubmitted), and in the middle of a transaction (rolled back, retryable, pool recovers).
- **Schema** layout 1 lives in a dedicated schema (default `nimblenewt`, validated name), created under an advisory lock so concurrent first opens are safe; every text column uses the binary `"C"` collation, bodies are `text` (not `json`/`jsonb`), uniqueness and state rules are database constraints (tested through a raw connection). A newer or older version, or a schema containing foreign tables, refuses to open without changing anything. `schema_info` is where the F04 migration runner takes over. The connection string contains the password and must come from the secret store (`controller.storage.url` in the configuration is a secret reference).
- **Test servers.** `testing/server.ts` starts a real server on a free loopback port in a temp directory, or uses `NIMBLENEWT_TEST_POSTGRES_URL` (a database where the tests may create and drop schemas; each test uses its own schema). The repository installs with lifecycle scripts disabled, so the helper recreates the embedded binaries' shared-library symlinks itself from the package's own list. The offline guard permits loopback, so these tests run inside it and inside the Linux network-namespace rerun.
- **Connections.** Session settings travel as startup options, so connections must be direct or go through a pooler that forwards startup options (PgBouncer in transaction mode does not). TLS is whatever the connection string's `sslmode` asks for and is untested. The database user needs CREATE on the database to create the schema; a permission failure says so.
- **Not verified (14-16 and 18 are covered by F04g):** PostgreSQL 14-16 and 18, TLS and remote servers, power loss and replica failover, a server restart mid-run (only connection cuts through the proxy), throughput and contention (F04d), and the Windows/macOS runs until CI reports.

## F04 notes: schema migration runners

Both backends now create and change their schema only through journaled migrations (`storage/migrations.ts` holds the shared rules and the pure planner; `sqlite/schema.ts` and `postgres/schema.ts` hold each backend's migrations in its own SQL; each adapter has its own runner and its own journal table, `schema_migrations`). This replaces the single-layout creation of F04b/F04c (`PRAGMA user_version`, `schema_info`).

- **Rules.** Migrations are numbered 1, 2, 3 without gaps and are never edited once applied: the journal records each one's name and a SHA-256 checksum of its content, and a database whose recorded checksum differs from this build's is refused. A database whose journal holds a migration this build does not know (written by a newer NimbleNewt) is refused untouched: there are no downgrades. A journal with a gap, or with a "running" entry that is not the last, is refused. A database that has tables but no journal was not created by NimbleNewt and is refused untouched (this also means a database created by the development builds before this card is not adopted; none was ever deployed). All refusals say "Nothing was changed" and are `unavailable`.
- **Transactional migrations** (the default) run their statements and write their journal entry in one transaction, so an interruption leaves the database exactly as it was and the next start runs the migration again. **Non-transactional migrations** (`transactional: false`, for things that cannot run in a transaction, such as PostgreSQL's `CREATE INDEX CONCURRENTLY`) are journaled as `running` (committed) before their statements, must consist of idempotent statements, are marked `done` afterwards, and are finished by the next start if found `running`.
- **SQLite runner.** Each migration step is a `BEGIN IMMEDIATE` transaction (write admission, as everywhere in the adapter). Two processes opening at once are serialised by that lock for transactional migrations; for non-transactional ones a second process may re-run the idempotent statements, which is allowed by the rule above.
- **PostgreSQL runner.** One connection holds a session-level advisory lock for the whole phase, acquired by polling `pg_try_advisory_lock` (never a blocking lock call: a session blocked in a statement holds a snapshot, and `CREATE INDEX CONCURRENTLY` waits for every such snapshot, which deadlocked two openers until this was found by the concurrency test). The lock vanishes with the connection if the process dies. The phase is exempt from the session `statement_timeout` (restored afterwards); DDL still honours `lock_timeout`, so a migration blocked behind a long transaction fails as `retryable` and the next start retries. The schema is created only if absent, so an account without CREATE on the database can use an existing empty schema.
- **What is verified (production list has one migration, so later layouts are synthetic and labelled as such):** an upgrade of a populated database through synthetic migrations 2 (transactional: adds a column, backfills it, adds an index, creates and fills a probe table with a non-idempotent insert) and 3 (non-transactional, idempotent; `CREATE INDEX CONCURRENTLY` on PostgreSQL) preserves everything the storage reports, each migration's statements run exactly once, and the adapter keeps working on the new layout (the entire shared conformance suite is also run on an upgraded database on both backends); a crash before and after every statement of that upgrade (SQLite 26 statements/52 points; PostgreSQL 34/68) leaves a journal that is a prefix of the migrations, never half a transactional migration, never a non-transactional one changed without a journal trace or marked done before it finished, and recovery reaches the state of an uninterrupted upgrade; a newer database, an edited migration and a journal gap are refused and leave the schema, the journal and the data unchanged (compared by reading the structure, the journal and the probe rows back, and the storage's own view of the data; not a byte comparison, which would not even mean anything on PostgreSQL); a non-transactional migration found `running` is finished by the next start, and one whose recorded content differs is refused; two processes (SQLite) or two connections (PostgreSQL) opening at once end with every journal entry `done` exactly once and the transactional migration's non-idempotent statements run exactly once (three rounds); for the non-transactional migration the test shows only that a repeat is harmless, which is all the rules promise on SQLite (a second process may re-run its idempotent statements; PostgreSQL's lock prevents even that); constraints that enforce unique operation, delivery, effect and timer IDs and delivery sequence numbers are tested directly against both schemas (F04b/F04c tests, unchanged). Committed layout-1 fixtures (`packages/controller/test-fixtures/`: a real SQLite file, a PostgreSQL JSON of DDL and rows, and the snapshot both must report) must open with every later build and upgrade without loss; regenerate only by `node dist/storage/qualification/fixtures.js` and only for deliberate pre-release changes to layout 1.
- **Operational rules.** Stop old controllers before starting a new version that will migrate: an old process started against a database a newer one has migrated is refused as "newer" (no downgrades), so old and new controllers cannot overlap across a migration (to be carried into the upgrade procedure of K02). On PostgreSQL a migration phase is exempt from `statement_timeout`, and `lock_timeout` does not bound `CREATE INDEX CONCURRENTLY` waiting for older transactions, so such a migration can wait as long as a long-running transaction exists; the polling lock gives up after 15 minutes of waiting for another process, not for the migration's own statements. If setting the statement timeout fails right after the lock is taken, the lock is released before the error propagates; that defensive path is not directly exercised by a test (it needs a server that refuses a harmless SET without dropping the connection).
- **Not done:** a backup before an upgrade (K01; the journal's `started_at`/`finished_at` are wall-clock times that K01 should record in the backup manifest); a naming convention for migration names (settle before the first real layout 2); long data migrations in batches with progress; moving data between SQLite and PostgreSQL (the separate logical export/import of K-cards); a real second layout (none is needed yet); running the PostgreSQL migration on a server other than 17.10 or through a pooler that does not support session advisory locks (PgBouncer in transaction mode does not).

## F07 notes: protected registry of tools and extensions

New dependency-free package `@nimblenewt/registry` (`packages/registry`). It is the controller-side facade that decides who may register which tool or extension name, which artifact versions exist, and which version a paused attempt gets back. It is not yet wired into `PiAdapter.open({ tools })` or any worker: that happens when attempts are launched (S02) and the catalog is built (T01, A05). Until then the adapter still accepts any tool list; this card provides and tests the rules those cards must use.

- **Names.** `<namespace>.<name>` in lower-case ASCII only. Namespaces: `nimblenewt` (protected, registered by the trusted controller), `toolbox` (shared) and `a_<id>` (one agent, 6-32 lower-case letters or digits assigned by the controller). Input that is not exactly in the grammar is rejected, never normalised, so look-alike spellings (upper case, full-width, Cyrillic, zero-width, trailing newline) cannot become a second name. Names are at most 28 characters.
- **Wire names.** `<namespace>__<name>`: nothing is replaced or dropped, names contain no underscore and a namespace at most one, so the first `__` is the only separator and two canonical names cannot merge. Even the longest valid name is exactly 64 characters, the usual provider limit; a decoder returns null for any spelling the scheme does not produce.
- **Three capabilities** from `createRegistry()`: `trusted` (allocate and retire agent ids, publish anywhere, seal the protected namespace, revoke, take a snapshot), `forAgent(id)` (publish only under that agent's own `a_<id>.`; reserved and other agents' names are refused with `reserved_namespace` or `foreign_namespace`), and `read` (resolve, list, pin, restore, verify the reserved set). Each is a frozen object of closures, with no `this` and nothing that leads to another capability. This is a facade against mistakes and unauthorised registration, not an isolation boundary: code in the same process could still tamper with the process, so execution is still authorised by NimbleNewt services (as the runtime-compatibility record requires).
- **Immutability.** There is no last-installed-wins: a (name, version) is immutable (the same content published again is a harmless no-op, different content is `version_exists`), versions must increase, `sealProtected()` stops any new `nimblenewt.` name, retired agent ids and their prefixes are never allocated again, and revocation is permanent (a fix is a new version).
- **Version selection and pins.** `resolve` gives the highest version that is not revoked, or exactly the one asked for. `pin(names)` records name, version and SHA-256 content digest in a pin set that carries its own digest. `restore(pinSet)` returns the same versions even after newer ones appear, and returns `blocked` with reasons (`revoked`, `missing`, `digest_mismatch`, or `invalid_pin_set` for a malformed or inconsistent set) instead of ever substituting another version. The pin-set digest is a plain SHA-256 checksum, not a signature: it catches accidental edits, but whoever can write a stored pin set can recompute it and select another registered, non-revoked version (never other content). The store that holds pin sets must therefore be writable by the controller only. Revoking the latest version makes the previous live version the default for anything that resolves afresh; an attempt that pinned the revoked version is blocked instead.
- **Integrity of the reserved set.** `verifyReserved(expectedDigests)` reports missing, changed, extra and revoked protected tools; the caller stops activation on any problem.
- **History.** `trusted.snapshot()` is the ordered list of operations; `createRegistry(history)` replays it through the same rules, so a stored history cannot say what a call could not (an agent tool without an allocation, a protected tool after the seal, a changed version, an unknown operation all throw). Storing the history durably belongs to a later card.
- **Verified by:** `registry.test.ts` (15 tests), plus mutation checks run while writing it: removing the foreign-namespace refusal, the reserved-namespace refusal, the pinned-digest check, the revoked-on-restore check, the pin-set tamper check, the seal, version monotonicity or the retired-agent check each makes at least one test fail.
- **Not done:** a durable store for the history and pins (a later storage card), per-attempt pinning in the controller, enforcement inside the worker and the adapter, execution-time authorisation, the shared-toolbox permission check (`toolbox.manage`), and aliases such as `/agent.command` (resolution to a canonical name is the caller's job; the registry only accepts canonical names).
- **Carry forward (not enforced by this card):** S02 (attempt admission) must store a pin set per attempt and call `restore` on resume; T01 (tool/skill catalog) and A05 must register through `forAgent`/`trusted` and call `verifyReserved` before accepting a customized environment; the worker must expose to the adapter only tools whose wire names `fromWire` resolves. Those cards' acceptance should be checked against this list.

## F04f notes: SQLite adapter on a worker thread

`SqliteWorkerStorage` (`storage/sqlite/worker-storage.ts`, `worker.ts`, `worker-protocol.ts`) is the existing `SqliteStorage` running on its own thread; the controller thread forwards each `ControllerStorage` call as a message and returns the answer. Nothing about the database changed (`synchronous = FULL`, WAL, `BEGIN IMMEDIATE`, the same SQL), so durability is the same; only where the flush wait happens moved. The measured effect and its costs are in section 7 of [f04d-storage-qualification.md](f04d-storage-qualification.md).

- **Same behaviour:** the shared conformance suite (twice, including on a database upgraded through the synthetic migrations), the seeded parity test (the worker store is a fourth participant, 12 seeds x 500 calls), the crash matrices (process killed from inside the worker at every statement of four write paths, 30/6/4/5 statements as in-thread) and a smoke workload all pass unchanged.
- **Errors keep their meaning.** A `StorageError` is rebuilt on the controller side with its kind, message and path; a refusal while opening (bad path, newer database, edited migration) arrives with its original kind and the thread is released. Input that cannot be copied between threads (a function, a cycle) is `invalid_input` and nothing is sent.
- **A worker that stops by itself** (crash, `process.exit`, uncaught error): the `applyOperation` waiting for it fails as `uncertain_commit` (resolve by operation ID on a reopened store, as for a lost connection), any other waiting call and every later call fails as `unavailable`. Tested by stopping the worker before and after every statement of a write (`mode: "exit"`): a reopened store always finds the operation complete or absent, and resubmitting it admits it once.
- **Process lifetime:** the thread is referenced only while calls are waiting, so an unclosed idle store does not keep the process alive (tested in a child process); `close()` answers the calls made before it, closes the database and ends the thread, and may be repeated.
- **Not done:** a separate read-only connection (reads queue behind commits; section 7), a per-call timeout on the worker (a hung worker would hang its callers; SQLite waits are bounded by the busy timeout, and nothing else in the worker can block), and measuring on Windows and macOS. The test-only crash plan (`testCrash`) is data, not a callback, and is never set in production.
- While making this change the in-thread SQLite smoke test was found to fail on a Windows runner (CI run 39430658838, Node 24): it required at least one inquiry and heartbeat in a 1.5 s window, and in-thread commits can starve those loops. The assertion was removed for the in-thread adapter (the invariants are the point, and the starvation is the F04d finding); the worker's smoke test keeps it.

## S01 notes: project and task records, revisioned commands

`packages/controller/src/domain/` (`ProjectService`) is the first domain service. It uses only the `ControllerStorage` contract, so it runs unchanged on the reference store, SQLite, SQLite on a worker thread and PostgreSQL (the same 11 domain tests run against all four).

- **Records.** `project` (name, goal, state `active | archived`, repositories, creator) and `task` (project, title, description, state, optional repository, creator). A project may have no repository and a task may have none; a repository can be attached to or detached from a task later. Repositories can be added to a project but not removed yet (a task may refer to one).
- **Identity.** A created record's ID is derived from the command ID (`proj-` or `task-` and 20 characters of base32 over a SHA-256 of the command ID), so it is stable, nobody chooses it, and a retry names the same record. Names and titles are editable fields and never identity.
- **Commands.** `createProject`, `updateProject`, `createTask`, `updateTask`, `transitionTask`. Each is one storage operation named `cmd:<commandId>`, with one audit entry (`project.created`-style type, subject, and the command's digest). Unknown fields are refused rather than ignored; text is checked (length, no control characters, no lone surrogates; a newline is allowed in goal and description).
- **Repeats.** A repeated command returns its recorded result (`replayed: true`) even after the record has moved on, because the command's digest is kept in its audit entry and compared before any state is read. The same command ID with any difference (payload or actor, or a different command type) is `command_conflict` and writes nothing. A duplicate sent at the same moment as the original, which can read the state the original produced, looks once more for a record of itself before it reports `stale_revision` or any other state-based refusal, and is answered with the original result (tested with four simultaneous copies over eight rounds, and with a duplicate whose first look is made blind). This also holds when the answer to a commit was lost: the retry finds the first application by command ID (tested with an injected lost commit).
- **Revisions.** Commands on an existing record carry `expectedRevision`; any other revision is `stale_revision` with the current revision, and of two commands racing on one revision exactly one wins.
- **Lifecycle.** Task states `proposed -> ready -> in_progress <-> blocked -> done | cancelled` per the `TRANSITIONS` table; `done` and `cancelled` are final and a finished task cannot be edited. Who is working on a task is not a state; it is the assignment record of S02.
- **Epoch.** `ProjectService.open` takes a new primary epoch (so it deposes any earlier service); after a takeover the old service's new commands fail as `stale_epoch`, while a repeat of something it already committed is still answered. A controller that will run several services (S02 and later) acquires the epoch once and gives every service that same epoch with `ProjectService.withEpoch`; tested, including that a takeover stops all of them.
- **Errors** are `DomainError` with a `code` (`invalid_command`, `command_conflict`, `stale_revision`, `not_found`, `invalid_transition`, `stale_epoch`, `unavailable`); storage busy beyond the retry budget is `unavailable` and the same command can be sent again.
- **Known limits.** Creating a task checks that its project exists and is active when the command is received; an archive that lands a moment later is not prevented (projects are never deleted, so no reference dangles). `listTasks` filtered by project reads pages of tasks and keeps the matches (bounded to 20 pages per call, with a continuation token), because storage lists by kind only; a per-project index belongs to the read side (U01). There is no outbox message or timer yet (S03), no permission check (A01) and no assignment (S02).
- **Found while doing this:** the Windows/Node 24 QA runs also showed the PostgreSQL immediate-shutdown test failing when no call happened to be in flight during the restart (the process is blocked while the server restarts). It now checks that the store held connections when the server was killed and then requires recovery and no loss, instead of requiring that a call failed.

## S06 notes: artifact publication and integrity

`packages/controller/src/artifacts/` (`FileBlobStore`, `ArtifactService`). The command machinery of S01 was moved into `domain/runner.ts` (`CommandRunner`) so that both services share one implementation of idempotency, conflicts, revisions and error mapping; the S01 behaviour and its 60 tests are unchanged.

- **Blobs** are immutable files named by the SHA-256 of their content (`blobs/ab/abcdef...`). A blob is written to `tmp/`, flushed to disk, renamed to its name and the directory flushed, then made read-only where the platform allows; so at its name it is absent or complete. Putting bytes that are already stored keeps the file only after hashing it again, refreshes its age (orphan cleanup uses age) and says `existed`; a file that does not match its name is replaced, never trusted. Anything that is not a regular file (a link, a directory) is refused when addressed and skipped when listing. A concurrency bug in the first version (two puts of the same bytes could delete each other's file) was found by the tests and fixed: a damaged file is now replaced by an atomic rename, with a remove-and-retry only where the platform cannot rename over a file.
- **Manifests** are records of kind `artifact` in controller storage (name, optional project and task, the files with path, content digest and size, the manifest digest, total bytes, creator), never updated. Paths use a portable grammar (relative, `/`, NFC Unicode, no `.`/`..`/empty segments, no control characters, backslash, colon or `< > " | ? *`, no trailing space or dot, no Windows device names, at most 512 bytes), and a set may not hold two paths equal ignoring case or a file inside a file, so an artifact unpacks the same on Linux, macOS and Windows. At most 1000 files per artifact (the record must fit a storage body); larger sets should be archives.
- **Publication order.** Check every path and the set of paths, then store and flush every blob, then check that each blob is still there, then commit the manifest as one idempotent command (S01 machinery; the artifact's ID is derived from the command ID). A crash anywhere before the commit leaves orphan blobs and no record; a crash after leaves a complete artifact; sending the same command again finishes the job exactly once. Qualified three ways: a commit that fails before it is recorded, a commit whose answer is lost (settled by command ID), and a real `SIGKILL` of a child process at four exact points (blob written but unnamed, first blob named, all blobs stored and manifest not sent, manifest committed): after each, the surviving blobs are exactly as expected, an accepted artifact always verifies, cleanup reclaims what nothing refers to without touching an accepted artifact, and a retry produces one complete artifact.
- **Integrity.** `verify` recomputes the manifest digest and hashes every blob (missing, wrong size and altered content are different findings, listed per file); `checkResumable` / `assertResumable` are what resuming work that depends on artifacts must call, and one damaged blob blocks it; `readFile` returns only bytes that match their recorded hash and size (an `integrity` error otherwise) and has a size limit per read.
- **Orphan cleanup** (`collectOrphans`) deletes a blob only if no artifact refers to it and it is older than the grace period (default one day), only while no publication in this process is in flight (a read-write lock: publication holds it shared from the first stored byte to the commit, cleanup exclusive), only under the current epoch, listing blobs before reading references. It also removes old stray files in `tmp/`. `dryRun` reports only. The lock belongs to the blob directory (every service and store object in the process that uses it takes part, tested with two services over one store); one controller process (the primary) owns a blob store, and nothing on the disk enforces that (no file lock or lease). Across processes, and for a controller deposed mid-cleanup (the epoch is re-checked before each delete, but a delete already under way completes), the only protection is the grace period: with the default one day such a process can delete only blobs untouched for a day, and a small `olderThanMs` removes that margin. A put that finds identical content already stored must be able to refresh its age, otherwise it replaces the file with the fresh copy, so an adopted old blob never keeps looking old.
- **The lock is keyed by the resolved directory path:** two spellings of one folder (a symlinked alias, different letter case on Windows or macOS) would get separate locks, so give every service the same path.
- **Smaller limits:** a repeat publication stores its blobs again before the replay record is found, and a command ID reused for a different command leaves its blobs behind before failing (both are ordinary orphans). The case-clash check uses lower-casing plus a few folds (ß, long s, dotless i), not full Unicode folding. There is no total-path-length rule (Windows' classic 260-character limit is the unpacking side's concern). A two-character folder that is a link is refused.
- **Not done:** streaming reads of very large files (`readFile` returns the whole file, bounded by `maxBytes`, default 64 MiB; verification hashes in chunks), compression, retention policy and deletion of old artifacts (K-cards), copying artifacts to remote hosts (H02), a blob store on network or remote storage, power-loss testing of the flush-and-rename order, and fsync of the directory on Windows (skipped there because directories cannot be opened). Windows file semantics (rename over an existing file, read-only flags) are covered by the CI matrix, not yet by the real-hardware QA of G06.

## S03 notes: durable transition delivery

`packages/controller/src/domain/events.ts`, `delivery.ts`, and the event writes in `service.ts`. The mechanism is the outbox already in the storage contract (F04a): the engine bridge is a destination that claims messages for `task-events`. `CommandRunner` commands can now also commit outbox messages, effect intentions, timers and extra audit entries in their own transaction (`Built.outbox` and friends).

- **No message without its change, no change without its message.** `createTask`, `updateTask` and `transitionTask` write one outbox message in the same storage transaction as the task change. A refused or failed command (stale revision, invalid transition, failed commit) writes neither; a repeated command is answered from its record and writes nothing new. The message's ID is `tev:<taskId>:<revision>`, so one revision of one task can be announced once (storage rejects a second use of the ID) and a repair can ask whether a revision already has its message.
- **Events are snapshots** (`taskId`, `projectId`, `revision`, `state`, `change`, `from`): "the task is now at revision r in state s". A receiver that misses one, sees one twice or sees one late applies the highest revision and ignores older ones. Messages of one task are delivered strictly in commit order; a message that keeps failing holds back later messages of the same task (and only that task).
- **`DeliveryDispatcher`** claims due messages, hands each to a handler, and records the handler's result as the receipt in one transaction with an audit record (`delivery.receipt`). Only the receipt makes a message delivered. A failing handler gives the claim back with a backoff (default 1 s doubling to 60 s). If the receipt cannot be recorded, the claim is left to expire, and the message is handed over again with the same ID. Delivery is therefore **at least once; the destination must deduplicate by `deliveryId`** (the inbox of card S04 does this on the receiving side). A receipt commit whose outcome is unknown is resolved by its operation ID (`rcpt:<deliveryId>`), as for every other operation.
- **Takeover.** When a lease ends another dispatcher may claim the message; the first dispatcher's late receipt then fails and is reported as `superseded`, with nothing recorded by it. A deposed controller's dispatcher stops with `stale_epoch`.
- **Cross-store gap.** `reconcileTaskEvents` pages through tasks and, for each whose current revision has no message, commits one (change `reconciled`, guarded by the task's revision, one command per task and revision, so repeating it changes nothing). It covers tasks written without a message (a store restored from a copy, records from before the outbox) and is what card S07's periodic scan will call. If a task moves while it is repaired, that repair is skipped: the command that moved it announced the new revision. It checks the current revision only, so a missed earlier revision is not recreated; snapshots make that unnecessary.
- **Tests.** The same suites on the reference store, SQLite, SQLite on a worker thread and PostgreSQL (36 tests): message written with the change, in order, as a snapshot; refused and replayed commands announce nothing; a commit failing before it happens leaves neither change nor message and one reported lost but committed is found by operation ID with one message; backoff and ordering behind a failing message; receipt lost then redelivered with the same ID to a destination that acts once; lost receipt commit resolved; takeover; stale epoch; reconciliation including paging. Plus four tests with a real child process killed with SIGKILL against a SQLite file (`delivery.crash.test.ts`): before the task's commit (no task, no message, the same command then makes both once), after it (message found and delivered once), after the destination has the message and before the receipt (redelivered after the lease ends, held once), after the receipt (not redelivered).
- **Not done or limited.** The consumer of `task-events` (the engine bridge, a durable inbox) is S04 and later cards; today only tests receive. Delivered messages are never deleted (retention belongs with K-cards), so an installation with no consumer accumulates messages. Only task records announce changes; project, assignment and artifact changes will announce when their consumers exist. There is no cap on attempts or visible blocker for a message that keeps failing; storage keeps the last error and attempt count, and S07 (bounded retry and blocker) adds the cap. The dispatcher is not a long-running loop: callers (S07) decide how often to call `runOnce`. Throughput was not measured. A pass handles its batch one message after another, so one slow handler delays other tasks' messages in the same batch (running independent ordering keys concurrently is a later improvement). When retention is added, reconciliation decides whether a revision was announced by looking its message up, so retention must keep an "announced" marker (or reconciliation must skip revisions older than the retention horizon), or purged messages would be announced again.

## S02 notes: assignment generations and attempt admission

`packages/controller/src/domain/assignments.ts` (`AssignmentService`) and `assignment-model.ts`. It shares the epoch and the command machinery of `ProjectService` (`AssignmentService.withEpoch(storage, epoch, projects)`).

- **Records.** `assignment` (one per task, ID derived from the task): generation, state (`assigned` or `released`), owner, the active attempt, attempts so far. `assignment-generation` (one per generation, written once, never changed): the history, with owner, who assigned, how the generation began (`assigned`, `transferred`, `reassigned`), the previous owner and a reason. `attempt` (ID derived from the admitting command): generation, owner, number over the task's life, state (`active`, `succeeded`, `failed`, `abandoned`, `superseded`, `released`). `activity` (one per task): see below.
- **Commands.** `assignTask` (first assignment, or after a release with the assignment's revision), `transferTask` (new generation, ends the active attempt as `superseded`), `releaseTask` (ends it as `released`; the generation number is kept so the next assignment is one higher), `admitAttempt`, `finishAttempt`, `observeActivity`. All are idempotent by command ID, revision-guarded and write an `assignment-events` message (a snapshot, ID `asv:<task>:<revision>`) in the same transaction, like S03.
- **Two competing admissions yield one writer.** Admission rewrites the assignment, so it commits against the assignment revision the caller read: of two admissions on one revision exactly one commits and the other gets `stale_revision`; one that arrives later and sees the winner is refused as `invalid_command` ("already has an active attempt"). The same holds for two first assignments of one task (both create the same derived assignment record). Repeated 6 times per backend in the tests, concurrently.
- **Fencing.** `AssignmentService.transitionTask` and `updateTask` take a `fence` (generation and attempt). The check runs inside the command and the assignment's revision is a guard in the same storage transaction as the task change, so a fenced write racing a transfer either commits before the transfer or fails with `fenced`, never after, and a refused write changes nothing. The fence is part of the command's digest. `finishAttempt` and `admitAttempt` are fenced the same way (generation, owner).
- **Observed activity is not ownership.** `observeActivity` stores the latest observation (who, which generation it claimed, what, when) and a count in its own record, so it does not contend with assignment writes. It keeps the latest observation and a count, not a log, and a second worker observing at the same moment may be asked to repeat (`stale_revision`). It marks the observation `current` only if the generation matches the current assignment, and it never changes the owner, the generation or the active attempt. A worker that lost its generation is visible and owns nothing.
- **Runner additions.** `Built.contention` lets a command say what a lost race means in its own terms (admission: `stale_revision`; a guarded task write: `fenced` if the guard now refuses, else `stale_revision`). New error code `fenced`.
- **Limits.** Admission re-checks the task's revision in its transaction, so an admission racing a task edit is asked to retry rather than admitted on stale state. The unfenced `ProjectService` commands remain; nothing forces an agent to use the fenced ones until permissions (A01) bind an actor to its fence, and the fence is not checked by the worker or adapter yet (T01/H01 carry that forward). Only task and attempt mutations are fenced; artifact publication and effects (S05) will take the fence the same way when they are tied to an attempt. There is no lease or timeout on an attempt: deciding that an attempt is dead and transferring is the controller's job (S07, V01). Attempts cannot be listed by task (only read by ID; the assignment counts them). A released task is not moved out of `in_progress` automatically. `observeActivity` loses a first-observation race with `stale_revision` and the caller repeats it.

## S04 notes: durable inbox, admission and settlement

`packages/controller/src/domain/inbox.ts` (`InboxService`). It is the receiving side of S03's at-least-once delivery.

- **Receipt.** `receive` writes an `inbox-message` record (ID derived from source and delivery ID: one record per delivery however often it arrives; payload kept, with its digest) and resolves only after the commit. `handler(source)` is a `DeliveryHandler`, so a `DeliveryDispatcher` acknowledges a delivery only for a message that is durably held; if the write fails the handler throws, the delivery is given back, and nothing was acknowledged (tested with an injected failure). A repeat is answered from the record (`replayed`); key order in the payload does not matter. The same delivery ID with a different payload is `payload_changed` (new error code) and changes nothing.
- **Admission.** `admitAssignment` turns an assignment message into an attempt. It decides from the **current** assignment, not from message order: an event that does not announce a new owner is `ignored`; one whose generation or owner is no longer current is `superseded` (settled, no attempt); a task that is cancelled or done is `task_closed`; a task that is not ready or in progress yet is **deferred** (nothing is recorded and the same call can be repeated later); a task that already has an active attempt is `already_active` (names it); otherwise an attempt is admitted through `AssignmentService.admitAttempt` with a command ID derived from the message. A duplicate message, a repeat call, two concurrent calls, or a repeat after a crash between creating the attempt and recording the decision therefore find the same attempt instead of creating a second (tested concurrently and with an injected failure at the recording step).
- **Decisions are guarded.** A decision that says "no attempt was made" (`superseded`, `task_closed`, `already_active`) is recorded together with a check of the assignment revision it was read at, so it cannot be recorded after another caller created the attempt for the same message; the loser re-reads, finds that attempt and records `admitted` (tested by interleaving, and the test fails without the guard).
- **Settlement.** `settle` moves an admitted message to `settled` with an outcome (`completed`, `failed`, `abandoned`) and optional detail; revisioned and idempotent; only an admitted message can be settled.
- **Attribution.** The commands an admission issues use the fixed actor `inbox`, not the caller: they derive from the message, so two callers issue identical commands and the second is answered by the first. The caller's `actor` is validated but not recorded for admission: the operation's audit entry is part of its hash, so adding the caller to it would make two callers' commands differ.
- **Limits.** Admission is implemented for assignment messages only; other kinds can be received and settled, and `admitAssignment` marks them `ignored`. The inbox and the sender share one controller store here; a remote worker's inbox (H01, H02) will be a separate store with the same contract. Messages are never deleted (retention is a K-card). `sequence` and `orderingKey` are recorded but nothing orders by them: decisions use current state. A delivery the inbox refuses outright (an invalid or oversized payload) makes the handler throw, so the dispatcher retries it with backoff until the retry cap of S07 exists. `payload_changed` also covers a changed ordering key or sequence (the digest covers the message's metadata). No real-process kill test (the crash points are covered by injected failures at each of the two commit steps).

## S05 notes: effect ledger and idempotent bridge

`packages/controller/src/domain/effects.ts` (`EffectService`, `EffectBridge`, `EffectRejected`). The ledger rows (status `intended`, `uncertain`, `confirmed`, `failed`; target; input digest; reconciliation handle) are the ones the storage contract already had (F04a); the service adds the full input, the claim and the rules for moving a row.

- **Intent first.** `intend` writes, in one transaction, the ledger row and an `effect` record holding the full input and the external key (the key is the effect ID, derived from the command ID, so it is stable across retries and processes). If the effect is done on an attempt's behalf the fence is checked in that transaction (`fenced` otherwise, nothing recorded). Repeating the command returns the same effect.
- **Bridges.** A bridge declares what its target can promise: `idempotent` (executing again with the same key applies at most once) and optionally `reconcile` (the target can be asked whether the key was applied). A bridge with neither is an **unsupported target**. A bridge throws `EffectRejected` only when it knows the target refused (the effect becomes `failed`); any other error means the outcome is unknown.
- **Executing.** `run` claims the effect (a revision-guarded write with a lease, default 5 minutes, holder named per executor; with the fence as a guard in the same transaction), calls the bridge once with the key, and records the result and releases the claim in one transaction. Any unexpired claim, the executor's own included, makes the effect busy (`effect_busy`), and an executor also refuses a second `run` of an effect it is running; so two executors, two calls on one executor, or a restarted process reusing a name cannot both act. A run that ends without a result (the target could not be reached, an error) gives its claim back; a process that dies keeps it until the lease ends.
- **Recovery after doubt** (a crash after the outside success and before the result was saved, or an error with no answer): a started effect is never simply executed again. If the target can be asked, it is asked: applied -> confirmed (marked `recovered`), not applied -> executed, does not know -> `uncertain`. Otherwise, if the target is idempotent it is executed again with the same key (an idempotent target that cannot be reached leaves the effect `pending` and the caller repeats `run`). Otherwise it becomes `uncertain`.
- **A vanished executor.** If an earlier executor disappeared holding the claim, its request may still be in flight, so a target that does not honour a key is **not** executed again on a "not applied" answer (it becomes `uncertain`); a keyed target is. A result that arrives after the lease passed to another executor is not recorded over theirs (the late executor is told `pending` and why; the new holder reconciles, and if nobody holds the claim any more the late result is recorded and resolves an `uncertain` effect). A concurrent or contradicting settlement is reported as what the ledger holds; a final result contradicted later is an `integrity` error.
- **Uncertain blocks blind retry.** Every `run` or `perform` of an uncertain effect is refused (`effect_uncertain`); only `resolve`, a person's recorded decision (`confirmed` or `failed` with non-empty evidence saying how the target was checked), moves it on, and only from `uncertain`.
- **Fencing.** An attempt that lost its generation before the effect started never starts it (`failed`, "superseded before it started", the bridge is not called). One that lost it after it started only asks the target (applied -> confirmed; not applied -> failed; cannot ask -> uncertain); it never applies the effect again.
- **Tests.** The same suites on the reference store, SQLite, SQLite on a worker thread and PostgreSQL (70): each of idempotent, askable and unsupported targets confirmed once and repeated without effect; a refusal; crash after the outside success and before the result was saved for each kind of target (applied once / asked / uncertain and never sent again, then resolved by a person); lost answer; unreachable idempotent target; askable target that never got the request; fence lost before and after start; two executors, the same executor twice, a reused name and lease takeover; a late result after the lease passed on. Plus two tests with a real SIGKILL against a SQLite file and a file as the outside world (`effects.crash.test.ts`): an idempotent target applies once after restart, an unsupported one becomes uncertain and nothing is sent again.
- **Limits.** The service does not decide which effects need a bridge or which are "protected" (the permission cards A-series do); nothing yet forces agent tool calls through it (T01, A04 and A05 do that). Recovery after a crash waits for the crashed executor's lease to end before another executor may act (`effect_busy`), five minutes by default. The lease must exceed the bridge's worst case: if a request outlives its lease, a target that cannot be keyed and has no way to be asked may be applied twice by the second executor only if it answers "not applied" and the first request landed in between; the vanished-executor rule above turns that case into `uncertain` instead. Evidence is stored as given, with no size limit beyond the storage body limit. `pending` is not durable state beyond the effect remaining `intended`: the caller (S07's repair scan) decides when to repeat. No outbox message announces effect results yet. An effect's ledger row and record cannot be deleted (retention is a K-card).

## S07 notes: startup and periodic reconciliation

`packages/controller/src/domain/reconcile.ts` (`Reconciler`), `blockers.ts` (`BlockerService`), and bounded retry in `delivery.ts`.

- **No wake-ups needed.** `runPass` reads durable state and does what is pending; it is the startup repair (call it once when the controller starts) and the periodic one (call it on a timer; the timer itself is the controller process's, not part of this card). A dropped wake-up, a crash or a restart costs only a delay. Nothing in it calls a model: every step is a rule over stored records.
- **A pass** (1) announces tasks whose current revision has no event (`reconcileTaskEvents`, S03); (2) delivers due messages to each configured destination, with bounded retry; (3) admits received inbox messages (`admitAssignment`, S04); (4) runs effects that an executor started and did not finish (`EffectService.run`, S05) and opens a blocker for an uncertain one. The report says what each step did and whether the pass reached the end of every scan (`complete`). Admitting an attempt announces itself (assignment events), so the next pass delivers and settles those; a pass after that finds nothing (tested).
- **Cursors.** The task-event, inbox and effect scans look at a page per pass (`pageSize`, default 100) and keep a durable cursor (`scan-cursor` records), wrapping at the end, so a restart between passes continues where the last stopped and a large backlog is covered over several passes without one pass growing without bound. Two reconcilers saving a cursor at once keep the first's position.
- **One bad record cannot stop a pass.** Each step of a pass stands alone, and inside the task-event, inbox and effect steps each item does too: a failure is counted (`errors` in the report), the cursor is still saved and the rest go on. Only losing the epoch stops a pass. A record that fails for a lasting reason (`integrity`, `invalid_command`, `not_found`, a changed payload) is skipped from then on and one `scan_failure` blocker names it and who resolves it; a passing trouble (storage unavailable) is only counted and retried next pass.
- **Bounded retry and visible blockers.** Handler failures (not claims: a message found held is not a failure) are counted per delivery in a small record; a message that has failed `maxDeliveryAttempts` times (default 5) is not retried on the normal schedule: a `delivery_exhausted` blocker is opened (one, however many passes find it; it says which delivery, how often it failed, the last error and who resolves it) and the message is looked at again only every `holdCheckMs` (default 5 minutes), without calling its handler while the blocker is open. Resolving the blocker lets delivery resume with a fresh count of failures (the count is cleared the next time the message is claimed after its blocker is gone), so a message whose cause is not yet fixed needs the full allowance again before it is held again. An uncertain effect gets an `effect_uncertain` blocker the same way.
- **Manual holds.** A `manual_hold` blocker on a task, an inbox message or an effect makes every pass leave the corresponding inbox messages and effects alone (reported as held). No pass opens, edits or resolves a manual hold; only a person resolves a blocker (`resolveBlocker`).
- **Blockers.** `BlockerService`: a record per blocker (type, subject, summary, resolver, state, who opened it, next review) and a slot per (type, subject), so opening is idempotent while one is open and "is this held?" is a single read; resolving closes it and a later trouble opens a new one. Types: `manual_hold`, `delivery_exhausted`, `effect_uncertain`, `scan_failure`, and `wait_overdue` and `unexplained_block` (used by S08). Resolving checks that the slot names the blocker being resolved (`integrity` otherwise).
- **Limits.** The hold on a delivery is checked when it is next claimed, so a resolved blocker releases the message within `holdCheckMs`, not instantly. The pass delivers one message per task per round (strict per-task order) and stops a destination's rounds when a round delivers nothing, so a slow handler delays the pass. A manual hold does not stop *delivery* of a held task's events (only admission and effects); holding a delivery is the `delivery_exhausted` blocker. Effects of a kind with no configured bridge are reported (`effectsUnbridged`) and left alone. Passes run in one process: nothing prevents two reconcilers running at once (they are safe, because every step is idempotent and revision-guarded, but they do duplicate work). No timer, shutdown handling or metrics yet.

## S08 notes: typed waits and deadline settlement

`packages/controller/src/domain/waits.ts` (`WaitService`), with two more steps in the reconciler (`reconcile.ts`).

- **A wait states its terms.** `openWait` needs a reason (`inquiry`, `approval`, `review`, `external`, `dependency`, `input`), a resolver ID, a summary, what happens when it is answered (`nextAction`), and exactly one of: a deadline with what happens at it (`onDeadline`: `resume`, `cancel` or `escalate`), or an explicit indefinite hold with its owner. Anything else is refused, so a waiting task always has a next action or a named owner. Opening blocks the task (ready or in progress only), writes the task event, schedules the deadline timer and records the wait, all in one transaction. A task has one open wait at a time (a per-task slot record). It can be opened on an attempt's behalf under a fence.
- **Answering.** Only the named resolver, only while the wait is open and the task is still blocked: the task goes back to ready, the timer is cancelled, the wait records the answer, who gave it and when, in one transaction. An answer to a wait that has closed, or whose task was cancelled or finished meanwhile, is refused as `wait_closed` and changes nothing, so a late answer cannot revive cancelled work. `cancelWait` ends a wait and either cancels the task (the operation is cancelled) or resumes it.
- **Deadlines.** `settleDue` claims due timers and, in one transaction per timer, completes the timer, closes the wait as timed out and applies `onDeadline` to the task (ready, cancelled, or left blocked). An answer racing a deadline is decided by the storage revision: exactly one commits (tested, repeated per backend). A timer whose wait already closed is just completed.
- **Overdue and orphaned waits.** The reconciler pass settles due deadlines; for an `escalate` wait it opens a `wait_overdue` blocker on the task naming the resolver, the reason and the next action; and it closes an open wait whose task was cancelled or finished (`waitsOrphaned`).
- **No blocked task is left unexplained.** The pass scans blocked tasks (with a cursor) and, for each that has neither an open wait nor an open `manual_hold` / `wait_overdue` / `unexplained_block` blocker, opens one `unexplained_block` blocker asking the owner to give it a wait or release it. It does not change the task. A blocked task is therefore always either explained or visibly flagged within one pass.
- **Limits.** `ProjectService.transitionTask` can still block a task without a wait (it is the unfenced controller path); the scan above is what makes that visible rather than preventing it. The resolver ID is matched as given: proving the caller *is* that resolver is the permission cards (A01). Deadlines use the controller's clock, so a skewed clock moves them (the timers are claimed with a caller-supplied `now`, as everywhere in storage). `settleDue` handles at most `limit` timers per call; the reconciler calls it once per pass. A wait answered by an inquiry transport (H04) is not wired here. Resolving a `wait_overdue` blocker without acting on the task (answering, cancelling or releasing it) only makes the pass open a new one the next time the wait scan wraps: resolving it means acting on the task. A wait whose task stopped being blocked by another route is closed by the pass with the task left exactly as it is.

## A01 notes: authenticated principals and capabilities

`packages/controller/src/security/` (`PrincipalService`, `SecureApi`, `access.ts`, `credentials.ts`, `redact.ts`).

- **Identities.** `owner:<name>`, `agent:<name>`, `host:<name>`. The installation has exactly one owner: `bootstrapOwner` creates an `installation` record and the owner in one transaction, so a second bootstrap (or two racing ones, whatever names) is refused. The owner enrolls agents and hosts, sets their grants, disables them and issues credentials; nobody else can. The owner cannot be disabled.
- **Credentials.** A token is `<principal id>.<secret>`; the secret is 32 random bytes, shown once to the caller of `bootstrapOwner` or `issueCredential`, and stored only as a salted scrypt hash. It is in no aggregate, audit record or read (`get` never returns the credential). Issuing a new credential replaces the old one at once; a crash between storing it and reading the token loses it (issue again). `authenticate` fails identically (`unauthenticated`, one message) for an unknown principal, a wrong secret, a malformed token and a disabled principal, and does the same hashing work in each case.
- **Grants.** A grant is `{ action, project }`: an action name (`task.create`), a prefix (`task.*`) or `*`, in a project ID or `*`. The owner may do everything. Anyone else may do exactly what a grant covers in the project it names; a grant for project A says nothing about B. An action that belongs to no project (creating a project, managing principals) needs a grant whose project is `*`. Grants are part of the principal record and take effect at the principal's next authentication (a `Principal` object is a snapshot). Revisioned grants, restrictions, expiry and delegation are A02.
- **`SecureApi`** exposes the project, task and assignment services for one authenticated principal. Every call: takes the actor from the principal (a command naming another actor is `forbidden`, never corrected); finds the project from the stored record (never from what the caller says) and checks the action there; for work done as an attempt's owner (admit, finish, fenced task writes) requires that the principal **is** the assignment's current owner; refuses a record in another project and a record that does not exist alike (`forbidden`; only the owner gets `not_found`); lists only readable projects, and lists tasks only within a named project (the owner may list across). Messages are cleaned of secrets (`redactText`) before they leave.
- **Tool path.** `authorizeTool(name, projectId)` is the same check for the action `tool.<name>` (prefix grants like `tool.shell.*` work), so API and tool calls share one rule. Wiring it into the registry and the Pi adapter's tool execution is T01/A04/A05, which carry it forward.
- **Redaction.** `redact` replaces the value of any field named like a secret (secret, token, password, credential, api key, authorization, private key, cookie) and, in any string, NimbleNewt tokens, bearer tokens, common provider key shapes (`sk-`, `ghp_`, `github_pat_`, AWS keys), PEM private keys and passwords in database URLs; depth-limited.
- **Review fixes (the first review found these and they are fixed and tested):** a refusal on a record in another project reads exactly like a missing record and names no project (non-owners only); command IDs are tied to the principal (`<principal id>:<hash of the caller's ID>`), so two principals using the same ID neither meet, probe nor block each other, and their derived record IDs differ; a replayed `bootstrapOwner` is refused instead of returning a token nothing stores; `observeActivity` accepts only the principal's own name (the installation owner may report for anyone); the tool gate takes the task and finds the project from the stored task; listing projects fills the page with readable ones and gives a `next` cursor; credential hashing is asynchronous.
- **What "secrets redacted" covers, plainly:** the credential itself is never stored, audited, logged or returned; `redact` and `redactText` clean what `SecureApi` returns in error messages and are available to every caller that logs or shows data. Stored content (task descriptions, activity detail, audit details) is **not** passed through them by the services; the desk and history services refuse credential-shaped text instead. Matched shapes: NimbleNewt tokens, bearer tokens, `sk-` / `ghp_` / `github_pat_` / `xox*` / AWS key shapes, JWTs, PEM private keys, URLs with a password, and `password=` / `secret=` / `token=` / `api_key=` pairs; fields are judged by their last word (`apiKey`, `client_secret`, `accessToken` yes; `inputTokens`, `userKey` no). Not covered: arbitrary high-entropy strings and secrets in free prose without one of those shapes.
- **Limits, stated plainly.** The unsecured services (`ProjectService`, `AssignmentService`, ...) remain the controller's own internal path; nothing yet forces every caller through `SecureApi` (the API, tool and worker cards must). Only projects, tasks and assignments are covered (desks and histories, C01, take the principal themselves); artifacts, effects, waits, blockers and the inbox are not yet behind it. **The tool gate (`authorizeTool`) is a function that nothing calls yet**: the registry and the adapter's tool execution (T01, A04, A05) must, so "permission checks cover tool paths" is true of the gate, not yet of any tool run. There is no throttling or lockout of repeated failed authentication, no token expiry, and no transport (TLS, session handling) here. Authorization is evaluated at call time, not when a long-running command was queued (A02/A05 add revalidation at execution). The owner's identity is a name chosen at installation, not a verified person; multi-human administration is a separate design decision. Authenticating still takes the principal's current grants only at that moment (a `Principal` is a snapshot).


## C01 notes: desks and scoped histories

`packages/controller/src/context/` (`DeskService`, `HistoryService`); they take the authenticated `Principal` of A01 and use the same grants.

- **Desks.** A `desk-record` belongs to a persistent agent identity (`agent:<name>`, so changing its model or harness changes nothing) and to one project, with kind (plan, progress, evidence, decision, note), status (`draft`, `accepted`, `superseded`), visibility (`shared` or `private` scratch), an optional task of the same project, and an optional record it supersedes (the old one becomes `superseded` in the same transaction). Only the owner writes or revises a record, found from the stored record, and revising needs `desk.write` now (revoking the grant ends the right to change records already written): a peer, a supervisor with every grant and the installation owner are all refused; the human owner may read but not write an agent's desk. Writing needs `desk.write`, reading `desk.read`, in the record's project; a record in another project is refused and reads like a missing one. Peers see only committed records (`accepted`, `superseded`); a draft is the owner's working copy and can be edited. **A committed record is not edited in place or taken back to draft** (peers have read it): write a new record that supersedes it. **Private scratch is read only by its owner or by a grant that names `desk.scratch.read`: a wildcard grant (`*`, `desk.*`) is not enough** (**the installation owner reads every agent's private scratch** and every shared record but **not their drafts**, and may join any chat: these are privacy rules chosen here, because the design leaves human inspection and retention policy undefined, and are open to the owner's decision). Credential-shaped text is refused. Records are data: nothing is executed or granted by reading one.
- **Histories.** A `history-scope` is a task's history (its ID derived from the task, created by the first append), a chat or a meeting (opened with a participant list of enrolled principals). Entries are appended with a gap-free sequence, one scope per entry, assigned in the same transaction that raises the scope's count; two appends at once both succeed in order (a loser retries). A task history follows the project (`history.append` / `history.read`, project found from the stored task); a chat or meeting is for its participants and the installation owner; each participant must hold `history.read` in the project when the chat is opened and `history.read` / `history.append` each time it reads or writes, so revoking a participant's grant ends access to the project's chats (a principal in the list without the grant is refused; a principal with every grant who is not in the list is refused too). **The role of an entry comes from the principal** (the owner speaks as `user`, an agent as `agent`; a different role is refused, `system` and `tool` are not available to callers). A chat may point at a task but its entries never enter the task's history (tested). Credential-shaped text is refused. Command IDs are tied to the principal, as in A01.
- **Limits.** Retrieval over histories and desks (summaries, search, links to originals) is C02; indexes, files and artifact links are not yet covered by these checks. No retention or size limit beyond 16,000 characters per desk record and 8,000 per history entry; no deletion. Participants cannot be added after a chat is opened. Reading a scope whose task does not exist yet returns the same refusal as one the caller may not see. An agent that serves several projects holds a separate grant per project; nothing here stops it copying text between projects by hand, only the records themselves are project-bound.

## A02 notes: revisioned grants and restrictions

`packages/controller/src/security/grants.ts` (`GrantService`); `access.ts` now judges resources, expiry and restrictions.

- **Grants.** The owner records a grant for an agent or host: action (`task.read`, a prefix such as `task.*`, or `*`), project (or `*`), optionally one resource (`{kind, id}`, such as one task), an optional window (`notBefore`, `expiresAt`), its source (`direct`: for something specific; `standing`: a lasting delegation), and the wording it came from (`basis`, free text, refused if it looks like a credential). It has a revision; revoking needs the current revision and a reason and happens once. Only the owner grants, revokes, restricts or lifts (an agent that tries is refused).
- **Derived grants.** A step reasonably necessary under a grant is covered without a new decision: the grantee (or the owner) derives a grant that **rests on** a grant the grantee holds. It must be inside the parent (action covered by the parent's, same or narrower project, same resource when the parent names one, a window no wider); a wider one is refused. It ends when its parent does (expiry, revocation, or its own parent's), through any depth (limited to 8 levels). Deriving from a grant one does not hold, or one that is not there or already revoked, gets the same refusal.
- **Restrictions.** The owner forbids an action (and optionally one resource) for one principal, or for `*`: everyone but the owner. A restriction always beats every grant, derived ones included, while active; it can expire or be lifted. A restriction that names a resource also applies when the caller did not say which resource (the safe reading); a grant that names a resource counts only when the caller says that resource. `SecureApi` says the task for every task-level check and for the tool gate.
- **When a change takes effect.** A `Principal` is a snapshot of its grants **and restrictions** taken at authentication (`authenticate` returns it with both loaded; `GrantService.effective(principal, now)` takes a new one). A new restriction, a lift, a revocation and a new grant show **only from the next snapshot**, not in one already held. `allows` refuses a non-owner principal that has no snapshot time (`asOf`), so a principal built by hand, which never had its restrictions loaded, is refused rather than trusted. expiry is also judged at each check (by the wall clock unless a `now` is passed; services with an injected clock do not yet hand it to `allows`), so a stale snapshot does not outlive a grant's `expiresAt`. A long-running operation that started before a revocation is not interrupted here: revalidating at execution is A05/A04's.
- **Explaining.** `explain(principal, action, project, now, resource?)` takes its answer from `allows` itself and only names the grant or restriction that decides it.
- **Reading grant records is not access-checked.** `getGrant` and `getRestriction` return the record, including the owner's wording (`basis`), to whoever holds the service; any API that exposes them must make them owner-only (or the grantee's own).
- **Depth.** Derivation is refused beyond eight levels; a deeper chain would also fail closed when judged.
- **Limits.** Grants given at enrollment (A01) still exist and cannot be revoked individually (use `setGrants` to replace them); they carry no window. `effective` reads every grant and restriction record on each call (fine for the expected numbers, to be indexed by principal if they grow). There is no approval workflow and no delegation chain beyond derivation; nothing yet *creates* derived grants automatically (the tool and review cards will), so "necessary scoped actions covered without redundant approval" is shown here for derivation by an explicit call. Restrictions apply by action, project and resource only (not by data class or time of day).

## H01 notes: worker hosts

`packages/controller/src/hosts/` (`HostService`). A host is an enrolled principal of kind `host` (A01); this adds what the controller records about it.

- **Identity.** The identity is the credential, never the name or address. Rotating it (`issueCredential`) ends the old token at once, and also ends any `Principal` object obtained before the rotation (each carries a digest-based id of the credential it authenticated with, compared with the stored one on every call), and keeps the host's record; revoking it (`disable`) makes every later authentication fail, and `HostService` also checks the stored identity on each call, so a `Principal` object a caller still holds from before the revocation is refused too (`unauthenticated`). The check is made just before the write, not inside it, so one heartbeat already past the check can still be accepted at the moment of a revocation.
- **Announce and heartbeat.** The host states its capabilities (OS, architecture, harness versions, isolation backends, tools, named workspace bindings; bounded, free of credential-shaped text, unknown fields refused) and repeats it after an upgrade. A heartbeat carries a sequence number that must be higher than the last accepted one, so an old message replayed later cannot make a dead host look alive; the controller stamps it with **its own** time (a time sent by the host is refused as an unknown field). A host on a new credential (rotation, reinstall) starts its own sequence from 1 (what the old credential sent can no longer authenticate); the same credential never goes backwards. Concurrent heartbeats are safe: each accepted one is counted once.
- **Freshness.** `status` and `list` report `identity` (`active` / `revoked`) and `freshness`: `unknown` (never heard from), `fresh` (last heartbeat within the window) or `stale`. The window is 90 seconds by default (three beats at 30 s), provisional and configurable per `HostService`. Staleness is evidence about the connection only and the status says so; the later cards decide what to do about it.
- **Ownership is never released here.** Nothing in `HostService` writes an assignment. A stale, silent, rotated or revoked host keeps every task it owns, with the same owner, generation and revision (tested); releasing, transferring or fencing is the owner's explicit command (S02) and the later reconciliation cards'.
- **Progress.** `reportProgress` records the task's observed activity under the host's own identity (the caller cannot name another), needs `attempt.work` in the task's project, treats an unrelated project's task like a missing one, and changes no ownership. **Any host holding `attempt.work` in the project can report on any task in it**, not only on tasks it works on (workers are not yet linked to hosts, H03): the record names the reporting host truthfully, and stall detection must compare `observedBy` with the task's owner or worker before reading it as that owner's liveness. It does not refresh freshness, and a heartbeat is not progress (they are separate evidence).
- **Visibility.** A host reads only its own status (another host reads as absent); the owner lists (paged, with `next`) and reads all. Other principals get nothing. A name that was never enrolled, or is not a host, has no status (it is not reported as revoked).
- **Limits.** The controller does not verify the claimed capabilities. There is no transport here (TLS, sessions, a network protocol), no automatic action on stale hosts, and no limit on how often a host may beat. Heartbeats are written one record per host (a write each); at the expected host counts that is fine, to be batched if it grows. Who the host's workers are, and fencing their attempts on revocation, belong to H03/A04/A05 and the reconciler.

## R01 notes: model routing and capability policy

`packages/controller/src/routing/` (`policy.ts`: the rules, pure; `service.ts`: the durable table).

- **The table.** One durable record, so one revision says exactly what was in force: providers (`enabled`, `paid`, `local` or `cloud`), routes (`provider/model`, with the context size and capabilities the model supports), profiles (ordered route lists, first choice first, such as the difficulty levels of the configuration) and roles (which profile each role uses). The owner replaces it with `setTable`, which validates all of it first (unknown providers or routes, a route listed twice, bad names, limits, prototype-style keys) and applies nothing if any part is invalid. `expectedRevision` is required (0 when there is no table yet), so two editors cannot silently overwrite each other.
- **Exclusions.** The owner excludes a provider or a single route, with a reason, and lifts it later. They are part of the same record and survive a new table, **but a new table that drops or renames an excluded provider or route is refused** (lift the exclusion first), and provider or route names that differ only by case are refused, so an exclusion cannot quietly stop pointing at anything. They apply to the **next** dispatch: `select` reads the table at the moment of the call (no cache), so retries and helper calls are covered the same way as a first attempt. A task's preferred route is tried first but passes the same rules, so it cannot bypass an exclusion; it may be any configured route, **not only one in the role's profile** (it still needs the data and spending authorizations). Excluding a name that is not in the table is refused (a typo must not exclude nothing).
- **Selection.** For a role (or an explicit profile) the candidates are the preferred route then the profile's routes in order. A route is skipped, with the reason recorded, when: its provider is disabled or excluded, the route is excluded, the request needs more context than it supports, it lacks a capability the request needs, it runs in the cloud and the task's data may not leave the installation (`data: "local-only"`), or it is paid and spending is not authorized. The first eligible route is chosen; if there is none, there is **no choice**: nothing is invented, no sample endpoint is used and no paid provider is picked on its own. The answer lists every candidate with its reasons (an exclusion's reason text, written by the owner, appears in them, so a selection should be treated as owner-visible) and carries the table revision, so an attempt can record which routing decision it ran under.
- **What the caller supplies.** The request's `data` and `paidAuthorized` come from the task's existing data-sharing and spending authorizations (the approval cards); R01 does not decide them. Only the controller's dispatcher calls `select`; it is not exposed to agents or workers.
- **Limits.** The table is built by calling `setTable`; reading the configuration document (F02) into a table, and showing "why a route is unavailable" in a UI, are separate steps (U01 and later). Context size and capabilities are what the owner states; the controller does not probe the models. There is no per-user or per-project routing, no cost accounting, and no automatic exclusion on failures (the supervisors of later cards raise those). A route being healthy right now is not checked here, only the policy.

## C02 notes: bounded, source-backed retrieval

`packages/controller/src/context/retrieval.ts` (`RetrievalService`), with `HistoryService.listScopes` added for it. It reads only through `DeskService` and `HistoryService`, so every result is checked against the reader's rights at the moment it is read.

- **Search.** A project's desk records, then its history entries, by plain word matching (case-insensitive; query words of two or more characters, at most eight; a record matches when at least one appears, and `matched` counts how many). A hit carries a link to the original (`desk-record` ID, or `history-entry` scope and sequence), the project, the title and a snippet of at most 240 characters around the first match (the text is passed through the secret redaction before it is cut). Records the reader cannot read (another agent's draft or private scratch, another project, a chat the reader is not in) are not searched, so they appear in no hit and no snippet. Results are in a stable order with an opaque, validated cursor, no match twice across pages (items added after a search started, such as new records or new entries in a scope already passed, may be missed until a new search); one call looks at no more than 2,000 items and says `scanLimited` when that is why it stopped. **The 2,000-item stop is implemented but not exercised by a test** (it would need thousands of records); the paging that covers it is.
- **Links.** `fetch` follows a link and returns the original with a digest if the reader may read it; a link to something missing and a link to something unreadable both return `undefined`.
- **Summaries.** `summarize` records a summary (text up to 4,000 characters, credential-shaped text refused) of one to fifty originals in one project. The writer needs `desk.write` in the project and must be able to read every original, each of which must belong to the project; a digest of each original's text is kept. `resolve` follows every link again as the reader and reports each original as `current`, `changed` (the original differs from what was summarized: for a desk record its text, title or status, so a draft that was edited and an accepted record that has since been superseded both show as changed; history entries do not change) or `unavailable` (gone, or not readable by this reader: the two are not told apart). **The summary text is shown only to a reader who can read every original**; otherwise it is withheld, with the sources listed by state, so a summary cannot be used to read what a permission hides. A reader needs `desk.read` in the project at all.
- **Assembly.** `assemble` takes wanted items (originals or summaries) in order and a character budget (1 to 200,000; at most 100 items) and fills it: an item that fits is included whole, one that does not fit but leaves at least 200 characters is cut and marked `truncated`, and the rest are listed as `over-budget`; unreadable or missing items are listed as `unavailable`. Every wanted item is in exactly one of the two lists, so nothing is hidden when the budget runs out or a source is missing; a summary whose originals changed carries a note saying so.
- **Limits.** The search is word matching, not semantic and not ranked beyond the count of matched words; it does not search tasks, artifacts or tool output, only desk records and histories, and only history scopes that exist. It scans rather than uses an index (the scan cap bounds one call). Summaries are not edited or deleted, and no summary is made automatically (a later card will have the agents or the supervisor write them; automatic compaction is Pi's own, G01 decision 12). The character budget is not a token count; callers convert.

## H03 notes: priority admission and reserved control capacity

`packages/controller/src/admission/` (`policy.ts`: the rules, pure; `service.ts`: the durable record `AdmissionService`). Its calls take the caller as an `actor` string like the other base services; the authorization wrapper comes with the API (U01).

- **One record, one decision.** What is running and what waits live in a single small record, so every decision is made on the whole picture in one guarded step, survives a restart, and two decisions at once meet a revision check (the loser decides again on the new picture, with a short random pause; up to 80 tries). The record is bounded (queue at most the configured length, default 100, at most 500).
- **Limits (decision D6, owner-accepted):** four productive attempts in total, two per host, and two places reserved for inquiries and reviews together. Productive work never occupies the reserve and control requests never take productive places (tested with every productive place taken: an inquiry and a review start at once, a third waits). Provisional, configurable and bounded: queue length 100, spawn depth 3, 4 live children per attempt, patience 5. `setLimits` validates every value; lowering a limit stops nothing that is running, it only admits nothing new until the system is under it.
- **CPUs and memory.** The owner declares each host's CPUs and memory (`setCapacity`); a productive request names its host, CPUs and memory. Inquiries and reviews are **not** counted against a host's CPUs and memory (they are small and must stay possible on a host that productive work has filled; only the lane's two places limit them), though a host they name must be an active one. So up to two inquiries or reviews can run on a host whose declared CPUs and memory productive work has fully claimed: **the declared capacity covers productive work only**, and the host as a whole can go over it by that small reserve. It runs only if the host's running requests plus this one fit, waits if they do not, and is refused if it could never fit or the host has no declared capacity or is not an active host.
- **Order and fairness.** Within a lane, higher priority (0 to 9) goes first, equal priorities in arrival order. A waiting request counts as passed over when a later one is admitted ahead of it and they compete for the same thing (the same host, the lane, or it could have run but was outranked); work on another host does not count. After the patience number of times it is "starved": served ahead of everything in its lane, and if it does not fit yet it holds back **only what it waits for** (its own host, or the whole lane when the lane itself is full), so work for other hosts carries on and smaller requests cannot keep taking what it needs. Tested with a steady stream of higher-priority work (the low one is served within a bounded number of rounds) and a large request among small ones.
- **Nothing waits for ever on something that cannot happen.** Before any change the service withdraws waiting requests whose host is no longer an active host, or whose declared capacity can no longer hold them (the owner lowered it), together with what they started and left waiting; the reason is kept (the last 50) and `where` reports `withdrawn` with it. Disabling a host does not call into this service by itself: the next change of any kind does the sweep first, or call `sweep` right after disabling so the withdrawal is on record at once. Running work is never touched by this.
- **Stop and revoke never wait.** `release` gives a place back, or withdraws a waiting request, without needing any capacity, whatever the saturation; it is safe to repeat (same command replays) and an unknown request is `not_found`. Releasing a request also withdraws the requests it started that are still waiting; ones already running are left, to be released on their own. Waiting requests that now fit are admitted in the same step.
- **No runaway spawning.** A request started by another must name a running parent, to a depth (default 3) and a number of live children per parent (default 4); the queue bound and the total limits apply to children as to anyone.
- **Limits of this card.** This decides *whether* and *in what order* work may start; it does not start anything, measure real CPU or memory use (the requested figures are what is counted), pick the host (the dispatcher names it), or check host freshness (H01 provides it for the dispatcher to use). Nothing here enforces the figures on the running process (the sandbox cards do). The single record is a deliberate simplicity trade: it serialises admission decisions, which is fine at four to a few dozen running requests and is the thing to revisit if that grows. Request IDs derive from the caller's command ID, so a replayed request that has since been released reports `released`; and because callers are plain `actor` strings here, they share one command-ID namespace (the per-principal scoping of A01 comes with the wrapper in U01). A lost race on the record is retried (up to 80 times, with a short random pause); a command ID reused for a different command is a real conflict and is retried only a few times, not for long.

## H04 notes: durable inquiries and correlation

`packages/controller/src/inquiries/` (`InquiryService`). It takes the authenticated `Principal` (A01) and builds on the side chats of C01, the retrieval of C02 and the typed waits of S08.

- **What an inquiry is.** A durable record: the question, who asked (a principal working on the task: `attempt.work` for that task), who is asked (`to`, an enrolled principal who can read the project's histories), the task and project (taken from the stored task), the side chat that carries the conversation, the asker's assignment generation when it asked, optional links to context, and its state (`open`, `answered`, `closed`, `cancelled`). Its own ID is the correlation in every step about it. A principal with no right to work on the task gets the same refusal as for a task that does not exist.
- **Side chat.** The question is the first entry of a chat (C01) between the asker and the addressee; the answer is the second. Nothing enters the task's own history (tested). The addressee needs `history.read` / `history.append` in the project, enforced when the chat is opened and each time it is used.
- **No transfer of ownership.** Asking, waiting and answering write no assignment: the asking attempt stays the owner throughout (tested by comparing the assignment before and after, same owner, generation and revision). `view` tells a reader whether the task's assignment is still at the generation it had when the question was asked (`generationUnchanged`), so a question that outlives the assignment it was asked under is visible as such (it does not claim the asker owned the task).
- **While the main attempt waits.** The asker may link an open typed wait (S08) of reason `inquiry` on that task whose resolver is the addressee; answering the inquiry then answers the wait, and the task goes back to ready. The inquiry does not open waits itself (the worker's adapter does, with the wait's own deadline rules); it checks the link and completes it.
- **Restart and repeat.** Everything is stored, so a new service on the same storage finds the question and takes the answer under the same correlation. The steps of an answer (record, chat entry, wait) each use a command ID derived from the inquiry; repeating the answer after a crash between steps finishes the missing ones and does nothing twice, **with the same command ID or any other**: the same responder repeating the same answer to an inquiry already answered by it is taken as the repeat (tested by making the chat step die once after the record step, then retrying under a new command ID: the wait is answered, the task is ready, the chat has the question and the answer once each). A different answer is refused.
- **Unauthorized context absent.** The question carries links, not copies. The asker may attach only what the asker can read, in the project; when an inquiry is viewed, each link is resolved as the viewer, so a link the viewer cannot read shows as `unavailable` with no text, and says nothing of whether it exists. Only the asker, the addressee and the owner can see an inquiry at all; anyone else gets what a missing inquiry gets.
- **Roles.** Only the addressee answers (the asker cannot answer its own question, nor can anyone else); only the asker closes (acknowledges); the asker or the owner withdraws an open inquiry. A late answer to a closed or cancelled inquiry is refused. At most ten open inquiries per asker per task, kept in a counter record updated in the same step under a revision check, so concurrent asks cannot exceed it (tested with three at once); answering or withdrawing frees a place. The count is also checked before the chat is made, so a refusal normally leaves no chat behind; in the rare race where two asks pass that check and one loses at the counter, its empty chat is left behind.
- **Limits.** Withdrawing an inquiry does not cancel a wait linked to it: the task's disposition is the caller's decision (S08's `cancelWait`). Nothing here starts the addressee's work or asks the admission service (H03) for an `inquiry` place: the dispatcher does that when it starts the addressee. There is no expiry of unanswered inquiries; a deadline comes from the wait when one is linked. Questions and answers are plain text up to 4,000 characters, refused if credential-shaped.

## A05 notes: exact-operation review admission

`packages/controller/src/review/` (`ReviewService`). It takes the authenticated `Principal`; it does not run anything and is not yet called by a tool path (the registry and adapter tool execution, T01/A04, must call `admit` immediately before running).

- **What a review is about.** One operation: the tool (`tool.<name>` is the action it needs), its arguments (a JSON object, at most 8 KB), its script text if it runs one (at most 16 KB), its target (`kind` and `id`), the requester and task, and the policy bearing on it. The request keeps the operation itself, so the reviewer sees exactly what is approved, and a binding of digests in parts: tool, arguments, script, target, and a digest of the grants and restrictions that bear on that action for the requester (their IDs, projects, resources and expiries). Arguments and scripts that look like they contain a credential are refused.
- **Who.** The requester needs `review.request` in the task's project and the right to work on the task (a task they may not work on reads like a missing task). The reviewer needs `review.decide` in the project, cannot be the requester, and **does not need the capability being reviewed**. The owner may review others' requests. The executor must be the requester.
- **Admission.** Immediately before the operation runs, `admit` recomputes the binding from the operation as it is about to run and from the requester's grants and restrictions **as stored now** (never a snapshot the caller holds), and compares every part. A changed tool, argument, script or target, a revoked or changed grant, or a new restriction makes it refuse with `review_invalid` and a message naming what changed. It also refuses an approval that has expired (default 30 minutes after the decision, at most 24 hours), been denied, withdrawn or already used. A refused attempt does not use the approval up.
- **An approval adds no capability.** The executor must itself hold the grant for the action on the target at admission (checked with the stored grants), or it is refused ("an approval does not give one"). The approval only waives the review. Because the digest includes the grants that bear on the action, any change to them, including a broader grant being added, invalidates an approval given before it: conservative on purpose, and the requester asks again.
- **One use.** A successful `admit` marks the review `used`, under a revision check, so of several executions at the same moment exactly one is admitted (tested with four), and the same call repeated (same command ID) replays instead of using it twice. The reviewer who approved, the requester or the owner can withdraw an approval before it is used.
- **Who must call `admit`.** The controller-side tool executor, with the exact operation it is about to run, immediately before running it, and never the agent: `admit` checks the operation it is handed, so if the agent could call it with the reviewed operation and the runner then ran whatever the agent asked, the binding would protect nothing (the principal it checks is the requester, but the call belongs to the trusted executor).
- **The target is bound by name, not by version.** The binding covers the target's kind and ID. If the target's content changes between approval and execution (a branch moves, a file is edited) the approval still admits; binding a target revision (a commit or content digest supplied by the executor) is not done here and should be added where the first tool that needs it is wired.
- **Two instants are not closed.** A grant revoked, or a restriction added, in the instant between `admit` reading the grants and committing is not seen by that admission (its revision check guards the review record only), so one admission can slip through at the moment of revocation. And a replayed `admit` (same command ID) reports "admitted" again, so an executor that crashes after running the operation and replays could run it twice; the effect ledger (S05) is what makes running it once safe.
- **Limits.** The digest is over the operation as described; whether the real process does what the description says (a script that fetches and runs other code) is for the sandbox (A03/A04). Reviewers are given no help in understanding a script. The policy digest ignores grants for other actions, so unrelated changes do not invalidate approvals, but a derived grant for the same action does. There is no queue, no notification to reviewers and no timeout on pending requests (later cards and the supervisors).

## U01 notes: the versioned state API and the controller start-up path

`packages/controller/src/api/` (`StateApi`, `operations.ts`, `start.ts`) and the generated contract `docs/nimblenewt/api-v1.md`.

- **One door.** `StateApi.handle(token, request)` authenticates the credential (A01), builds that principal's `SecureApi` and runs one of the version-1 operations (nine queries, eight commands: projects, tasks, assignments and their history, activity, search over desks and histories, the caller's pending inquiries). There is no other path to those operations, so a chat client and an API client holding the same credential get the same facts (tested by comparing results), and every fact is scoped by that principal's grants (a task in another project reads like a missing one; a search of a project the caller has no rights in finds nothing).
- **The contract** (generated from the operation table into `docs/nimblenewt/api-v1.md`; a test fails if the file is out of date): request `{ v, op, commandId?, args }` with the strict rules (version 1 only, unknown fields refused everywhere, a command needs a `commandId`, a query takes none, `actor` and `commandId` never go inside `args`); response `{ v, op, ok, result | error }`; writes idempotent by command ID (`replayed`, `command_conflict`), optimistic revisions (`stale_revision` with `currentRevision`), pagination (`limit` 1 to 100, `after`, `next`), errors with a code, message and field. Failures outside the contract are `unavailable` with no detail (the detail goes to a server-side hook).
- **Accepted differs from completed.** A command's response says `accepted: true` and `completed`. Recorded changes that are the whole effect (create or update a project or task, transition, release) are `completed: true`. `task.assign` and `task.transfer` are `completed: false` with `awaits` naming what must happen (the owner's worker admitting an attempt), and `assignment.get`, `assignment.history` and `activity.get` are where it is seen. Tested: assigning returns `completed: false`, the task is still `ready`, and a transition returns `completed: true`.
- **The start-up path** (`startController`, first built here, running the F04h check): detect the environment (or take injected facts), decide with `startupCheck` before anything is opened: an unsupported operating system or Node.js **refuses to start** (`UnsupportedEnvironmentError` with what was found, what is supported, how to test and the exact override) and creates no database; with `--allow-unsupported-environment` or `NIMBLENEWT_ALLOW_UNSUPPORTED_ENVIRONMENT=1` it prints the notice and goes on. For PostgreSQL the override is passed to the adapter (`allowUnsupportedServer`), an unsupported server is refused without it, and with it the server's problem is added to the notice; then `recordOverride` writes the audit record once per epoch (a restart is a new epoch and is printed and recorded again). A supported environment prints nothing and records nothing. Tested with injected facts for the operating system and with a real server against a faked higher floor for PostgreSQL.
- **Limits.** There is no network listener, no TLS and no sessions: this is the transport-agnostic core that the HTTP server and the chat front end call (the API package, still a placeholder, and the UI). Authentication costs one password-hash verification per request (deliberate; a session or token cache is a transport decision). The operation set is the state the controller has today; the services built in this batch that are not yet on it (hosts, admission, routing, grants, reviews, desk writes, inquiry ask/answer) are called by their own services until their API operations are added with the cards that need them. Nothing rate-limits a client and the core has no request-size limit: both belong to the transport (the HTTP card must take them on). `startController` itself prints a refusal (the full message with what was found, how to test and the override) before throwing, so the operator sees it whatever calls it. `task.release` reports `completed: true` because the record is the effect, while the previous owner's worker may keep running until its next fenced write is refused. Input the storage layer rejects as malformed is reported as `invalid_command`, not as a server fault. The start-up path builds the services but does not yet start the dispatcher, the reconciler or workers.

## H11 notes: agent, team and role records

- **Identity.** An agent has a computer-assigned ID (`agt-` and 20 characters, made from its creating command ID, so a retry names the same agent) and authenticates as `agent:<that ID>`. The friendly name is a label on the record: it may change and may repeat and never decides identity, ownership, authorization or routing. A rename therefore moves nothing: desk records, grants, the credential and history stay with the same identity. (Agents enrolled by hand under a chosen name, as in earlier cards' tests, still work; H11 agents are the ones the owner-facing commands create.)
- **Records.** `agent` (friendly name, roles, team, supervisor, default routing profile name, permitted overrides, environment name, persona, state, identity), `team` (name, parent team) and `role` (name, capability bundle, excluded roles). Created, changed and retired by revisioned commands, each audited; `null` clears an optional field; a retired agent cannot be changed.
- **Roles grant nothing.** A role names a bundle (`capabilitiesOf` shows the union for an agent) and exclusions. Nobody is granted anything by holding a role; granting stays a separate bounded act (A02), and the effective-policy view that joins the two is card A07. Exclusions are symmetric and enforced when roles are assigned and when a role is redefined (a redefinition that would put two excluded roles on one active agent is refused).
- **Organisation is not authority and not work.** Supervisor and team parent give no write to a child's desk and no read of its scratch (C01 decides that from the record's owner; a test gives the supervisor `*` and still gets refused), and no task dependency or assignment is touched when an agent is moved: the audit shows one change, to the agent record. Reporting cycles (also through several agents) and team cycles are refused; a retired supervisor is refused.
- **Managing.** The owner, or a holder of `agent.manage`, creates and changes records; `agent.read` (or manage) reads them; an agent reads only its own. A manager creates agents with no grants and no credential, so managing agents cannot widen anyone's authority. Someone who may not read an agent gets the answer a missing agent would get.
- **Retire, clone, import.** Retiring also disables the identity in the same step and is refused while active agents still report to the agent; the ID is never reused (the record stays). A clone copies roles, team, supervisor, profile and environment under a new ID and records `clonedFrom`. An import always gets a new ID, keeps the source ID only as `importedFrom`, and is refused as a collision if the source ID is one of this installation's agents or was imported before; identities are never merged.
- **API.** Four queries (`agent.get`, `agent.list`, `team.list`, `role.list`) and five commands (`agent.create`, `agent.update`, `agent.retire`, `team.create`, `role.define`) in the state API; `docs/nimblenewt/api-v1.md` regenerated. `team.update`, `agent.clone` and `agent.import` exist in the service but are not yet in the API table (the first chat and UI cards will decide whether they are wanted there).
- **One door for organisation changes.** Every command that changes agents, teams or roles also updates one small record (`org-registry`) at the revision it read first, and is tried again if another change got there first. This is what makes the checks that read many records true under concurrency (no reporting or team cycle, no conflicting roles after a role is redefined, no retirement under an agent that just gained a report); concurrent tests cover each. The price is that these commands are serialized, which suits changes made a few at a time. The safety checks that read every agent fail closed (`unavailable`) when there are more than 5000 (configurable), and a listing cut at that point returns where to continue.
- **Managers are powerful.** Any holder of `agent.manage` can change or retire any agent, including ones the owner created; the owner grants it deliberately and it widens no one's authority (agents are created with no grants). Retiring an agent leaves the tasks it owns assigned to its disabled identity: ownership is never released silently, so they need an explicit transfer.
- **Not done here.** The default execution profile and environment are stored as names; checking them against the routing table (R01) and the environments (A08) happens where they are used. Persona text is stored but nothing reads it yet.

## S10 notes: task contracts, the dependency graph and circular waits

- **Contracts.** A task's contract (expected result, acceptance criteria, priority 0 to 9 with higher served first, difficulty, budget, P or PC class, required evidence, the actions its work may use) is stored per task with a version. Every change stores a new `task-contract-version` record and keeps the old ones; `history` returns them. A task with no stored contract reads as the defaults at version 0 (priority 5, class P, nothing else), so tasks made before contracts keep working. The contract narrows, it never grants (the permission list is a ceiling for the task's work; stored now, enforced by the tool path in T06 and H12).
- **Authority per field.** `task.contract.write` for the general fields, `task.priority.write`, `task.difficulty.write` and `task.class.write` (the one that stands for planning authority) for those three; a grant can be narrowed to one task. A field set to the value it already has needs no authority for that field, and a change that changes nothing is refused. Each change is audited under the principal who made it.
- **Priority takes effect at the next decision.** `priorityOf(taskId)` reads the current contract; stored versions keep the priority they had. **Not done:** admission (H03) still takes a priority with each request and orders its queue by that stored value, so a queued request does not yet follow a later contract change; the dispatcher (H12) is where the two meet.
- **Dependencies.** An edge says a task depends on another task of the same project and names who answers for the prerequisite (default: its owner). Self-dependencies, duplicates, cross-project edges and cycles (also through several tasks) are refused. Every change to a project's dependencies updates one `dep-registry` record at the revision read first, so two edges added at the same moment cannot make a cycle (tested). Removing an edge keeps the record as `removed`.
- **Circular waits.** The wait-for graph is made of tasks. A task waits for each unfinished task it depends on; a task with an open inquiry waits for the unfinished tasks of the agent it asked (what that agent is busy with); reviews will add edges once a review has a designated reviewer. A ring of tasks (strongly connected, found with an iterative Tarjan) is a circular wait: one agent doing its own dependent tasks in order is not a ring, and neither are two agents whose dependencies cross but can each finish (both tested). `detect` opens one `circular_wait` blocker per ring, on a `wait-ring` subject named by a hash of the ring's tasks (so two rings never share a blocker and the same ring has one open one); its summary lists the tasks, agents and waits, and its resolver is the owner of the ring's lowest-numbered task, taken from assignments, never from anything a caller typed. Inquiry edges are deliberately conservative: an inquiry makes the asking task wait on all of the addressee's unfinished tasks, although answering is not itself held up by the addressee's dependencies, so a ring through an inquiry can be flagged where the addressee could still answer. A person looks at the blocker; tightening the rule (only the addressee's tasks that are themselves waiting) is left until real use shows the noise. A ring that is resolved and forms again gets a new blocker. Only open inquiries of the project count against the scan limit.
- **Carried by other cards.** Two S10 clauses are completed elsewhere and the plan says so: reviews in the wait-for graph (H05 supplies reviewer edges through the `extraEdges` hook, with a ring test) and priority taking effect at the next admission decision for queued requests (H12 reads `priorityOf` at each admission request). The contract's permission list is stored now and enforced by the tool path (T06, H12). Nothing calls `detect` on a schedule yet (health checks, card V01, will).
- **Responsible agent.** A dependency may name the agent answerable for its prerequisite; it must be an existing active agent. It is information for people: it is not used to decide who a blocker is for. A prerequisite the caller cannot read answers like a missing one, and the dependency lists show only edges whose other end the caller can read.
- **API.** `contract.get`, `contract.history`, `dependency.list` (queries) and `contract.set`, `dependency.add`, `dependency.remove`, `waits.detect` (commands); `api-v1.md` regenerated.

## F08 notes: harness capability declarations and per-task recovery requirements

- **Declaration.** A harness states what it can do about restarts and moves: continue a conversation from its own storage (`nativeContinuation`), have it rebuilt from exported records on another machine (`portableReconstruction`, which needs `checkpointExport`), and what an abort stops (nothing, a whole conversation, one request). The type is in the contracts package (`HarnessDeclaration`); the controller does not import the contracts, so it has its own copy of the structure and of the checks (`declarationProblems`, `durableSupport`, `recoveryGap`), and a test in the integration package, where both meet, runs the controller's checks on the declaration the Pi adapter ships.
- **Pi.** `PI_DECLARATION` is derived from the G02 lists, not typed beside them: native continuation because `restart-recovery` is supported; no portable reconstruction or checkpoint export because `portable-history-export` is unsupported; abort of a whole conversation because `cancel-single-request` is unsupported. If a capability moves between the lists, the declaration moves with it, and a test pins today's values.
- **Unsupported for durable tasks.** A harness that can neither continue a conversation nor have it rebuilt is unsupported for durable tasks (the rule reads "a harness without state export" as "without any way to recover"; Pi has no export but continues natively, so it is supported). A task that needs no recovery may still run there.
- **The requirement.** A task's contract carries `recovery` (`none`, `native-continuation` (the default) or `portable-reconstruction`), changed like any other contract field. `AssignmentService.admitAttempt` takes an optional `harness`; when named, the attempt is admitted only if the service's attempt gate accepts it, and a refusal is an `invalid_command` on the field `harness` whose message says which capability is missing. The installer builds the `HarnessCatalog` (the first release ships Pi only; another harness is the owner's decision) and wires the gate in `startController`. Naming a harness where no gate is configured is refused, never let through. With a gate configured every admission is checked: an attempt that names no harness is accepted only for a task whose requirement is `none`. (Without a gate, not naming one is the old unchecked call; H12's acceptance now says every admission names its harness.) Lowering a task's requirement needs planning authority (`task.class.write`), like the P or PC class, because it says losing the work is acceptable; raising it needs only contract authority. One gap: the gate reads the contract's requirement inside the admission without a revision check on the contract, so a requirement changed at the same moment can let one admission run under the old one.
- **Second harness.** There is no second harness. The shared contract is the declaration check; fake declarations (a rebuild-only harness, one with no recovery at all, a self-contradicting one) pass or fail it in the controller tests, and catalog tests admit and refuse attempts against them on all four backends. The suite in the plan's wording ("a fake second harness passes the same contract suite") is therefore met at the level of declarations, not of a running second runtime.
- **Not done.** A refusal is an error to the caller; it does not yet open a blocker or appear in a status view (U05). Routing (R01) does not yet choose a harness, so nothing picks one for a task today.

## A03 notes, part 1: sandbox launcher core and the Linux backend (2026-10-21)

A03 is **not** implemented yet. This part is the launcher and the bubblewrap backend in `packages/worker/src/sandbox/`; Seatbelt (macOS), Windows Sandbox, the Windows-specific items (package publisher check, per-job share ACLs, session-dependent capability, auto-login mode) and the quarantine of work under a lost path are still to do, and the card stays `planned` until they are.

- **Recipe** (`recipe.ts`): the owner's decision of 2026-10-21 made concrete. A recipe names the agent's host-side checkout, home and scratch (writable; `/work`, `/home/agent`, `/scratch`), read-only inputs (only under `/inputs` or `/opt`), network `none`, an explicit environment, and protected names under the checkout (default `.git`). Its revision is the SHA-256 of its normalised form, so any change gives a new revision and every launch names the one it ran with. A recipe is refused unless every host path is absolute, normalised, real (no symbolic-link component), existing, not a system directory, not the service user's home or an ancestor of it, not overlapping any protected path (the supervisor's own package, the controller's data, the user's credential directories such as `~/.ssh`), and not overlapping another mount. Trusted-host recipes get the same checks.
- **Bubblewrap backend** (`linux.ts`): every namespace unshared (no network, private process list and `/tmp`), environment cleared, new session, capabilities dropped, root and `/dev` remounted read-only, system directories read-only, the whole tree ends with the launcher. A protected name that exists in the checkout is bound read-only on top of it; one that does not exist cannot be, and is reported in the audit record as unprotected (the Git bridge, A04, owns that case).
- **Capacity** (`launcher.ts`): the launcher advertises capacity only after the backend has started a real confined probe (isolated network, the probe's own directory invisible). No backend, a failed probe or a throwing probe means no capacity and every launch is refused as `unavailable`; nothing ever falls back to running unconfined. `recheck()` re-runs the probe. macOS and Windows have no backend yet and say so.
- **Audit**: each launch is recorded before it starts (mode, backend, recipe revision, a digest of the command line instead of the line itself, the trusted-host authority); if the record cannot be written the launch does not happen.
- **Trusted-host mode** runs unconfined as the service user and needs an authority the owner configured; without it the launch is `not_authorized`. It still gets a cleared environment and the same recipe checks, and it is recorded as `trusted-host`.
- **Time and output**: every run has a timeout and an output bound; a timeout, `kill()` and `stop()` end the process group and, through the private process list, everything the agent started.
- **Evidence**: 29 tests in the worker package, 22 of them against real bubblewrap: writes to system directories, the root, `/dev` and host-only paths denied; the controller's data and the user's credentials invisible; symbolic links in the checkout cannot reach them; no network (a loopback server on the host is unreachable); host processes invisible; `/tmp` private per run; `.git` unchangeable; timeout and kill leave no survivors; truncation; audit and fail-closed cases. CI installs bubblewrap, lifts Ubuntu's user-namespace restriction for the job and sets `NIMBLENEWT_REQUIRE_SANDBOX=1`, so a Linux run where nothing could be confined fails instead of skipping; elsewhere those tests skip.
- **Review fixes (Opus, round 1)**: guest paths are checked as POSIX paths so Windows hosts work; nothing inside `/proc`, `/sys`, `/dev`, `/run`, `/boot`, `/root` or another user's home can be mounted; nested user namespaces are disabled (`--disable-userns`; a test fails without it); a protected name is re-checked right before the start and refused if it became a link; a trusted-host child that outlives its parent no longer holds the result open (2 s drain); the QA workflow installs bubblewrap and requires the sandbox tests like CI.
- **Limits stated**: the credential-directory list is a deny list (SSH, GPG, cloud CLIs, keyrings, browser profiles and a few more) and cannot be complete, so read-only host paths should still come from configured roots, which the recipe builder (H12/A08) owns; a protected name can still be swapped in the instant between the re-check and bubblewrap's own bind, or created when it did not exist, which the Git bridge (A04) must cover; two runs may share one checkout; a seccomp filter is not applied yet (a later hardening step); a trusted-host child that starts its own session is not killed with its parent; `/dev/shm` stays a private writable in-memory directory; CPU, memory, disk and process limits belong to A08 and are not enforced here; the sandbox shares the host kernel (the reason the plan keeps a VM backend possible); the CI user-namespace setting is confirmed only by the first CI run on a GitHub Ubuntu runner.

## H05 notes: review routing (2026-10-21)

H05 is implemented apart from the reviewer pause and hold behaviour, which needed the lifecycle (Pause, card L01) and is now card **H05b**; X02 depends on it. Everything is in `packages/controller/src/review/` (`review.ts`, `routing.ts`), with 72 new tests on four backends (`routing.test.ts`) and the 36 earlier review tests still passing.

- **Policy** (`review-policy`, one per project, versioned): independence `required` or `preferred`, designated reviewers, authorized fallbacks, a deadline in minutes (default 60, provisional), and tools reserved for the owner (`mandatoryHuman`). Setting it needs the new `review.policy.write` action; reviewers must be active agents.
- **Routing** (`review-route`, one per review, created with it): a request is routed at once. The reviewer is chosen from the designated list (or, when none is designated, from every active agent holding `review.decide` in the project), the least loaded first, never the requester, never a contributor (`preferred` independence lets a contributor review only when no one else is eligible), never one already tried; then the authorized fallbacks the same way. With nobody eligible the review **waits**; nothing is approved by waiting.
- **Who may decide**: the assigned reviewer or the owner for a pending review; only the owner for one reserved for the owner or sent to the owner; never the requester or a contributor.
- **Verdicts**: `allow`, `deny`, `request-context` (the review waits for the requester to supply it and returns to the same reviewer with a fresh deadline) and `requires-owner-decision`. `allow` is refused unless the essential context (tool version, authority source, expected effects) is present. The A05 verdict `approve` became `allow`; nothing outside the tests used it.
- **Context**: tool version, working directory, environment revision, affected resources, script hashes (the hash of the script under review is always included), expected effects, authority source, budget and a bounded text. Credentials in it are replaced and the record says so.
- **Contributors**: a principal who commits to the version under review records itself (the owner may name others). If it was the assigned reviewer, the review moves; if it had approved, the approval is withdrawn.
- **Escalation**: `sweep` (needs `review.policy.write`; a scheduler will call it, no timer is wired yet) gives a late review to the next eligible reviewer, then to the owner; it assigns waiting reviews when someone becomes eligible; it handles at most 50 reviews per call.
- **Clearing**: a repeat request for the identical operation (same requester, tool, arguments, script, target and policy digest) that an unexpired, unused approval covers is cleared against that approval and recorded in its route. An approval by an agent never clears a tool reserved for the owner. The card text said "matched to an existing grant"; there is no grant that waives a review yet (that is the policy card A07), so the match is against earlier approvals.
- **Figures**: queue delay, latency and cost per decided review, escalations, and false blocks and missed hazards recorded afterwards by someone with `review.policy.write`; `metrics` totals them.
- **Wait graph**: `waitEdges` supplies the S10 graph with an edge from the task under review to each unfinished task of the assigned reviewer; a test finds a ring through a review and shows it clears once the verdict is in. `extraEdges` now receives the project's task map.
- **The reservation is read now, not at request time**: when a tool is added to `mandatoryHuman`, an assigned agent can no longer decide a review of it, the next `sweep` hands the open review to the owner, and an agent's earlier approval no longer admits the tool (lifting the reservation lets it stand again). Other policy changes (who is designated) apply to requests made afterwards; an assigned reviewer dropped from the list can still decide the review already on them.
- **Limits stated**: contributors are self-reported (a reviewer who commits and stays quiet is not detected; automatic detection comes with the Git bridge and commit attribution, A06); the essential context is whatever the requester states, required before `allow` but not verified; a reviewer's load counts only the reviews in this project; a first policy created at the very moment of a request is not seen by that request.
- **Not yet**: no state-API operations for reviews (they come with the cards that expose approvals), no timer driving `sweep`, and nothing yet pauses a reviewer at a safe boundary or skips held reviewers (H05b).

## U02 notes: the durable conversation service (2026-10-21)

U02 is split like H05: this is the **service** (`packages/controller/src/conversations/`, 56 tests on four backends); the HTTPS transport with cursor long-polling, the opt-in remote listener and TLS are card **U02b** (T05 now depends on it). The service is not yet exposed through the state API or wired into `start()`; that comes with U02b.

- **Records** (all in the controller store, so no connection owns history): `thread` (participants, project, `nextSeq`, a run counter), `message` (named `<threadId>.<8-digit seq>`, so a thread's messages list in order), `conversation-delivery` (one per recipient: accepted → delivered → handled → answered), `conversation-cursor` (per reader and thread), `conversation-inbox` (per recipient: waiting count and which threads), `conversation-rate` (per sender).
- **Retries**: the message is named by thread and sequence number and the command by its ID, so a repeat returns the same message and a different payload under the same ID is `command_conflict`. Sends to one thread are ordered by the thread record's revision; two senders at the same moment retry (8 times) and get distinct, gapless numbers (tested with 16 simultaneous sends).
- **Reading**: `read` returns messages after a sequence number (default: after what the reader confirmed) and does not change anything; `acknowledge` moves the cursor forward only and marks the messages addressed to the reader as delivered (100 per call, says if more remain). A reader's own messages appear in the listing; its cursor skips them.
- **Who may do what**: `conversation.start` to open a thread in a project, `conversation.send` to send in one, `conversation.receive` to be addressable, `conversation.request-action` for an action request, `conversation.urgent` for an urgent message. A recipient the sender may not address reads the same as one that does not exist. The owner can always be addressed and can read every thread.
- **External clients**: a new principal kind `client`. A client can hold only single named `conversation.*` actions: enrolment, `setGrants` and `GrantService.grant` all refuse anything else (`*` and `conversation.*` included), so joining a thread gives it no tool, task or file capability. Every message records the authenticated sender (nothing in the content can change it) and, only for a client, an optional `claimedSender` kept beside it that grants nothing. A client cannot send notices.
- **Content** is untrusted: views carry `trust: "untrusted-content"`, credentials in the text are replaced and flagged, text is bounded (8000 characters), and an action request is stored with `needsAuthorization` and carried out by nothing here.
- **Limits** (provisional, adjustable): 20 recipients, 50 participants, 100 waiting messages per recipient (more is refused with a reason; confirming receipt makes room), 30 messages per sender per minute, reply chains 20 deep, 40 messages in a thread without the owner speaking (the owner speaking resets it).
- **Lifecycle**: the service takes an `availability` function (paused, suspended, stopped, available). A message to a recipient that is not available is accepted and kept, reported as `queued`; a sender that is not available cannot send; reading and confirming stay possible; nothing resumes anything. Until L01 and L02 exist the default is that everyone is available; L01 now carries the clause to supply it.
- **Who sees which message (decision for the owner, built provisionally)**: a participant reads the messages it sent and the ones addressed to it; a message sent to others only is not shown to it, nor is anything sent before it was added that was not for it. The owner reads everything. A send with no `to` goes to every participant, so group messages stay visible to all. Listed as an open owner decision in the G01 record; the alternative is a fully shared thread.
- **Accepted**: the thread view shows how many messages the thread has (`lastSeq`), so a participant can tell that messages exist that it cannot see; a reply to a message the sender cannot see is refused as if the message did not exist.
- **Revoking grants ends access**: reading, listing, confirming and sending need a `conversation.receive` or `send` grant in the thread's project, so taking a participant's grants away stops it at once.
- **Backpressure**: a send to several addressees fails if any one of them has a full queue (the refusal names the recipient); naming only the others still works. A client that never confirms receipt therefore blocks group sends to it until it does; this is deliberate, and the sender can address the rest.
- **Action requests** are stored with `needsAuthorization` and nothing here acts on them; evaluating them as requests under policy is carried by A07 (its acceptance now says so).
- **Limits stated**: queue and rate figures are checked when a message is accepted, so two senders racing for the last queue place both lose and retry; a reply marks only the replier's copy of the parent as answered; `markHandled` is the recipient's word, not a verified fact; no push channel exists yet (readers poll or, with U02b, long-poll).

## U10 notes: layered configuration (2026-10-21)

`packages/controller/src/configuration/` (`settings.ts`, `configuration.ts`), 44 tests on four backends (11 scenarios, including two checked by removing the rule they test and watching them fail).

- **Layers**: installation, team, agent, task, least specific first; one record per layer (`config-layer`). An agent's team comes from its record (H11); a task's layer applies on top of whatever agent works it.
- **Settings are defined in code** (`DEFAULT_SETTINGS`; the service takes more): each has a name (one segment may be `*`, as in `provider.*.enabled`), a checker, a default, a kind and the time its changes start to count. A `default` setting is simply overridden by the more specific layer. A `restriction` can only be narrowed (a switch can be turned off, never on again; a ceiling lowered; an allowed-list shrunk). The built-in ones: provider switches, `budget.paidAllowed` and `budget.maxCostPerTask`, time, CPU and memory ceilings, allowed and denied tools, the P/PC floor, ceiling and target, checkpoint interval, minimum resources, fallback profiles, and a visible `lifecycle.reloadPreservesPause`.
- **Locks**: a layer can lock a setting; the layers below cannot set it, and a value they had set earlier stops counting (the resolver says why).
- **Resolver** (`effective`): for an agent and/or task, every setting's value, the layer it comes from, who locked it, when a change starts to count (next request, after the current operation, after restart) and the lower-layer values that do not count with the reason. A restriction is re-judged on every read, so a task value that was fine when set stops counting if the installation is later tightened.
- **Draft and applied**: `stage` records changes without putting them in force (it checks names, values, locks and narrowing); `apply` puts the whole draft in force as one revision only if the combination fits (floor under ceiling, target between them, checkpoint shorter than the longest attempt, minimum resources under maximum, no tool both allowed and denied, no circular or missing fallback profile). A refused apply changes nothing in force, keeps the draft and records why. History keeps who, what and the timing of each applied change (40 entries). Revisions guard against two editors, and the layers above are checked in the same step.
- **Who**: the owner anywhere. `config.write` holders may stage and apply team, agent and task layers, never the installation layer and never a lock. `config.read` (or write) reads; an agent reads its own scope.
- **Routing**: `bindRouting` loads the document's routing section into the routing table after checking it against the configuration; `reorderProfile` changes one profile's order (same routes only). Both end in `RoutingService.setTable`, so a reorder asked for from the screen and from the coordinator agent give the same table and the same revision (tested in two separate installations). `RoutingService` now accepts the owner or a principal with `routing.write`, instead of the owner alone; nobody else.
- **Reload changes only configuration**: a test applies configuration and binds routing and checks that the task's assignment and the task are untouched. Pause is not built yet (L01) and neither are owner decision records (C08); each of those cards now carries the clause that applying or reloading configuration leaves it in place.
- **Denials only grow**: `permissions.deniedTools` is a restriction whose tighter value is the union, so no layer can remove a tool another layer denied. The P/PC floor, ceiling and target are planning shares, not authority, so a more specific layer simply overrides them (decided on purpose).
- **Tasks are judged with their agent**: a task layer is checked against the installation and, when an assignment names an agent, that agent's team and the agent; reading a task alone finds the agent now working it, and says `complete: false` when there is none (the team and agent layers could not be applied). A task staged before anyone works it is checked against the installation only and is checked again, in full, whenever it is read for an agent.
- **A repeated apply** is answered from the record that apply left (found by the revision it left the layer at; refused applies keep their reasons for the last ten).
- **Not yet**: no state-API operations or screens (U08 and U11 use this service), no secret references in this service (F02 handles them in the configuration package), and the settings of later cards are added by those cards.

## U02b notes: the conversation transport (2026-10-21)

`packages/controller/src/transport/` (`http.ts`, 32 tests on four backends with real sockets, including TLS with a certificate the test builds itself from `node:crypto`). The controller's start-up takes an optional `conversationTransport`; without it nothing listens.

- **Transport**: authenticated HTTPS requests with cursor-based long-polling (provisional choice, recorded in the G01 record); routes under `/v1`: start a thread, send, read after a cursor (with `wait` up to 25 s), acknowledge, mark handled, close, list threads, unread. Every change needs an `Idempotency-Key` header, which becomes the command ID, so a retry applies once and a changed retry is `command_conflict`.
- **Local by default**: it binds 127.0.0.1 unless told otherwise. Binding anywhere else needs `allowRemote`, and then it also needs TLS (certificate and key as PEM) and `publicHosts`, the host names clients use; any other host name in a request is refused (421), which defeats DNS rebinding. Starting the controller with a remote host and no opt-in fails and closes the storage.
- **Every request is checked afresh**: the bearer credential is authenticated against the store each time, so a disabled or revoked client is refused on its next request; hosts (workers) are refused; failures all read the same (401). Errors carry the service's code and message with credential-shaped text replaced, never the credential.
- **Bounds**: bodies 64 KiB (413), JSON only (415, 400), 600 requests a minute per principal and 120 a minute per address before authentication (429 with `Retry-After`), at most 4 long-polls per principal and 200 in all (503 with `Retry-After`), header size, request and header timeouts, no CORS headers, `Cache-Control: no-store`.
- **Dropped connections lose nothing**: the record is the conversation service, so a client that disconnects mid-wait reconnects with its cursor and gets each message once (tested); closing the listener ends waiting polls quickly.
- **Lifecycle**: the service's availability gate applies to API calls (a paused sender gets 503 with the reason); the lifecycle itself arrives with L01 and L02 through `startController`'s `availability` option.
- **Also**: at most 1000 open connections; internal faults (storage integrity, a lost epoch) answer with a generic message; the per-address limit uses the connection's own address and ignores `X-Forwarded-For`, so behind a reverse proxy all clients share the proxy's allowance; a listener on the default port for its scheme also answers to the port-less host name.
- **Limits stated**: rate windows are kept in memory (a restart forgets them); long-polls re-read every 250 ms rather than being pushed (200 open polls are about 800 reads a second; waking waiting polls when a message is accepted is a later improvement); no certificate management (the owner supplies the PEM files); the controller start-up now also builds and exposes the review, conversation, configuration and routing services, and the review edges feed the wait graph.

## A03 notes, part 2: the macOS backend (Seatbelt) (2026-10-21)

A03 is still **not** implemented: Windows Sandbox, the Windows-specific items and the quarantine remain. This part adds `packages/worker/src/sandbox/seatbelt.ts`.

- **Profile**: deny by default; process fork; exec only of programs in the system, the developer tools and the agent's own directories (and read-only inputs); read of the system (`/usr`, `/bin`, `/sbin`, `/System`, a few `/private` places the dynamic linker and locale need); read and write only in the agent's checkout, home and scratch; the recipe's read-only inputs read-only; the protected names read-only on top of the checkout; network denied. Paths are never written into the profile: they go in as `-D` parameters read with `(param ...)`, so a path (a directory named with quotes and parentheses is tested) cannot change the profile. Looking at a file's existence and size is allowed everywhere, so denied paths are visible but unreadable.
- **Guest view**: macOS has no private filesystem, so the agent sees host paths. `SandboxBackend.guestView` says where, and every `SandboxRun` carries it (`guest`); the agent's temporary directory is `<scratch>/.tmp`. The recipe's `/inputs` names are not mounted anywhere on macOS; the input is at its host path.
- **Process tree**: there is no private process list, so while a run goes the launcher asks the backend for the run's descendants (`ps`, every 250 ms) and remembers every one it sees; at a timeout, a kill, a stop and at the run's end it ends them, then the group and the child. Tests: a child that left the process group (`setsid`), and a detached child whose parent exits first (still ended when the run ends). Each remembered process is kept with its start time and is ended only if it is still the same process (the start time is looked up again in one call just before the kill), so a process id that was reused by an unrelated program is left alone (unit test with a stand-in backend; the test fails if the check is removed). Stated limits: a process that starts and is handed to launchd between two looks (under 250 ms) is not found; `ps` reports start times to the second, so a process id reused within the same second would still match (very unlikely).
- **Health**: the backend proves itself with a real confined probe (write in the checkout allowed; write and read outside denied). A machine without `sandbox-exec`, or one where the profile no longer works after a macOS update, has no capacity and the reason says so.
- **Not yet required in CI**: the macOS sandbox tests skip with the reason when the probe fails. This commit has never run on a Mac: the first CI run will show whether the profile works (the skip reason names why if not); the macOS cells are made to require the tests after that run is seen.
- **Review fixes (Opus, round 1)**: recipe variable names `DYLD_*`, `LD_*` and `LDR_*` are refused on every platform (an injected library would run inside the launcher before the profile applies); the agent's temporary directory is created only if it is not already something else (a link left in scratch is refused); the health probe also checks that a loopback connection that works unconfined is refused inside, and that exec and shared memory are limited; shared memory is limited to the notification centre's segment.
- **Limits stated**: `file-ioctl` and `sysctl-read` are allowed everywhere (the run has no controlling terminal); the weaker boundary of the decision record applies (process-level confinement, no resource limits, reported bypasses for hostile code); `file-read-metadata` everywhere; `mach-lookup` is limited to a short list of system services and may need widening for some tools, which is learned from real runs.

## A10 notes: private records and project boundaries (2026-10-21)

A10 is split like H05 and U02: the per-task credentials are card **A10b** (X02 depends on it). Everything else is in `packages/controller/src/context/` (`inspection.ts`, `publication.ts`, changes to `desks.ts`) with 60 tests on four backends (`inspection.test.ts`), five of which were also run with the rule they test removed to see them fail.

- **Owner inspection** (`InspectionService`): the installation owner is no longer exempt from the ordinary rule. A private record or a draft is not returned by the ordinary read, listing or search, whoever asks; the owner reads it with `inspect`, which follows the installation's inspection policy (`allowed` by default, as C01 built it; the owner can set `denied`), needs a reason (no credential-shaped text), and leaves an inspection record (who, which record, whose, why, under which policy, when) plus an audit entry before the record is returned. The agent whose record it was can list the looks at its own records; other agents see nothing of them. This is the provisional policy of the G01 record's open owner decision; the mechanism is what stays when the owner decides.
- **Recovery service**: a new principal kind `service`, created by the owner, that can hold only single named `recovery.*` actions (enrolment, `setGrants` and `GrantService.grant` all refuse anything else). `recoveryRead` reads unpublished records for restoring state, needs a `service` principal holding `recovery.read`, and leaves the same inspection record. An agent holding a token, even one granted `recovery.read` by name, is refused; the service cannot be addressed in a conversation, cannot start one, and its credential is refused by the conversation transport. The owner's inspection policy does not apply to it (restoring must keep working) but every read is recorded. Recovery records proper (checkpoints) arrive with C04, which now carries the clause that its recovery reads go through this path.
- **Publication paths** (`PublicationService`): the owner opens a one-way path from one project to another and can close it. A desk record may cite, and may be copied from, another project's record only along an open path; closing a path stops later citations and copies and takes back nothing already copied. A summary still needs every original in its own project (C02), whatever paths exist.
- **Copies and provenance**: `copy` puts a readable record on the copier's desk as a private draft (shared if asked) that cites the original and records the identity at the root of any chain of copies (`origin`). `independence` counts evidence by origin: an original and every copy of it are one source. Q02 now carries the clause that its evidence counting uses it.
- **Content from another desk never becomes executable**: `executableSource` (T01 and T06 call it first) returns a record's text only to its own author, only if it is accepted, and never if it is a copy; a record read from another desk, and copies of it, are data. Retyped text cannot be told from original work here; the review of a new tool is the control for that, and T01 carries the clause.
- **Review fixes (Opus, round 1)**: a copy is never more public than its source (a private record or a draft can be copied only into private scratch; a test publishes a copy of a supervisor-readable private record and finds it refused); an explicit `desk.scratch.read` grant is bound by the inspection policy like the owner is (policy `denied` stops those reads, listings, copies and citations too; the grant itself is the recorded decision that names who may read, and its individual reads are not written to the inspection log); a repeated look returns the record of the look and no content (reading again, or reading later content, is another look with its own command and its own record), and the content returned is the content read in the same step as the look and guarded by the record's revision.
- **Embeddings and indexes**: none exist yet; search reads live records with the reader's rights each time, so it inherits restrictions by construction. The clause that an index, embedding or compressed view keeps its source project and origin and is readable only by someone who can read every source is now on C07 (context compression) and K06 (retention and deletion of derived data).
- **Stated limits**: the owner still reads chats unaudited (C01; A10 covers desks and scratch); a path closed at the very moment of a copy or citation can still let that one through; the policy cannot take back a copy made while a grant worked.
- **Not here**: credentials per task (A10b).

### A03 part 2, after the first real macOS runs (2026-10-21)

- **What the Mac showed**: on a hosted macOS 26.6.2 machine the first profile killed every program at launch. A hand-started diagnostic (`sandbox-diagnose.yml`, `scripts/seatbelt-diagnose.mjs`) found the sandbox denying `file-read-data /` (the root directory entry itself); one literal rule fixed it (Apple's own `system.sb` baseline also worked but is far broader, so it is not imported). With it, the confinement checks pass on the Mac: writes outside the agent's directories and reads of the secret are denied, and the sandbox log shows outbound network attempts denied.
- **Found by CI on the Mac**: a process that outlives the run and holds the output pipes kept the launcher's own process from exiting (a hung Node 24 job); the launcher now closes its ends of the pipes when a run ends. The detached-child test was rebuilt so the shell stays alive long enough for the child to be seen (a child whose parent exits before the first 250 ms look is still the stated limit).
- **Required from now on**: the macOS cells of CI and QA set `NIMBLENEWT_REQUIRE_SANDBOX=1`, so a Mac run where the sandbox cannot work fails instead of skipping.
