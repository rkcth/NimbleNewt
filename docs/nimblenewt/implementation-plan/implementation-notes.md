# Implementation notes and known limitations

Running record of limitations found while implementing task cards. Each entry names the card that should resolve it.

- **Install scripts (resolved in F03):** `.npmrc` sets `ignore-scripts=true`; `@google/genai` (a no-op preinstall) and `protobufjs` (postinstall) never run their scripts and all tests pass. Enabling any install script needs a reviewed change; the license inventory marks affected packages.
- **Minimum Node (F03):** `engines` requires Node >=22.19.0 and `@types/node` is pinned to 22.x. CI runs 22.19.0 and 24.21.0 on Linux, macOS and Windows. 
- **Database isolation is convention (F01):** the boundary check restricts package dependencies and imports, but does not forbid built-ins such as `node:sqlite` inside `pi-adapter`.
- **Offline guarantee (F03):** `scripts/offline-guard.mjs` is preloaded into every package test process and blocks non-loopback `fetch`, sockets, DNS and UDP; Worker threads and Node child processes inherit it. It is a tripwire, not a sandbox: non-Node child processes and native code are not covered. The Linux CI job therefore reruns the suite inside a network namespace (`unshare --net`).  A Node child started with an explicit `env` that omits `NODE_OPTIONS` runs unguarded; when F05 adds tool tests, check how Pi Durable spawns tool processes (the Linux namespace rerun covers it there).
- **Test-only dependencies (before the first test-only package):** the boundary check requires every imported package to be a runtime dependency. F05 added none; fix it so test files may import `devDependencies` when one is first needed.

## F05 notes and limitations

- **Results are recorded once, durably.** The first time a request's result is built it is stored in an adapter-owned Pi document (`nimblenewt.requests`, committed with the transcript) keyed by request ID; every later call returns that record. Results are built from an ID-range scan of the conversation history, not the active view, because compaction removes older entries from the view but not from storage. An unanswered request owns the entries up to the next user input.
- **Request-ID reuse is detected from a payload fingerprint** (SHA-256) stored before admission, so it works while the original is still queued and after compaction. A crash between recording and admission leaves a record for the same payload, so a retry with that payload succeeds and one with different content is conservatively rejected.
- **Growth:** the document holds one record per request, including tool outputs, in a single conversation-scoped document. Revisit (size limits, pruning, per-request storage) before long-lived installations.
- **Commands:** the adapter supports no commands yet, so every command request is rejected with `UnknownCommandError`. F06 adds branch, checkpoint and abort commands. `abort()` and `compact()` are minimal whole-conversation placeholders; F06c replaces `abort()`.
- **Unknown-tool detection depends on a Pi Durable 1.3.0 diagnostic code** (`tool_unavailable`). The runtime pin makes this safe; G03/upgrade qualification must re-check it. The code is also produced for tools that exist but are not offered to the model, so `unknown_tool` means "unavailable". It marks the request `failed` after the fact; Pi lets the run continue and later tool calls still execute. If F06/G02 need the run stopped, end it from the adapter's tool layer.
- **Tool errors are normal feedback:** a throwing tool yields an `error` outcome on a `completed` request.
- **Tool API:** tools receive `{ signal, callId }` and may declare `replay: "safe"` (default: interrupted calls are not re-run). F06's restoration tests must cover both.
- **Command `args`** are in the contract but unused until F06d.

## F06 split

F06 (checkpoints and cancellation mapping) has several independently verifiable units, so it is delivered as four pieces, each separately reviewed and committed. F06 is complete when all four pass; G02 follows.

- **F06a:** conversation handles, `whenBusy`, restart and fresh-process restoration, F05 review follow-ups.
- **F06b:** inquiry branch that leaves the parent context unchanged; selective update applied exactly once.
- **F06c:** cancellation, delivered as **F06c1** (abort mapping: abort during streaming and partial tool arguments, incomplete tool calls never execute, queued input survives cancellation and is readmitted only by the controller) and **F06c2**, itself delivered as **F06c2a** (the interrupted-work hold, plus the readmission follow-ups) **F06c2b** (the context decisions: update versus resume and the aborted-instruction behaviour) and **F06c2c** (branch lifecycle/retention).
- **F06d:** checkpoints and the typed controller boundary (retained commands require later controller readmission), delivered as **F06d1** (checkpoints: create, verify, restore) and **F06d2** (the controller-facing interface, audit events and one reviewed recovery step).

## F06a notes

- **API shape:** `PiAdapter.root()` and `PiAdapter.conversation(id)` return an `AdapterConversation` with `submit`, `recorded`, `lookup`, `abort` and `compact`. `submit`, `abort` and `compact` moved off `PiAdapter`. `recorded(requestId)` reads a stored result without waiting.
- **Busy policy:** `whenBusy` (`followUp` default, `steer`, `reject`) is part of a request's identity (fingerprint `v1:sha256:`, covering content and busy policy; extend it, and bump the version, when branch or entry options are added). `reject` on a busy conversation throws `ConversationBusyError`; the request was not admitted and the ID stays reusable.
- **Reopening storage does not run interrupted work, but almost any progress call does.** Pi's scheduler is harness-wide: besides `resume()`, `submit`, `abort`, `compact`, `Submission.wait` (so `result()`), `waitForTask` and `waitForIdle` on any conversation start it, which resumes every interrupted run in every conversation. `lookup(requestId)` is the read-only alternative: it returns a settled request's result (recording it the first time) or `undefined`, never waits, and never starts the scheduler. A controller recovering after a crash must use `lookup()` until it has decided what to do with interrupted work.
- **F06c acceptance item (hold):** provide a real hold. For example, list interrupted runs at open (Pi's `harness.inspect()` is read-only) and refuse progress calls until the controller chooses resume or abandon for each one. Decide the scope of `abort()` and `compact()` (hold versus resume) together with this.
- **Attribution rule:** a request owns the tool calls after its input and before the next input in the transcript, so a steered input starts a new segment and each call is counted once (the steered-in request owns calls after the steer). Requests merged into one run share the final answer text.
- **Crash semantics verified with a real SIGKILL** (Pi JSONL storage, child process): an interrupted tool declared unsafe is not re-run and the model is told it was interrupted; a `replay: "safe"` tool runs again. External effects remain at-least-once for safe tools; exactly-once is not claimed.
- **Fingerprint on old records:** a record without a fingerprint, or with another version prefix, matches any payload (implemented in F06b as `fingerprintsMatch`). Records written by the F05 commit (24019e5) hold an unprefixed SHA-256 and would conflict with `v1:` fingerprints; no data has been deployed. The rule going forward: compare only fingerprints with the same version prefix, and treat unknown formats as legacy.
- **No storage lock:** Pi's JSONL storage does not stop two processes opening one directory (for example a hung process plus its replacement). Worker ownership and leases (H cards, F06d) must provide fencing.
- **Branch requests (F06b):** inquiry-branch creation must be idempotent by request ID, and branch options belong in the fingerprint.
- **Open from the F05 review (non-blocking):** the single results document grows by about 6 KB per request in Opus's measurement (linear); move to per-request documents (`defineDocFamily`) and decide on bounded stored outputs before G02 long-run tests. `settings` exposes Pi's own settings type from the adapter package; consider narrowing it. G02 repeats the kill test on macOS and Windows; this piece's kill test runs on whichever OS CI uses (Windows detects death by non-zero status, not by signal).

## F06b notes

- **Inquiry branch:** `conversation.branch({ requestId, at? })` forks a child conversation (Pi `fork`, ownerless) from a completed-turn boundary. The child sees the parent's history up to that entry, shares nothing afterwards, and the parent's transcript is left exactly unchanged (tests compare full transcripts before and after, and check what each side's next model step sees). Branch creation is idempotent by request ID: the fork and its record are written in one commit (Pi runs the fork's `init` in the creating commit), so concurrent calls return the same branch and a crash cannot leave an unrecorded orphan. Naming a different `at` for an existing request ID is a conflict.
- **Fork point:** the latest completed-turn boundary (a final assistant answer, the last tool result of a fully answered tool round, or a compaction summary), resolved at first creation and then fixed. A turn still in progress is not part of the branch, so a "how is it going?" inquiry on a busy task sees the task as of its last completed turn, not its in-flight work. Forking inside a turn would leave a tool call without its result. If product needs the in-flight state, F06c decides between finish-and-hold and a parallel inquiry. `NoBranchPointError` when there is no completed turn; `InvalidBranchPointError` for an explicit `at` that is not a boundary.
- **Selective update:** `submit({ kind: "update", requestId, content, source? })` places the text in the parent as its own `nimblenewt.update` entry (provenance in the entry data), applied once per request ID (same dedupe, fingerprint and result machinery as inputs; the fingerprint covers kind, content, busy policy and source). Applying it starts a run, like any input. An update is a normal input to the model; there is no "silent" context edit.
- **Attribution:** input segments start at `pi.user` and `nimblenewt.update` entries.
- **`transcript()`:** read-only full history of a conversation (including compacted-out entries and inherited parent entries), for inspection and tests.
- **Bug found while testing:** a conversation with no adapter document yet made `recorded()`, `lookup()` and branch lookup crash on `undefined`; fixed and covered.
- **Not covered (F06c/F06d):** abort of an inquiry branch, queued input surviving cancellation, discarding or retaining a side conversation as policy, branch retention limits, and the controller-facing boundary.
- **Compaction and branches:** a compaction entry is a boundary, so the default branch of a compacted task gets the compacted context (summary plus recent entries), not the history the task no longer has. An explicit `at` before the latest compaction is allowed and gives the older, uncompacted history; that is deliberate (historical inquiries) and costs the full prefill and window of that history.
- **Retrying a branch request without `at`** returns the original fork point even if the task has since moved on; request a new branch (new request ID) for the current context.
- **Namespaces:** branch request IDs are stored apart from input/update request IDs, so one ID can be both without conflict. Controllers should still use distinct IDs per operation.
- **Decision for F06c/F06d (update vs resume):** `kind: "update"` currently fuses "apply the update" with "resume the task": it is an input, so it starts a run when the parent is idle. That clashes with the F06c hold and with "retained commands require later controller readmission". Decide between `applyAndRun` (today) and a place-only variant that adds the update to the transcript without asking the model anything (Pi's `write` submission with a model-visible entry, applied at the next boundary like a steer), so a controller can apply an update and resume later. Also decide on fixed framing of the update text for the model (for example "Update from inquiry <id>: ..."), since provenance lives only in entry data the model does not see.
- **F06c/F06d acceptance item (branch lifecycle):** `AdapterBranch` has no discard, close or retention operation, and ownerless branches survive parent aborts. Define discard/retain policy, a bound on accumulated branches per task, and how aborting a task treats its inquiry branches. Each fork also forks the adapter document.
- **Perf:** `branch()` scans the parent's whole history to find boundaries; it could stop at the newest compaction.
- **Compaction while an input is pending:** Pi also compacts while preparing a generation, so a summary can land after a still-unanswered input. That compaction is not a fork boundary (the branch would inherit the task's pending instruction); the default fork point is then the last answered turn, before the compaction, and the branch pays for the uncompacted prefix of that turn. A controller that wants the compacted context for an inquiry must wait for the turn to settle (finish-and-hold, F06c).

## F06c1 notes

- **`abort()` returns an `AbortReport`** `{ aborted, retained }`: requests that had started (stopped mid-run) and queued requests withdrawn before starting. Pi's `abort` withdraws queued inputs; the adapter keeps each request's payload (in the request record, until its result is recorded, or for good while it is retained) and marks the withdrawn ones `retained: true` on their `unanswered/aborted` result. Nothing of a retained request ran.
- **Retained requests never run by themselves.** `retainedRequests()` (read-only, survives restart) lists them in admission order with payloads; `readmit(id, newId)` submits one again under a new request ID, an explicit controller decision. Idempotent for the same new ID, refused (`AlreadyReadmittedError`) for another, and refused (`NotRetainedError`) for requests that had started or are unknown. A readmitted update stays an update, with its provenance. This is the "retained commands require later controller readmission" behaviour; F06d wires it to the controller's inbox.
- **Partial tool calls:** verified against Pi 1.3.0 with a slow faux stream: aborting while a tool call's arguments are still streaming leaves the request `unanswered/aborted`, the tool is never executed, and Pi omits the aborted assistant message from the next model request. The transcript keeps the partial assistant entry (stopReason `aborted`) with no tool result; it is not a fork boundary, so `branch()` right after such an abort throws `NoBranchPointError`.
- **Scope:** aborting a conversation does not abort its inquiry branches and vice versa (ownerless forks), tested. Whether aborting a task should also abort its branches is F06c2.
- **Payload growth:** payloads of retained requests accumulate until the retention policy (F06c2/F06d) prunes them; a readmitted request's payload is kept so readmission stays idempotent.
- **abort() starts Pi's harness-wide scheduler** (a progress call), so on a freshly reopened storage it resumes interrupted runs everywhere. The hold (F06c2) must gate it.
- **Readmission is claim-first.** `readmit` records the new ID in one commit (exactly one new ID can win, concurrently or across a crash) and then submits; the same new ID is idempotent. After a crash between the two steps the request no longer lists as retained, so the controller must repeat the call with the same new ID (F06d should surface "claimed but not yet admitted").
- **Known behaviour, F06c2 decision:** the input of a request that had *started* and was then aborted stays in the model's context on later runs (Pi drops only the aborted assistant message). Nothing re-runs it, but the model can see it and may act on it; only never-started requests are retained and need readmission. Options for F06c2: hide the entry with Pi's context-only edits, add fixed framing ("aborted by the user; do not continue unless asked"), or make it an explicit controller choice. A test pins today's behaviour so a change is deliberate.
- **Abort report caveats:** the report is the difference between aborted submissions before and after the call, so (a) two concurrent `abort()` calls can report the same IDs, (b) requests aborted by anything else in the window (for example Pi closing) are attributed to the call, and (c) the scans cost O(every aborted submission ever). An adapter-side record of aborts, or a cursor watermark, would fix (c).
- **Payload retention:** a request's payload is dropped only when a non-retained result is recorded, so requests nobody ever reads keep theirs. Fold into the retention policy (F06c2/F06d). The report covers only the conversation `abort()` was called on, and readmission links old to new only through `readmittedAs`; F06d will want the reverse link and original admission order.

## F06c2a notes

- **The hold.** Pi's scheduler is harness-wide and almost any progress call starts it, which re-runs every interrupted run. So on open the adapter inspects the storage (`harness.inspect()`, read-only); if any task or unsettled submission exists it holds (option `holdInterrupted`, default true). While held, `submit`, `abort`, `compact`, `readmit` and waiting on an unsettled result throw `InterruptedWorkError`; reads (`lookup`, `recorded`, `transcript`, `retainedRequests`, `branch`, `interrupted`) work and start nothing. A settled result is read from its record, not by waiting.
- **Controller flow:** `interrupted()` lists per conversation the live tasks, unsettled request IDs and whether it is abandoned; `abandonInterrupted([conversationId...])` marks every live task of those conversations for abandonment (Pi `abortTask` only marks; verified it neither runs anything nor starts the scheduler) and withdraws their queued submissions (which then stay available through `retainedRequests()` and `readmit()`); `releaseHold()` ends the hold and starts the scheduler, so everything not abandoned resumes (replay-safe tools re-run; others are reported to the model as interrupted). The abort handlers of abandoned work run at release, and their requests settle `unanswered/aborted`. `resume()` is replaced by `releaseHold()`. Without a hold, opening still runs nothing: the next progress call resumes everything, as before.
- **Granularity limit:** Pi cannot resume one conversation and keep another stopped. The only per-conversation choice is abandon; everything else resumes together at release.
- **Verified with real crashes** (child process SIGKILL, two conversations interrupted, one with a queued request behind it): nothing runs while held; abandoning the root leaves the branch's work untouched; after release only the branch's replay-safe tool re-runs and its request completes; the abandoned request settles `unanswered/aborted`; the queued request never reaches the model and is retained.
- **Readmission follow-ups (from the F06c1 review):** `readmit(id, id)` throws `InvalidReadmissionError`; a typed refusal at submit (new ID taken by a different payload, busy, held) gives the claim back so another new ID can be tried; other errors keep the claim (unknown outcome, retry with the same new ID).
- **Still open:** the hold is in-memory per adapter instance (a second process opening the same storage has its own); real ownership/fencing across processes belongs to the worker/lease cards. `abandonInterrupted` is not atomic across conversations (a crash midway leaves some marked; marking is idempotent, so repeat it).

## F06c2b notes: context decisions (defaults chosen here; owner may override)

- **Aborted instructions are framed by default.** Pi keeps the input of a request that started and was aborted in later model context as if it were live. The adapter now replaces it, *for the model only* (a Pi context edit), with the same text prefixed "[This request was aborted before it finished. Do not continue it unless asked again.]", once per request, and appends a `nimblenewt.aborted-input` entry; the transcript keeps the original. `PiAdapterOptions.abortedInputs: "keep"` restores the old behaviour. Rationale: after an abort the controller, not the model, decides whether to continue; a bare aborted instruction invites the model to resume it. Alternative considered: omit the input entirely (loses the fact that it was asked). Framing happens when the abort is observed: in `abort()`, when a result is read, and in `abandonInterrupted()` before release, so no run can start between the abort and the framing in the paths the adapter controls. A run that is already generating when the abort lands has already read its context.
- **Updates keep running by default, with a place-only form.** `submit({ kind: "update", ... })` still applies the update and resumes the task (an input). `run: false` places it as a Pi passive write with model messages: it is added to the transcript at the next turn boundary and the model is asked nothing, so a controller can apply an update and resume later (the shape F06d's readmission model needs). Its result is `{ status: "placed", entryId }`. `run` is part of the request's identity. A placed update is part of the task's context: it is a fork boundary (a branch taken after it sees it), it does not leave an input pending, and it does not cut a running request's tool calls out of its segment. The update text is still shown to the model as a plain user message; fixed framing of its provenance ("Update from inquiry <id>: ...") is not added yet, because the provenance lives only in entry data the model does not see; decide with F06d.
- **Hold notes from the F06c2a review:** a lone queued submission (including items left queued after a failed run, "queued items stay in the inbox until the next input") engages the hold on open, so controllers may see a hold after a model error with no crash; `abandonInterrupted` throws `NotHeldError` once the hold is released (afterwards it would be a late abort); abandonment marks tasks by conversation ID and does not yet follow ownership into conversations owned by tasks (a tool that spawns a subagent): not reachable through today's adapter, mark owned conversations transitively when tools gain that ability.
- **Still for F06c2c/F06d:** branch lifecycle (discard/retention/bounds), and presenting `interrupted()` -> decide -> `abandonInterrupted` -> `releaseHold` as one reviewed step with an audit trail.
- **Branches inherit the framing.** The `nimblenewt.aborted-input` entry only carries a context edit, so like a placed update it extends the preceding boundary: a branch taken right after an abort forks after the edit and sees the aborted instruction framed, as the task does (tested).
- **Submit waits for an abort in progress** (per conversation, within one adapter instance): `abort()` frames after Pi's abort resolves, and a `submit()` in that window would start a run that reads the input unframed, so submissions wait for the abort and its framing to finish (tested; the test fails without the wait). Handles from other adapter instances on the same storage are not coordinated.
- **Queued place-only updates are not withdrawn by `abandonInterrupted`.** They ask the model nothing. With no run left to reach a turn boundary, Pi keeps them queued until the next input places them; they are neither lost nor run behind the controller's back. (Conversation `abort()` also leaves queued writes alone: Pi: "queued writes stay".) A place-only update queued behind a running request is placed at that run's next boundary, so it joins that run's context mid-run, like a steer without a reply; controllers wanting it to wait for "between tasks" must submit it when idle.
- **Framing from `settle()`** (an abort the adapter did not start, first observed while another run is mid-turn) appends the edit directly in a commit instead of waiting for a boundary; it worked in every probe but Pi does not document that interleaving. `abort()` and `abandonInterrupted()` frame while the conversation is idle or held.
- **Growth:** the `framed` flag and `nimblenewt.aborted-input` entries add to the single results document's growth (see F05 notes).

## F06c2c notes: branch lifecycle

- **Policy:** branches are kept for review (nothing is deleted), but are bounded and closable. `listBranches()` lists a conversation's branches in creation order (request ID, conversation ID, fork point, discarded). `discardBranch(requestId)` marks the branch discarded in one commit (the parent's record and the branch's own document), then aborts whatever it is running (returning its `AbortReport`); after that the branch refuses `submit`, `compact`, `readmit` and nested `branch` with `BranchDiscardedError`, while its transcript, `lookup`, `recorded` and `abort` keep working. Idempotent; an unknown request ID is `InvalidBranchPointError`; refused while interrupted work is held (aborting would start the scheduler). Discard survives restart.
- **Bound:** `maxActiveBranches` (default 8) active (not discarded) branches per conversation; creating another throws `TooManyBranchesError`. The count is taken inside the fork's creating commit, so concurrent creators cannot exceed it (tested with six at once against a limit of two). Asking again for an existing request ID (even a discarded one, returned with `discarded: true`) is never refused.
- **Aborting a task does not touch its branches** and discarding a branch does not touch the task; to stop a task's inquiries the controller lists them and discards or aborts each (no cascade flag yet).
- **Not done:** deleting or archiving branch storage (each branch is a full conversation plus its adapter document, which grows with the single-document design noted under F05), automatic expiry, and per-branch budgets. Revisit with F06d's controller policies.
- **Discard vs submissions in flight (found in review, reproduced with a slow store):** a `submit()` that had passed the "is this branch discarded?" check could be admitted after the discard's abort finished and then run. Three layers now close it: (1) `discardBranch` marks, then waits for submissions in progress on that conversation (tracked per adapter instance), then aborts; (2) after Pi admits a submission the adapter re-reads the branch's document and, if it was discarded meanwhile, withdraws the submission and throws `BranchDiscardedError` (covers other adapter instances); (3) the claim commit refuses once the branch is marked. The test holds a submission between its claim and its hand-over to Pi through an internal test seam (`beforeAdmission`) and asserts no tool runs after the discard returns; it fails with all layers removed, and either (1) or (2) alone is enough. Pi's own `abort` already waits for a submission that is currently being admitted, which is why a merely slow store did not reproduce it; the window is before the call reaches Pi.
- **Discard cascades down the tree:** discarding a branch also discards its own branches (their work is aborted, nested reports merged). Discarding is not undoable.
- **Discarded work never resumes after a crash:** discard is mark-then-abort; a crash between the two used to leave a discarded branch with live tasks. `interrupted()` now reports `discarded` per conversation, and `releaseHold()` (now async) abandons the interrupted work of discarded conversations before starting the scheduler. Tested by marking a branch discarded in an interrupted storage and releasing.
- **For F06d:** checkpoints must say whether discarded branches are included; `discard`, like `abandonInterrupted`, should be a reviewed, audited controller action.

## F06d1 notes: checkpoints

- **What a checkpoint is:** a small JSON record `{ format: 1, conversationId, at, digest, runtimeVersion, contractsVersion }` taken after a completed-turn boundary (default the latest, with exactly the boundary rules of `branch()`, so a turn in progress or a pending input is never part of it). It holds no conversation content. The `digest` (`v1:sha256:`) covers every history entry up to and including `at`: id, kind, model messages, data, head marker and context edits, in id order with canonical JSON; not the writing task or conversation, so a fork's inherited prefix digests like its source.
- **`verifyCheckpoint` (conversation or adapter) is read-only and allowed while interrupted work is held.** It rejects with a typed reason: `unsupported_format`, `incompatible_runtime` (any other Pi Durable version or contracts version: there is no forward migration yet, so an upgrade invalidates old checkpoints explicitly; this is the compatibility rejection G03 builds on), `unknown_conversation`, `unknown_entry`, `not_a_boundary`, `history_changed`. Later turns and compaction do not invalidate a checkpoint, since the prefix is unchanged and compaction keeps older entries in storage. A store restored from a different or damaged backup with the same ids is caught by the digest (tested with a look-alike store).
- **`restoreCheckpoint(checkpoint, requestId)`** verifies, then branches the checkpointed conversation at `at` (`CheckpointRejectedError` otherwise; nothing is created on rejection). The result is a new conversation whose context is the task as it was, idempotent by request ID, subject to the branch limit and the usual branch rules. It does not roll the original back; the controller decides which conversation continues.
- **Limits, stated plainly:** a checkpoint is a reference, not an export. Restoring needs the same storage (or a faithful copy of it); there is no portable history export/import for a replacement worker with an empty store, which the worker/lease cards and G02's cross-worker recovery must add, probably as an artifact manifest of the history. The digest detects accidental change and mismatched backups, not an adversary who can rewrite both the history and the checkpoint (there is no signature). Workspace state (files, uncommitted changes) is outside this record: per the design, immutable artifact manifests own workspace checkpoints and the controller references both. The adapter's own request records are not part of the digest (results are re-derivable from the history).

## F06d2 notes: controller boundary, audit and recovery

- **Typed boundary (`@nimblenewt/contracts`):** `RuntimePort` and `ConversationPort` list everything a controller may do, using only contract types (no Pi types), so a controller does not depend on Pi Durable and another runtime could implement them. `PiAdapter implements RuntimePort` and `AdapterConversation implements ConversationPort`, checked by the compiler, and a test drives a task, a branch, a checkpoint and a restore through the port type alone. Controllers should depend on the ports, not on the adapter classes (`AdapterConversation` is exported as a type only). Deliberately off the port: `abandonInterrupted` / `releaseHold` (replaced by `recover`), and the test seams (`testHooks.beforeAdmission`, `markBranchDiscardedForTests`, `@internal` helpers).
- **Audit trail:** `PiAdapterOptions.audit` receives an `AuditEvent` after each controller-reviewed action has taken effect: `abort`, `readmit`, `discard_branch` (one event for the whole cascade, not one per nested abort), `restore_checkpoint`, `recover`. Ordinary submissions are not audited. The sink is awaited; if it throws, the error reaches the caller although the action has already happened, so a controller that must not lose records should make its sink durable and retrying. Events are emitted by the adapter instance that performed the action; audit across adapter instances or processes belongs to the controller.
- **`recover(decision)` is the one reviewed recovery step:** `{ abandon, reason, decidedBy }`. It refuses (`NotHeldError`, `InvalidRecoveryError`) unless interrupted work is held, a reason and a decider are given and every listed conversation actually has interrupted work, and a refused decision changes nothing. It then abandons the listed conversations (discarded branches are abandoned automatically), releases the hold, and emits one `recover` event carrying the decision and exactly what `interrupted()` showed. `abandonInterrupted` / `releaseHold` remain on the adapter class for low-level use. `releaseHold()` must be awaited.
- **Checkpoint compatibility (from the F06d1 review):** validity now depends on `format`, the digest algorithm and the runtime version, not on `contractsVersion`, which is informational; an unknown digest prefix is `unsupported_format`. G03 will need a runtime storage/history format identifier plus a migration table rather than an exact npm version; until then any other Pi Durable version is `incompatible_runtime`. Restoring a checkpoint taken before a later compaction brings back the full uncompacted history up to `at` (same window and prefill cost as an explicit `at` before a compaction, see F06b).
- **Restores and inquiries are limited separately:** `BranchInfo.kind` is `inquiry` or `restore`; `maxActiveBranches` applies to each kind on its own, so a burst of one cannot starve the other. Restoring from a discarded branch throws `BranchDiscardedError`, not `CheckpointRejectedError`.
- **For the controller (S09):** keep a checkpoint together with the workspace artifact manifest it belongs to as one controller-owned recovery point (`{ checkpoint, artifactManifest, requestIds }`); the adapter only knows the conversation half. Bridge the controller's inbox to `ConversationPort.submit` with the controller's own operation ID as the request ID; readmission is the only way a withdrawn command runs again.

## F06e notes: independent tasks, and gaps carried to G02/S09

- **`createTask({ requestId })`** (on `PiAdapter` and `RuntimePort`) starts a task with an empty context, separate from every other task and the root (the "task A/B context separation" G02 requires; before this the port could only fork from an existing context). It is a child record of the root conversation, built on the same machinery as branches: the conversation and its record are created in one commit, idempotent by request ID (also under concurrent callers: exactly one caller gets `created: true`), limited separately (`maxActiveTasks`, default 16; inquiries, restores and tasks each have their own count), listed by `listBranches()` with `kind: "task"` and `forkedAt: 0`, closed with `discardBranch(requestId)` (abort, close to new work, cascade), durable across restart, and audited (`create_task`, once per creation). One request ID cannot be a task and a branch or restore (`RequestIdConflictError` both ways). Tasks are ownerless: aborting the root or another task does not touch them. Creating a task starts nothing, so it is allowed while interrupted work is held. Each task starts on the adapter's configured model.
- **Equivalent mutant:** the early "already created" check in `createTask` is an optimisation; the atomic registration in the creating commit also returns the existing task, so removing the early check changes no behaviour.
- **Recovery after a crash in the middle of `recover()`** (probed by the F06d2 reviewer on the real-kill fixture): `abandonInterrupted` marks are durable, so if the process dies after abandoning and before releasing, the reopened adapter is held again with those conversations showing `abandoned: true`; a second `recover()` completes the job (the abandoned work is not re-run; the rest resumes). Consequences: an abandonment cannot be undone by a later decision, and the first decision's audit event is lost because `recover` emits only after releasing (the second event shows `abandon: []` with `abandoned: true` in its `found`, which is how the earlier decision surfaces). If that record matters, add a `recover_started` intent event; not done yet.
- **Audit semantics to know:** events are at-least-once (a retried `readmit` with the same new ID emits again; concurrent aborts can overlap in their reports); `at` is a wall-clock hint, so the controller's audit log should assign its own sequence; direct `abandonInterrupted` / `releaseHold` are not audited (they are off the port; use `recover`). Branch creation is not audited yet.
- **Gaps in the controller port (G02 or S09):** (1) waiting for a result after losing the handle needs `submit` of the same payload again or polling `lookup`; add `wait(requestId)` (storage lookup by request ID plus `submission.wait`, refused while held); (2) cancelling a single request (Pi `abortSubmission` for a queued one); (3) transcript paging (`from`, `limit`) before long runs; (4) a progress/event stream for the UI cards; (5) treat `submissionId` and conversation IDs as opaque in the port docs. `BranchPort` lacks `kind` (it is on `BranchInfo`).
- **`compact` is on the port (G02):** the design requires compaction to be explicit, and the milestone needs to compact through the controller-facing surface. It is not an audited action.

## F02 notes: versioned configuration and secret references

New package `@nimblenewt/config` (no runtime dependencies; boundary-checked). What it does and does not do:

- **Schema-versioned configuration** (`configVersion` 1). `loadConfig` takes JSON text or a value, upgrades an older layout with `migrateConfig`, applies documented defaults (D6 limits 4/2/2, strong isolation, remote exposure off, tight approval preset, no grants), then validates. Every problem is returned with its dotted path, all at once; unknown settings get a "did you mean" suggestion; JSON syntax errors give line and column. A layout newer than the build, a missing or invalid version, or a missing migration step is refused with a reason. Nothing is written anywhere.
- **Migrations** are pure steps `from -> from + 1` applied in order to a copy; a failing step leaves the original untouched. There are no production migrations yet (the current layout is the first); the chain is tested with a synthetic registry, labelled so. A real layout change adds a step with a fixture of the old layout.
- **Secrets are never in configuration.** A setting that needs one holds `{ "secret": "name" }`; a plain string there is refused. Anything shaped like a credential (API keys, GitHub/Slack tokens, AWS keys, private keys, URLs with a password) anywhere in a document is refused by path, and the error never repeats the value. Resolvers (`environmentSecrets`, `directorySecrets`, `memorySecrets`) turn names into values on demand; `resolveSecrets` reports every missing name with where it is used (and skips disabled providers); a resolved `Secret` prints, serializes and inspects as `[redacted]` and is revealed only by an explicit `reveal()`. Secret names can never be paths.
- **Public profiles exclude private things:** a `public` profile may not hold private grants, an enabled paid provider, trusted-host execution or remote exposure; trusted-host mode needs a named authorizer and reason; a `private` profile may not carry unfilled `{{placeholders}}`. Cross-setting checks: routes name real providers and listed models, no duplicate routes, an enabled provider is reachable, `perHost` cannot exceed the installation total.
- **Sanitized export/import:** `exportProfile` produces a public profile with private grants, host paths and database locations removed or replaced by `{{placeholders}}`, paid providers switched off, trusted-host and remote exposure reset, secret references kept by name, and a preview of what was kept, omitted and left to map. `importProfile` fills placeholders from a mapping and names any missing or unused mapping entry. Export never contains a secret value, transcript or deployment history (the configuration never holds them).

- **Windows:** example paths in the tests use both POSIX and Windows styles; the directory secret resolver was tested only with POSIX-style temp directories on Linux here, and runs on all CI platforms.
- **Hardening after review:** JSON syntax errors come from our own scanner (line, column and a generic reason), never the engine's message, which quotes input. Secret detection "by shape" is a safety net for well-known token formats and for key names, not a guarantee; the protection is that secret-bearing settings accept only `{ "secret": "name" }`. ## F04a notes: the transactional controller storage contract

Lives in `packages/controller/src/storage/`. It defines what domain services may ask of storage and what every adapter must do, and provides the reference implementation and the shared conformance suite. **It does not touch a real database yet**: SQLite is F04b, PostgreSQL F04c, and the contract has so far been exercised only against `MemoryStorage`, which is the oracle the adapters are compared with. Whether the suite is strong enough for real concurrency, crashes and disconnections is what F04b-F04d must show; the suite's concurrency tests are meaningful on a real database, trivially satisfied by single-threaded memory.

- **One write primitive.** `applyOperation` takes everything a command changes (aggregate creates/updates/checks, audit entries, outbox messages, effect intentions, timers, timer cancellations) and commits it as one transaction or not at all, including the operation record itself. Checks run in a fixed order: input validity, existing operation (same hash replays, different hash is `idempotency_conflict`), epoch, revisions, then ID uniqueness. A repeat of an already committed operation is answered even after the epoch has moved on.
- **Identity.** `operationHash` covers actor, correlation, changes, audit, outbox, effects, timers and cancellations, and deliberately excludes the operation ID, epoch and issue time. Key order does not matter (canonical JSON).
- **Fencing.** The primary epoch starts at 0 (no owner; nothing is admitted), rises by 1 per `acquireEpoch`, and supports compare-and-set takeover. **Every write method takes the caller's epoch** (`applyOperation`, `claimDeliveries`, `retryDelivery`, `claimDueTimers`) and refuses a stale one with nothing written, so a deposed controller cannot claim, retry, complete or settle after a takeover; lease tokens only fence claimant against claimant. The one exception is a repeat of an operation that already committed, which is answered from the record. Aggregates use per-record revisions; `check` changes guard without writing. Lease expiry uses a caller-supplied `now`, so clock skew can at worst redeliver a message (receivers deduplicate by `deliveryId`); correctness against an old controller rests on the epoch, not the clock.
- **Reconciliation is part of the one write primitive.** Receipts (`completeDeliveries`), timer firings (`completeTimers`) and effect settlements (`settleEffects`) are fields of `OperationInput`, committed in the same transaction as the domain transition, audit and outbox entries of the handler, under the same operation ID, epoch check and idempotency. There is no separate "complete" call, so a crash cannot leave a receipt recorded and the task not moved; rerunning the handler with the same operation ID replays. Every effect settlement writes an automatic `effect.settled` audit record. A timer cancelled while claimed makes its holder's completion fail with `state_conflict` (cancellation wins; treat as superseded). A delivery already delivered with the same receipt is a no-op for any token.
- **Delivery.** Claims are leases with opaque tokens (the memory store's tokens are guessable: they fence honest mistakes, they are not a security boundary). Ordering within `(destination, orderingKey)` is strict commit order even across retries and priorities; unkeyed messages are independent. A late completion by the current token holder is accepted if nobody took over; completion by anyone else is `state_conflict`; a repeated completion with the same receipt is a no-op.
- **Ambiguous commits.** `commitOperation` is the only way domain code should submit an operation: it reruns `retryable` failures within a bounded budget and resolves `uncertain_commit` by asking `getOperation` for the stable ID, resubmitting only if the operation is absent. Only `applyOperation` can be uncertain; claims and completions are safe to repeat because leases expire and receipts are idempotent. `FaultInjectingStorage` scripts these failures for any adapter.
- **Rules for adapters (stated in `types.ts`).** Sequence numbers (audit `seq`, delivery `seq`) come from a counter row updated inside the operation's transaction, never a database sequence, because sequences allocate in statement order and leave gaps, which would let a later message of an ordering key become claimable before an earlier one commits; the throughput cost of serialising on that row is for F04d to measure. Bodies are stored as text or `json`, never `jsonb`. IDs and kinds compare in binary order (`COLLATE "C"`). A race on a unique key is mapped to `retryable` (operation ID, so the retry replays) or `duplicate_id` (delivery, effect, timer), never a raw driver error. The conformance suite includes raw concurrent submissions and racing IDs, which are only truly exercised on a real database; F04d must add a test where two operations commit in the opposite order to which they started and the delivery order must still follow commit order.
- **Representation.** IDs are ASCII (`ID_PATTERN`), timestamps are `YYYY-MM-DDTHH:mm:ss.sssZ` strings, integers are safe integers, bodies are canonical JSON text with the rules in `types.ts` (no undefined, NaN, -0, unsafe integers, cycles; depth 32; 256 KiB), absent optional fields are omitted (never `null`), reads return copies, listings sort by code point. Limits keep transactions short: at most 100 entries of each kind per operation.
- **No raw SQL in domain code.** `scripts/package-boundaries.mjs` now fails the build if SQL statements or database drivers (`node:sqlite`, `pg`, ORMs, and so on) appear anywhere except `controller/src/storage/sqlite/` and `controller/src/storage/postgres/`. This is a tripwire (upper-case SQL statement forms anywhere, the same forms in any case inside string and template literals, and a list of known drivers; prose in comments is not flagged, but a string that merely contains words like "select ... from" is, an accepted false positive), not proof; a domain service could still obtain a handle some other way, which the typed contract exists to prevent.
- **Not in the contract yet (later cards):** the domain aggregates' own schemas (F03/F05 and the domain cards), schema migration journals (F04), durability settings and busy handling (F04b), connection pooling and serialization retry (F04c), measured throughput and contention (F04d), backup and logical export (K01). **Query extension point:** `listAggregates(kind)` is the only query. S01/S02 will need to list by relation or state (tasks of a project, active assignments of a host); the planned extension is an `index` map of declared, typed fields on `create`/`update`, backed by an index in each adapter, added with the first domain card that needs it. Record kinds from the design's minimum-records table are stored as generic aggregates; their body schemas are not defined here.

## F04b notes: the SQLite controller storage adapter

`packages/controller/src/storage/sqlite/` (the only place besides `postgres/` allowed to hold SQL). Uses Node's built-in `node:sqlite` (no dependency; stability "active development", which prints an ExperimentalWarning on the supported Node versions). It passes the whole shared conformance suite (101 cases on this backend) plus SQLite-specific tests.

- **Explicit settings, read back and verified at open:** WAL journal mode (open fails if SQLite answers anything else, which also catches file systems that cannot do WAL), `synchronous = FULL` (the log is flushed before each commit returns: an acknowledged operation survives power loss, not just a process crash), foreign keys on, `trusted_schema` off, `journal_size_limit` 64 MiB (the WAL shrinks back after a spike; auto-checkpoint stays at SQLite's default), and a bounded busy timeout (default 5 s, at most 60 s). `settings()` reports them. These are per connection and re-applied on every open. Pi's own SQLite default (`synchronous = NORMAL`) is unaffected.
- **Write admission and short transactions.** Every write is one `BEGIN IMMEDIATE ... COMMIT`; a second writer waits at most the busy timeout and then fails as `retryable`, rolled back. Transactions contain only database work. Each method completes without yielding, so calls on one connection never interleave; contention comes from other connections and processes. Claims use one indexed query inside the write transaction; ordering uses a `NOT EXISTS` over open earlier messages of the same key, which is equivalent to the reference store's "head of the key" rule.
- **Sequence numbers** (audit, delivery) come from counter columns in the single `state` row updated in the same transaction, per the contract; no `AUTOINCREMENT`. Cost: every audited or outbox-writing operation serialises on that row (F04d measures it).
- **Failure classification.** Busy or locked is `retryable`. A constraint violation is `unavailable`, reported as an invariant violation with the extended result code: every write holds the database's only write lock (`BEGIN IMMEDIATE`) before it reads, so no one can have raced it to a unique key, and a violation means an adapter bug, schema drift or another program writing the file; it fails fast instead of being retried. (The contract's "operation-ID race is `retryable`" rule is for PostgreSQL under READ COMMITTED.) A failed `COMMIT` is `retryable` if it was only contention, otherwise `uncertain_commit` for `applyOperation` (resolve by operation ID) and `retryable` for claims. Other database errors are `unavailable`. No driver error escapes.
- **No network file systems.** `open` refuses `\\server\share` paths on every platform and `//server/share` on Windows only (on POSIX `//var/lib` is an ordinary path), and on Linux checks the directory's file system magic number and the mount table for NFS/SMB/CIFS/AFS/Ceph/9p/Lustre/GPFS/FUSE network mounts. The mount table is parsed with all octal escapes decoded. **This is best effort:** it cannot see a mapped network drive on Windows or a network mount on macOS, and a FUSE mount that hides its backing store looks local. The WAL check above is a second, independent net. The operator remains responsible; the PostgreSQL backend is the answer for shared storage.
- **Schema** layout 1 is created on first open and recorded in `PRAGMA user_version`; a newer version, an unknown database or a missing migration refuses to open without touching the file. The journalled migration runner (interruptible, downgrade-refusing) is card F04. Uniqueness of operation, delivery, effect, timer IDs and delivery sequence numbers, state values and revision/priority ranges are enforced by the schema as well as the code (tested against a raw connection).
- **Verified here:** the conformance suite; several OS processes racing to bump one counter (no lost update, gap-free audit and delivery numbers, one winner per revision); processes competing to claim deliveries (no duplicates, ordering chain respected); a writer SIGKILLed at six arbitrary points (never a partial operation, every acknowledged operation present, at most one in-flight operation extra, database accepts work and resolves the in-flight operation by ID); a process killed while holding the write lock releases it; a blocked writer fails as `retryable` within the bound and the database is unchanged. **Not verified:** power loss (it needs hardware or a VM; `synchronous = FULL` is the documented basis), Windows and macOS runs (they run in CI), a real network file system (only the refusal logic, with its limits), or throughput (F04d).

## F04c notes: the PostgreSQL controller storage adapter

`packages/controller/src/storage/postgres/` (SQL and the `pg` driver are allowed only here and in `sqlite/`). Runtime dependency: `pg` 8.23.1 (MIT, exact pin) with its small transitive set; test-only dependency: `embedded-postgres` 17.10.0-beta.17 (MIT; ships real PostgreSQL 17.10 binaries for Linux, macOS and Windows; the "beta" is the package's build tag, not the server's maturity). `@types/pg` for types. It passes the whole shared conformance suite (101 cases on this backend) plus PostgreSQL-specific tests against a **real server**, not a mock.

- **Concurrency model.** Writers run in parallel under READ COMMITTED; there is no global write lock. Correctness comes from row-level rules: the operation row is inserted first with `ON CONFLICT DO NOTHING`, so two submissions of one ID serialise on the key and the loser sees the winner's committed result (replay) or conflict; revisions are checked by conditional `UPDATE ... WHERE revision = expected`, creates by `INSERT ... ON CONFLICT DO NOTHING`, guards by `SELECT ... FOR SHARE`; delivery, effect and timer IDs by `ON CONFLICT DO NOTHING`. The primary-epoch row is read `FOR SHARE` by every writer and claimer, so a takeover (an `UPDATE`) waits for in-flight writers and everything after it sees the new epoch (tested: a takeover really does wait for a writer that already passed the fence, which completes under the epoch it held). Audit and delivery sequence numbers come from one counter row updated late in the transaction and held to commit, so they follow commit order with no gaps (tested under 60 concurrent operations); the cost is that every audit- or outbox-writing operation serialises briefly on that row (F04d measures it). Locks are taken in one fixed order (operation, epoch, aggregates by key, delivery rows, timer rows with completions and cancellations locked together, effect rows, new effects and timers by ID, the counter row, audit and new deliveries by ID), so the adapter's own transactions do not deadlock one another (tested: aggregates touched in opposite order, timers completed and cancelled crosswise, the same effect IDs or the same timer IDs inserted in opposite orders; delivery inserts happen under the counter-row lock, which already serialises them; any deadlock would show as a `retryable` outcome after the server's 1 s `deadlock_timeout`). PostgreSQL still detects a deadlock that arises from an outside session, and it is classified `retryable` (tested with a real server-detected deadlock). Sustained high-priority load can starve low-priority messages; that is inherent to the contract's rule and F04d should measure it. Serialization failures cannot occur at READ COMMITTED; they are classified `retryable` anyway. When an operation has several things wrong, the error reported is the first in the contract's order (changes, receipts, timer completions, settlements, duplicate delivery, effect, timer IDs; each in argument order), the same as the reference store and SQLite: PostgreSQL collects refusals while it takes locks in its own order and reports the first by that ranking (found by the parity test).
- **Claims** use `FOR UPDATE SKIP LOCKED` only to skip rows another claimant holds. The per-ordering-key rule is a `NOT EXISTS` over earlier undelivered messages of the same destination and key, evaluated on the claimant's snapshot: it can only hold a later message back, never let it overtake, and a concurrently claimed or completed head cannot make a successor claimable early. Tested with 12 concurrent claimants on a 10-connection pool: no delivery claimed twice, the chain yields only its head, every free delivery claimed.
- **Bounded pool, bounded waits, explicit settings.** At most `maxConnections` (default 10, at most 200) connections; waiting longer than `connectTimeoutMs` for one is `retryable` (tested). Every session runs with `lock_timeout` (default 5 s, tested), `statement_timeout`, `idle_in_transaction_session_timeout`, `synchronous_commit = on`, `READ COMMITTED` and the controller's own schema on `search_path`. At open the adapter reads back and verifies `fsync = on`, `full_page_writes = on`, `synchronous_commit = on` and the isolation level, and refuses a server that fails (tested against a second embedded server started with `fsync=off`). Minimum server version 14 is a code floor, not a support statement: **only PostgreSQL 17.10 has been qualified, and which versions are supported is an open owner decision.**
- **Failure classification** (driver errors never escape): deadlock, lock timeout, statement timeout, too many connections, pool wait and connection loss before COMMIT are `retryable` (the transaction never committed); connection loss **during** COMMIT is `uncertain_commit` for the operation primitive (resolved by operation ID) and `retryable` for claims; an unreachable server, bad credentials, missing database, disk full and any constraint violation (an invariant the adapter checks itself) are `unavailable`. Ambiguity is tested deterministically with a TCP proxy that cuts the connection at an exact statement: after the server processed COMMIT but before the answer (the operation is found committed and replayed, admitted once), before the server saw COMMIT (nothing committed; resubmitted), and in the middle of a transaction (rolled back, retryable, pool recovers).
- **Schema** layout 1 lives in a dedicated schema (default `nimblenewt`, validated name), created under an advisory lock so concurrent first opens are safe; every text column uses the binary `"C"` collation, bodies are `text` (not `json`/`jsonb`), uniqueness and state rules are database constraints (tested through a raw connection). A newer or older version, or a schema containing foreign tables, refuses to open without changing anything. `schema_info` is where the F04 migration runner takes over. The connection string contains the password and must come from the secret store (`controller.storage.url` in the configuration is a secret reference).
- **Test servers.** `testing/server.ts` starts a real server on a free loopback port in a temp directory, or uses `NIMBLENEWT_TEST_POSTGRES_URL` (a database where the tests may create and drop schemas; each test uses its own schema). The repository installs with lifecycle scripts disabled, so the helper recreates the embedded binaries' shared-library symlinks itself from the package's own list. The offline guard permits loopback, so these tests run inside it and inside the Linux network-namespace rerun.
- **Connections.** Session settings travel as startup options, so connections must be direct or go through a pooler that forwards startup options (PgBouncer in transaction mode does not). TLS is whatever the connection string's `sslmode` asks for and is untested. The database user needs CREATE on the database to create the schema; a permission failure says so.
- **Not verified:** PostgreSQL 14-16 and 18, TLS and remote servers, power loss and replica failover, a server restart mid-run (only connection cuts through the proxy), throughput and contention (F04d), and the Windows/macOS runs until CI reports.

## F04 notes: schema migration runners

Both backends now create and change their schema only through journaled migrations (`storage/migrations.ts` holds the shared rules and the pure planner; `sqlite/schema.ts` and `postgres/schema.ts` hold each backend's migrations in its own SQL; each adapter has its own runner and its own journal table, `schema_migrations`). This replaces the single-layout creation of F04b/F04c (`PRAGMA user_version`, `schema_info`).

- **Rules.** Migrations are numbered 1, 2, 3 without gaps and are never edited once applied: the journal records each one's name and a SHA-256 checksum of its content, and a database whose recorded checksum differs from this build's is refused. A database whose journal holds a migration this build does not know (written by a newer NimbleNewt) is refused untouched: there are no downgrades. A journal with a gap, or with a "running" entry that is not the last, is refused. A database that has tables but no journal was not created by NimbleNewt and is refused untouched (this also means a database created by the development builds before this card is not adopted; none was ever deployed). All refusals say "Nothing was changed" and are `unavailable`.
- **Transactional migrations** (the default) run their statements and write their journal entry in one transaction, so an interruption leaves the database exactly as it was and the next start runs the migration again. **Non-transactional migrations** (`transactional: false`, for things that cannot run in a transaction, such as PostgreSQL's `CREATE INDEX CONCURRENTLY`) are journaled as `running` (committed) before their statements, must consist of idempotent statements, are marked `done` afterwards, and are finished by the next start if found `running`.
- **SQLite runner.** Each migration step is a `BEGIN IMMEDIATE` transaction (write admission, as everywhere in the adapter). Two processes opening at once are serialised by that lock for transactional migrations; for non-transactional ones a second process may re-run the idempotent statements, which is allowed by the rule above.
- **PostgreSQL runner.** One connection holds a session-level advisory lock for the whole phase, acquired by polling `pg_try_advisory_lock` (never a blocking lock call: a session blocked in a statement holds a snapshot, and `CREATE INDEX CONCURRENTLY` waits for every such snapshot, which deadlocked two openers until this was found by the concurrency test). The lock vanishes with the connection if the process dies. The phase is exempt from the session `statement_timeout` (restored afterwards); DDL still honours `lock_timeout`, so a migration blocked behind a long transaction fails as `retryable` and the next start retries. The schema is created only if absent, so an account without CREATE on the database can use an existing empty schema.
- **What is verified (production list has one migration, so later layouts are synthetic and labelled as such):** an upgrade of a populated database through synthetic migrations 2 (transactional: adds a column, backfills it, adds an index, creates and fills a probe table with a non-idempotent insert) and 3 (non-transactional, idempotent; `CREATE INDEX CONCURRENTLY` on PostgreSQL) preserves everything the storage reports, each migration's statements run exactly once, and the adapter keeps working on the new layout (the entire shared conformance suite is also run on an upgraded database on both backends); a crash before and after every statement of that upgrade (SQLite 26 statements/52 points; PostgreSQL 34/68) leaves a journal that is a prefix of the migrations, never half a transactional migration, never a non-transactional one changed without a journal trace or marked done before it finished, and recovery reaches the state of an uninterrupted upgrade; a newer database, an edited migration and a journal gap are refused and leave the schema, the journal and the data unchanged (compared by reading the structure, the journal and the probe rows back, and the storage's own view of the data; not a byte comparison, which would not even mean anything on PostgreSQL); a non-transactional migration found `running` is finished by the next start, and one whose recorded content differs is refused; two processes (SQLite) or two connections (PostgreSQL) opening at once end with every journal entry `done` exactly once and the transactional migration's non-idempotent statements run exactly once (three rounds); for the non-transactional migration the test shows only that a repeat is harmless, which is all the rules promise on SQLite (a second process may re-run its idempotent statements; PostgreSQL's lock prevents even that); constraints that enforce unique operation, delivery, effect and timer IDs and delivery sequence numbers are tested directly against both schemas (F04b/F04c tests, unchanged). Committed layout-1 fixtures (`packages/controller/test-fixtures/`: a real SQLite file, a PostgreSQL JSON of DDL and rows, and the snapshot both must report) must open with every later build and upgrade without loss; regenerate only by `node dist/storage/qualification/fixtures.js` and only for deliberate pre-release changes to layout 1.
- **Operational rules.** Stop old controllers before starting a new version that will migrate: an old process started against a database a newer one has migrated is refused as "newer" (no downgrades), so old and new controllers cannot overlap across a migration (to be carried into the upgrade procedure of K02). On PostgreSQL a migration phase is exempt from `statement_timeout`, and `lock_timeout` does not bound `CREATE INDEX CONCURRENTLY` waiting for older transactions, so such a migration can wait as long as a long-running transaction exists; the polling lock gives up after 15 minutes of waiting for another process, not for the migration's own statements. If setting the statement timeout fails right after the lock is taken, the lock is released before the error propagates; that defensive path is not directly exercised by a test (it needs a server that refuses a harmless SET without dropping the connection).
- **Not done:** a backup before an upgrade (K01; the journal's `started_at`/`finished_at` are wall-clock times that K01 should record in the backup manifest); a naming convention for migration names (settle before the first real layout 2); long data migrations in batches with progress; moving data between SQLite and PostgreSQL (the separate logical export/import of K-cards); a real second layout (none is needed yet); running the PostgreSQL migration on a server other than 17.10 or through a pooler that does not support session advisory locks (PgBouncer in transaction mode does not).

## F07 notes: protected registry of tools and extensions

New dependency-free package `@nimblenewt/registry` (`packages/registry`). It is the controller-side facade that decides who may register which tool or extension name, which artifact versions exist, and which version a paused attempt gets back. It is not yet wired into `PiAdapter.open({ tools })` or any worker: that happens when attempts are launched (S02) and the catalog is built (T01, A05). Until then the adapter still accepts any tool list; this card provides and tests the rules those cards must use.

- **Names.** `<namespace>.<name>` in lower-case ASCII only. Namespaces: `nimblenewt` (protected, registered by the trusted controller), `toolbox` (shared) and `a_<id>` (one agent, 6-32 lower-case letters or digits assigned by the controller). Input that is not exactly in the grammar is rejected, never normalised, so look-alike spellings (upper case, full-width, Cyrillic, zero-width, trailing newline) cannot become a second name. Names are at most 28 characters.
- **Wire names.** `<namespace>__<name>`: nothing is replaced or dropped, names contain no underscore and a namespace at most one, so the first `__` is the only separator and two canonical names cannot merge. Even the longest valid name is exactly 64 characters, the usual provider limit; a decoder returns null for any spelling the scheme does not produce.
- **Three capabilities** from `createRegistry()`: `trusted` (allocate and retire agent ids, publish anywhere, seal the protected namespace, revoke, take a snapshot), `forAgent(id)` (publish only under that agent's own `a_<id>.`; reserved and other agents' names are refused with `reserved_namespace` or `foreign_namespace`), and `read` (resolve, list, pin, restore, verify the reserved set). Each is a frozen object of closures, with no `this` and nothing that leads to another capability. This is a facade against mistakes and unauthorised registration, not an isolation boundary: code in the same process could still tamper with the process, so execution is still authorised by NimbleNewt services (as the runtime-compatibility record requires).
- **Immutability.** There is no last-installed-wins: a (name, version) is immutable (the same content published again is a harmless no-op, different content is `version_exists`), versions must increase, `sealProtected()` stops any new `nimblenewt.` name, retired agent ids and their prefixes are never allocated again, and revocation is permanent (a fix is a new version).
- **Version selection and pins.** `resolve` gives the highest version that is not revoked, or exactly the one asked for. `pin(names)` records name, version and SHA-256 content digest in a pin set that carries its own digest. `restore(pinSet)` returns the same versions even after newer ones appear, and returns `blocked` with reasons (`revoked`, `missing`, `digest_mismatch`, or `invalid_pin_set` for a malformed or inconsistent set) instead of ever substituting another version. The pin-set digest is a plain SHA-256 checksum, not a signature: it catches accidental edits, but whoever can write a stored pin set can recompute it and select another registered, non-revoked version (never other content). The store that holds pin sets must therefore be writable by the controller only. Revoking the latest version makes the previous live version the default for anything that resolves afresh; an attempt that pinned the revoked version is blocked instead.
- **Integrity of the reserved set.** `verifyReserved(expectedDigests)` reports missing, changed, extra and revoked protected tools; the caller stops activation on any problem.
- **History.** `trusted.snapshot()` is the ordered list of operations; `createRegistry(history)` replays it through the same rules, so a stored history cannot say what a call could not (an agent tool without an allocation, a protected tool after the seal, a changed version, an unknown operation all throw). Storing the history durably belongs to a later card.
- **Verified by:** `registry.test.ts` (15 tests), plus mutation checks run while writing it: removing the foreign-namespace refusal, the reserved-namespace refusal, the pinned-digest check, the revoked-on-restore check, the pin-set tamper check, the seal, version monotonicity or the retired-agent check each makes at least one test fail.
- **Not done:** a durable store for the history and pins (a later storage card), per-attempt pinning in the controller, enforcement inside the worker and the adapter, execution-time authorisation, the shared-toolbox permission check (`toolbox.manage`), and aliases such as `/agent.command` (resolution to a canonical name is the caller's job; the registry only accepts canonical names).
- **Carry forward (not enforced by this card):** S02 (attempt admission) must store a pin set per attempt and call `restore` on resume; T01 (tool/skill catalog) and A05 must register through `forAgent`/`trusted` and call `verifyReserved` before accepting a customized environment; the worker must expose to the adapter only tools whose wire names `fromWire` resolves. Those cards' acceptance should be checked against this list.
