# G10: llama.cpp and vLLM, measured on a rented GPU (2026-11-25)

What this is: the same kind of measurement the Radiance runs made (a shared head read again in other conversations, after idle gaps, after other conversations may have pushed it out, and with several at once), run against two open engines.
The raw figures are in `g10-vllm-run1.json`, `g10-llamacpp-run1.json` and `g10-llamacpp-run2.json` (usage, timing and counter fields only). The code is `packages/integration/src/g10-engines-live.ts`; the run command is in `g10-engines-live-bench.ts`.

**One run per engine configuration, no repeats**: every figure below is a single observation (llama.cpp ran twice, but with different settings and on different pods; run 2 ran only the extras, concurrency and ladder parts). **These are not comparable with the Radiance numbers as such.** Radiance ran `qwen3.8-flash-next-iq4r` (a hybrid model) on the owner's hardware; these runs used Qwen3-8B (a plain transformer) on one rented RTX 3090. Where a quantity corresponds it is named; no equivalence is claimed.

## What was measured

Reuse is "tokens from cache / prompt tokens". "Reused" below means at least half.

**Shared head across conversations (both engines):** the cold call computed everything (llama.cpp: 0 of 6,472 cached; vLLM: 0 of 6,470). A second conversation with a different question and a third both reused the head: vLLM 6,400 and 6,464 of 6,470 (whole 64-token blocks), time to first token 190 to 220 ms against 1,820 ms cold; llama.cpp 6,454 of 6,472, 72 to 81 ms against 1,605 ms cold. An unrelated head was not reused on either. (Client times include the RunPod proxy.)

**Idle gaps 0, 15, 30, 60 and 120 s:** the head was reused after every gap on both engines (vLLM 6,400 of 6,471 to 6,473 each time; llama.cpp, run 1 only, 6,451 to 6,455 of 6,469 to 6,473). Each gap used its own new head; nothing else was sent during a gap. **One vLLM call after 15 s had a slow first token (1,794 ms, about as slow as a cold call) although the server reported the same 6,400 cached tokens**; its cause is not known and was not investigated (one observation; the RunPod proxy, the server's scheduling or something else). vLLM's other calls with the head reused also varied: 244, 369, 757 and 668 ms after the other gaps, 206 to 531 ms in the ladder probes, against 190 to 220 ms in the shared-head part. llama.cpp's were 173 to 299 ms after the gaps. Nothing past 120 s was measured.

**Other conversations pushing the head out (the cliff).** One head is read, then distinct heads of the same size, and the first head is asked again once 1, 2, 4, 8, 16 and 32 others have been read in total (the ladder stops at the first miss). Each probe, hit or miss, also re-reads the head, so the cliff figure is the number of *other* heads read since the head was last used (since the previous probe); the cumulative total is given in brackets:
- vLLM (a cache of 33,280 tokens, about 5 heads): kept with 4 others since last use (total 8), lost with 8 since last use (total 16). The edge lies between 4 and 8; it was not searched.
- llama.cpp, no host cache (`--cache-ram 0`, run 2): kept with 2 others since last use (total 4), lost with 4 since last use (total 8). With 4 slots, that matches the slot count: once four other conversations had run, the head's slot had been taken. The edge (3 or 4) was not searched.
- llama.cpp, host cache at its default (run 1): kept with 8 others since last use (total 16; about 52,000 tokens of other heads since last use), lost with 16 since last use (total 32; about 104,000 tokens since last use, about 207,000 in all). So with the host cache on, the head outlived its slot: it was served back after more conversations than there are slots. How much the host cache holds depends on `--cache-ram` and the machine's memory; only the default (documented as 8192 MiB; not read back) was exercised.

**Concurrency 1, 2, 4, 8, on a head already read:**
- vLLM: every request reused the head at every level (1, 2, 4, 8 of 8). Wall time for the whole group 248, 683, 708 and 748 ms.
- llama.cpp: **only one request in a group of 2 or 4 reused the head**; the others were placed in a slot that did not hold it and computed it again (cached 4 to 6 tokens; slot ids were not recorded); at 8, five of eight reused it. Whole-group wall time 114, 1,670, 4,651 and 4,779 ms in run 1 (115, 1,660, 4,715 and 4,837 ms in run 2): it grew with the number of copies computed again; how the server scheduled them was not measured. The same counts in both runs, so the host cache did not change this. In this configuration a warm head in one slot was not shared with requests placed in other slots at the same time.
- Brand-new head to n conversations at once: vLLM shared the first computation (reuse in n-1 of n, with one call computing it: 0, 1, 3, 7 of 1, 2, 4, 8). llama.cpp did not share while n was at most the slot count (0 reused at 1, 2, 4) and at 8 four of eight reused it (in both runs; plausibly requests that waited for a slot, but slot placement and waiting were not recorded, and first-token times do not separate them: in run 1 one request that waited 7,089 ms did not reuse the head).
- No request was refused or failed; every answer was right.

**Engine extras:**
- Unknown request field (`nn_unknown_cache_setting`): **ignored with status 200 by both**. So neither engine gave a refusal to exercise the adapter's refusal fallback with; it has nothing to do here. (Radiance also accepted every cache field; its refusal run used `logit_bias`, not a cache setting, as a stand-in.)
- llama.cpp `cache_prompt: false` computed everything (0 cached), `id_slot` pinned reuse to that slot, and the same head in a second slot was **not** reused (0 cached with the host cache off, 4 with it on).
- llama.cpp slot save, erase and restore (needs `--slot-save-path`): with `--cache-ram 0` (run 2) erase removed the head (`extras/slot0-after-erase`: 0 of 6,471 cached) and restore brought it back (`slot0-after-restore`: 6,470 of 6,471). **With the host cache at its default (run 1) the erase did not stop reuse**: the erase answered 200, and the next call into slot 0 with the same head still reused 6,469 of 6,470 tokens (`extras/slot0-after-erase` in `g10-llamacpp-run1.json`; first token 687 ms, against 75 ms for the warm slot and 1,882 ms for `cache-prompt-off`). The sequence before it was: warm slot 0, again in slot 0, the same head in slot 1, `cache_prompt: false` in slot 0, save, erase. Run 1's restore figure therefore shows nothing (the head was already served before it), and run 1's JSON carries the earlier code's single check `restoreBroughtTheHeadBack: false` for this reason; the code now records `eraseRemovedTheHead` and `restoreGaveTheHeadBack` separately (run 2: both true). `cache_prompt: false` computed everything in both runs (0 cached), host cache on or off. This is one observation per setting on this build (different pods, one run each), not a general rule about llama.cpp; the run 1 ladder (head served back after 8 others with 4 slots) points the same way.
  **Bearing on C06 (observation; no C06 code changed here).** C06's slot hygiene (`packages/controller/src/inference-cache/adapter.ts`, `#call`, with `freshSlot: "erase"`, the default; implementation-notes, C06 "Limits stated" (3)) assumes that erasing a slot whose last holder was another project or unknown means the next call "cannot reuse another project's KV", and then sends that call with `cache_prompt: true`. Run 1 contradicts that assumption for a llama-server with the host prompt cache on: after a successful erase the call was still served the same prefix from cache. What it affects: only calls whose prompt starts with the same tokens another project already sent (the cache matches by prefix). What it does not affect: the `reuseOff` path (`cache_prompt: false`, also used by `freshSlot: "off"` and when the erase fails), which computed everything in both runs. The llama.cpp profile (`profiles.ts`) does not mention `--cache-ram` in its tuning list, and its retention text ("an idle slot keeps its prompt until another prompt takes the slot") does not cover the host cache; its `isolation` is already `none`. Filed as an open follow-up in implementation-notes (G10, other engines).
- vLLM `cache_salt`: the same head under the same salt was reused, under another salt or no salt it was not (0 cached). So salt isolation works on this build.
- Counters: both servers' `/metrics` moved with the calls (vLLM prefix-cache hits and queries; llama.cpp prompt tokens and seconds); `usage.prompt_tokens_details.cached_tokens` is present on both (vLLM needs the flag; this llama.cpp build repeats `timings.cache_n` there).

## Compared with Radiance (named quantities only)
Radiance's reuse came in whole 2,048-token steps of a hybrid model (for example 6,144 of about 7,050 tokens); its retained marker survived 0, 15 and 30 s and was lost at 60 s in both runs that waited that long on a busy shared server (a first run on a quieter server had kept 90 s; `g10-evidence.md`, second run). Here vLLM reused in 64-token blocks and llama.cpp to within a few tokens, and nothing was lost across 120 s on rented servers that had no other client. The Radiance runs were on a server with other clients; these were not.

## What was not measured
Retention past 120 s; the exact edge of each cliff (the ladder is 1, 2, 4, 8, 16, 32 and each probe refreshes the head); llama.cpp with other slot counts or unified KV; vLLM host-memory or connector offload; a hybrid or other model on these engines; heads of other sizes; more than 8 concurrent requests or load that makes vLLM preempt (the preemption counter stayed 0); repeats and variance (each figure is one run); the host's memory and the actual host-cache fill; GPU speed on other cards; the build number of llama.cpp; the region. Claude, OpenAI chat and Responses and Strata are still open (see implementation-notes, G10).
The retained-marker clause is Radiance's (markers a server honours across requests); neither engine here has a marker, so the idle runs above are its counterpart.
