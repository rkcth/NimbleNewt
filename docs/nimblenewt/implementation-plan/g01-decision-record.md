## Dual database support

Both SQLite (default for a simple local installation) and PostgreSQL are first-release controller backends behind one typed transactional storage interface (cards F04a-F04d). There is one scheduler with two storage implementations, not two engines, and no promise of compatibility with arbitrary databases. Pi's own conversation storage is a separate boundary and does not move with the controller database.

## Remote topology

One authoritative controller; subordinate workers on other hosts (D1); private-network browser access (D3); optional replicated standby with owner-controlled promotion (D7). Workers cannot promote themselves, and loss of primary communication stops their work.

## Operating limits and workload envelope

As D6: 4 productive attempts installation-wide, 2 per worker host, 2 inquiry/review slots; qualification workloads of 100 simulated idle hosts and 20 concurrent synthetic tasks. These are qualification targets, not capacity claims for real agents.

## Sandbox decisions, 2026-10-21 (owner, one at a time)

- **Linux launcher (A03): bubblewrap.** The owner chose it over rootless containers and microVMs ("A sounds good"). Recommendation rationale (not the owner's words): it meets the stated boundary (scoped files, no credentials, controlled network, killable process tree) with the lightest install; the launcher refuses to advertise capacity where unprivileged user namespaces are unavailable (a consequence of the choice, not a separate decision); the launcher interface leaves room for a stronger backend later.
- **Changing permissions on a running agent.** Controller-side grants and revocations apply at the agent's next call with no restart. Sandbox-level access (mounts, network, limits) is fixed at launch and recorded as a recipe revision. Widening starts a fresh sandbox from a checkpoint; narrowing takes effect before the next action.
- **Revocation never destroys state** (the owner's concern was lost work or context; "Yes, write it down"). Order: freeze new calls, let in-flight calls settle (cancelled or uncertain ones go in the effect ledger), checkpoint, restart with the narrower recipe (A03 owns the launcher and quarantine; H12 owns the freeze, settle and checkpoint order). The checkout, home, scratch and conversation context are host-side and survive. Work under a path the agent lost is quarantined read-only for the owner. Only an emergency stop skips settle and checkpoint; the exposure then is the step in progress and context since the last checkpoint.
- **macOS launcher (A03): Seatbelt profiles** ("Seatbelt for macOS, keep the container option for later"). Research by the implementing AI session (2026-10-21), from news and blog sources, not Apple documentation, and not verified on hardware; A03 settles the first claim on the owner's Mac. Reported there: `sandbox-exec` is deprecated as a tool but the kernel mechanism underlies Apple's own sandboxing, it reportedly still works on macOS 26, other tools rely on it, and no Apple replacement was found for sandboxing arbitrary command-line processes. Expected limits, stated so the owner accepts them knowingly: process-level confinement (denied paths visible but unreadable), weaker CPU, memory and process limits, and reported bypasses for hostile code. Apple's Containerization framework (Linux containers in lightweight VMs; reported as Apple silicon and macOS 26 only, with sources disagreeing on its maturity) is kept as a possible later backend behind the launcher interface; it runs Linux, not macOS, tools. It has no card yet and is not planned for the first release. K07 re-runs the G05 macOS cases after each macOS release before the launcher keeps advertising capacity.
- **Workspace editing (OD-9, A04): mediated** ("Mediated for 1"). Agents edit their own host-side per-task checkout, mounted into their sandbox; changes reach shared files only through the controller's Git bridge with expected-version writes and the A06 human pre-commit gate. No shared workspace or `.git` is mounted writable into a sandbox. Two agents needing the same live files get conflict handling rather than shared live editing; a scoped file service remains the documented route if that proves too limiting.
- **Weaker macOS boundary shown at decision time** ("yes for #2"): U08 shows each host's sandbox mechanism and flags the weaker macOS boundary wherever the owner chooses or reviews where work runs.

## Open owner decisions from the documentation audit (2026-10-21)

A requirement-by-requirement audit of the product documents against the task cards added 38 cards (the plan now has 151). It also found places where the documents leave a policy open. These are recorded here for the owner; none is decided, and the recommendations are an AI session's suggestions.

- **Owner inspection of private desks and scratch** (README "Activity history and replay", operational contracts): the documents say only that the policy is to be specified and that the boundary between agents stays intact. Built provisionally in C01: the owner may read all agents' private scratch and join any chat, but not read their drafts or write to their desks. Recommendation: the owner may read anything, every read is audited and visible to the agent; decide before the inspection card (A10).
- **Pi and "state export" (card F08):** the README says harnesses that cannot export enough state are unsupported for durable tasks. Pi has no portable export but continues a conversation from its own storage after a restart, so it is treated as supported for durable tasks, reading the rule as "no way to recover". If you read it as "no portable export", Pi is unsupported for durable tasks until an exporting adapter exists. Tasks that must be rebuildable on another machine (`portable-reconstruction`) cannot use Pi either way.
- **Who sees which message in a conversation thread (card U02):** built so a participant sees only messages it sent or that were addressed to it, and the owner sees all. The alternative is a fully shared thread where addressing only controls delivery. Recommended: keep the built rule (it matches the private-by-default rule for agent scratch).
- **Conversation transport (card U02b):** built as authenticated HTTPS requests with cursor-based long-polling, which the documents listed as the likely first choice; server-sent events or WebSockets are not built. Local only by default; remote exposure is off unless asked for, and then needs TLS and the host names clients use. Recommended: keep it, and add push channels only if long-polling proves too slow.
- **Second harness in the first release:** recommended no (Pi only, with the capability declaration and refusal kept).
- **Retention defaults, backup deletion, recovery objectives; notification delivery; meeting quorum and seconding; amendments, points of order and sealed positions; agents building candidate releases of NimbleNewt itself; simulation mode; default cleanup deadline; model thinking in replay (recommended: not shown, as the documents say); supported filesystems and Linux distributions; first-release MVP selection:** see [the audit record](documentation-audit-2026-10-21.md), section 3; each needs an owner answer before its card starts.
