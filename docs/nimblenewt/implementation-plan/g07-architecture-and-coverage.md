# G07: current architecture, requirement coverage and validated task manifest

Status: **recorded; reviewed by a separate AI session (not a human review).** This is the architecture-of-record summary, a requirement-to-card coverage matrix, and what "validated" means for the task DAG. It does not change the design, open N00, or claim any card beyond its recorded status.

The detailed design is [design-proposal.md](design-proposal.md) (contracts, data ownership, failure handling) and the product description is the [README](../README.md); this record points at them rather than repeating them.

## Architecture in one page

- **One authoritative controller** (embedded TypeScript service) owns projects, tasks, assignments, policy, leases, effect admission, evidence and the audit trail. It makes deterministic transitions without a model.
- **Pi Durable** (pinned 1.3.0) runs agent conversations behind a **harness adapter** (built: `packages/pi-adapter`). Pi owns transcripts, branches and tool execution; the controller never reaches into Pi's storage, and Pi's storage is a separate boundary from the controller's database.
- **Controller storage** is a typed transactional interface with SQLite and PostgreSQL implementations, one scheduler over both, and journaled schema migrations (cards F04a-F04).
- **Integration tests** (`packages/integration`, card S09) are the one place the controller and the Pi adapter meet: a tests-only package that holds no product code, that nothing depends on, and that the package-boundary rules allow to depend on both. The controller itself depends on neither Pi nor the contracts; it talks to a conversation through a small structural interface (`ConversationSubmitter`).
- **Subordinate workers** on other hosts run work and artifacts over an authenticated transport; they stop on loss of the primary and cannot promote themselves. Optional replicated standby with owner-controlled, fenced promotion (D1, D7).
- **Isolation** by default for agent execution, per-OS boundary, protected filesystem and Git bridge; a trusted-host mode needs explicit authority (D4).
- **Interfaces:** conversation is the primary interface (private-network browser chat, D3); a versioned state API and durable conversation API for other clients; MCP adapters in both directions.
- **Recovery and release:** consistent backup and restore, deterministic release staging, migration rollback limits (cards K01-K05); external release-test protocol and qualification campaigns on macOS, Linux and Windows (X01-X10).

Built so far (see the README roadmap for current status): the TypeScript workspace and CI (F01, F03), the Pi adapter contract and its controller-facing port (F05, F06, G02), and the compatibility gate (G03). Everything else in the DAG is planned.

## The task DAG, and what "validated" means

`task-plan.json` is the source of truth: 302 cards under 22 workstream parents (N00, the implementation gate, is a parent issue with no cards), one root (G01) and one leaf (D05), a longest dependency chain of 52 cards, and 52 dependency phases. It is generated by `scripts/generate_task_plan.py`, which refuses to write a plan with an unknown dependency or a cycle. `scripts/plan.test.mjs` re-checks this on every `npm test` and in CI: every dependency exists, the graph is acyclic, card IDs and parents are unique and well formed, every card has a deliverable and acceptance text, a card marked implemented has all its blockers implemented or on a recorded exception list (F01 started before G01/G07 were closed), and every card named in this record's coverage matrix exists. Dependencies are leaf-level: a parent completes when its approved children do, so parent edges are not mechanical blockers.

**Authorization on record.** Planning synchronization and plan approval: October 17, 2026 ("Approved implementation plan", [approval.md](approval.md); detail in [G01](g01-decision-record.md#authorizations-on-record)). N00 execution authorization remains separate and is not recorded; work on the Pi-first path began on the owner's instruction of October 19, 2026.

Qualification follows implementation: tests exercise the actual NimbleNewt component, never a stand-alone probe, and the G cards qualify components after they are built. Historical probes are feasibility evidence only. A failed test preserves artifacts and blocks dependent acceptance; it does not erase completed work or reopen settled architecture.

### Areas the plan covers only partly, or not at all

These come from comparing the register with the cards; none is a new requirement.

- **Agent organization and hierarchy** (creating agents, team structure, reporting lines and delegated roles; the register calls the agents "persistent, hierarchical" and says "teams and delegated roles belong to agents") has no card that owns it. Identities and capabilities (A01), grants (A02) and supervisor recovery (V02) all assume the structure exists but none builds it.
- **Replay** (read-only observable activity, source and artifact versions, short rationales) has no dedicated card. The effect ledger (S05), artifact integrity (S06) and status explanations (U05) cover pieces of it.
- **Notification delivery, presence and disconnection handling** (an open engineering choice in the register) has no card.
- **Owner inspection of private agent records, retention, retirement and deletion/backup treatment** has no card; backup (K01) touches backup treatment only.
- **Credential storage** is covered only as secret references (F02) and bridge enforcement (A04); there is no card selecting and qualifying a credential store per OS.
- Contributor guidance, which the register says remains to be completed, is covered by D02 ("Architecture, contribution, protocol, troubleshooting and notices") and is not a gap.
- **Numeric defaults left unset by the owner** (P/PC allocation, meeting cadence, voting rules, lifecycle limits, update windows) are inputs to cards B01, M01, M02, L01-L03 and K02, not decisions this plan can make.

These should be turned into cards or explicit non-goals by the owner before the cards that depend on them start.
