# Context-window stalls: will NimbleNewt hit them?

Written 2026-10-21 by the implementing AI session, in answer to [`/srv/code/team/CONTEXT-WINDOW-STALLS.md`](../../../../team/CONTEXT-WINDOW-STALLS.md) (the Paperclip team's account of Hermes agents on a local model with a 131,072-token window dying with `Context compression timed out without reducing this conversation`). This is an AI analysis of NimbleNewt's design and of the Pi Durable runtime it uses, checked against the code in this repository. Nothing here is a measurement on a real local model; the numbers come from Pi's documented settings and the library source. It records one new plan card, **C07**, that makes the fixes testable.

## Short answer

**NimbleNewt can hit every one of these failures today, and only partly by design is it protected.** What protects it: work state lives in controller records and artifacts, not in the conversation (Q6); Pi compacts in the background well before the window is full, and a failed blocking compaction fails the run instead of hanging (Q4, partly). What does not: nothing yet bounds the size of the first prompt, Pi's default per-tool output limit is too large for a small window, the summariser is by default the same model that is running low, with a timeout that is Pi's default (at least ten minutes), our adapter leaves Pi's automatic compaction on although our own design says compaction must be explicit, and nothing turns "the run died after its real work" into a hand-off (Q2, Q4, Q5, Q7). Resumed sessions and branches inherit the whole history (Q3). Plan card **C07** (below) closes these with tests; nothing has been built for it yet.

## How Pi Durable compacts (the facts everything below rests on)

From the library's README and source (`@earendil-works/pi-durable` 1.3.0, pinned):

- Automatic compaction is **on by default**. Settings: `reserveTokens` 16,384, `keepRecentTokens` 20,000, `backgroundTokens` 32,768.
- For a **131,072-token** window that means: a compaction starts **in the background** above about 81,900 tokens (62.5%), the conversation keeps working while the summary is made, and the **next request waits** only above about 114,700 tokens (87.5%). This is gentler than Hermes' synchronous compression at 75%.
- By default the summary is written by **the same model the conversation uses** (`completeSimple(model, ...)` with the agent's own model and the harness-level `settings.stream` options). Pi lets a controller change that: a `beforeCompact` hook on the compaction task can decline a compaction or supply its own summary, and Pi has `reset(handoffNote)` and a tool result `control: { handoff }` for starting fresh from a short brief (README, "Reset and Handoff"). NimbleNewt uses none of these yet. The summary may take up to `0.8 x reserveTokens` (about 13,000 tokens). The request is the serialised older history plus a prompt, so it can itself approach the window.
- Failure handling: a retryable error is retried with backoff up to `maxRetries`; a **blocking** compaction that fails makes the waiting generation fail with `model_error` ("Compaction failed: ...") and sends no request. If a provider rejects a request as too long, generation compacts and retries once.
- **There is no timeout of its own on the summary request.** The stream timeout is `timeoutMs` from the harness settings, which defaults to the provider SDK's (OpenAI and Anthropic clients: 10 minutes, and those SDKs also retry up to 2 times by default); Pi then retries a retryable summary error up to 3 more times (2 s base delay, 60 s cap). `PiAdapter` sets none of this (it only passes `settings` through). The worst case for one blocking compaction is therefore at least ten minutes and possibly several times that when timeouts count as retryable. The 10 minutes is the same 600-second ceiling the Paperclip Lead hit.
- Pi bounds **every tool result** by default (text to 50 KB or 2,000 lines, the head kept; the `bash` tool keeps the tail and spills the full output to a file), but 50 KB is roughly 12,000 to 17,000 tokens, so three or four large results fill a 131k window from empty. Images and other non-text content are not covered by that bound.
- If there is **nothing to cut** (the history before the last `keepRecentTokens` is empty, which is what a short conversation with one huge first message looks like), compaction finds nothing to compact and lets the request go ahead unchanged. A huge first prompt therefore cannot be compacted by Pi either.

## The seven questions

| # | Question | Status in NimbleNewt | Evidence and consequence |
| --- | --- | --- | --- |
| 1 | Small-window or local model with automatic compression? | **Exposed.** | The design targets local models (the llama.cpp experiments in `context-and-windows-results.md`; local-to-cloud fallback in R01/R02), and Pi's automatic compaction is on by default. The first local model with a 128k window brings the whole failure mode. |
| 2 | Large fixed first prompt? | **Not bounded yet.** | Today's bridge sends only the task title and description (at most about 8,000 characters), so the *text* is small. But every first call also carries Pi's system prompt and the schema and description of every tool (bash, read, edit, write, and later MCP tools), which nothing measures yet, and the design builds startup context from task history, retrieval and continuation records (C02, C04) with no number on it: C02 says only "context budget bounded". Without a hard rule the Lead's 78k-token start is reproducible. |
| 3 | Unbounded history replayed? | **Exposed.** | A task is one long-lived Pi conversation, and a resumed attempt continues it whole. An inquiry branch forks at the task's latest completed-turn boundary (C05, F06), so it starts about as large as its parent: with a parent at 100k tokens an inquiry on a 131k model has 30k left. If a compaction is the latest boundary the branch already gets the compacted context (summary plus recent entries); the bad case is a compaction that lands after a still-unanswered input, which is not a boundary, so the branch forks before it and pays for the whole uncompacted prefix and can be larger than its parent. |
| 4 | Summariser is the model that is out of room? | **Exposed, partly mitigated.** | By default the same model (above). Mitigated: background compaction starts early and a failed blocking compaction fails the run cleanly instead of stalling forever. Not mitigated: no short timeout, no separate summariser or fallback when the summary cannot be made. Pi offers the hook for exactly that (`beforeCompact`); we do not use it yet. |
| 5 | Tools return large blobs? | **Bounded, but too loosely for a small window.** | Pi bounds every tool result's text by default (50 KB or 2,000 lines; `bash` keeps the tail and spills the rest to a file), and the controller bounds its own records (inbox payloads and effect inputs at 64 KB, artifacts kept out of the conversation). But 50 KB is about 12,000 to 17,000 tokens per call, so a few large results fill a 131k window, and images and other non-text content are not bounded by it. |
| 6 | Work kept in files, not conversation? | **Yes, by design.** | Effects, attempts, artifacts, recovery points (the conversation checkpoint with the artifact manifest and request IDs) and continuation records are controller state. A fresh attempt can start from them. This is NimbleNewt's strongest protection, but starting fresh from a short brief is not yet an implemented path (C04). |
| 7 | Clean hand-off before the risky step? | **Half.** | The Lead's failure (merge done, hand-off lost) is handled for the *effect*: intent is recorded first and the result is reconciled after a crash (S05, S09 proves it). Not handled: the *hand-off* is written by the agent's final message, so if the run dies afterwards no hand-off exists. The controller has the facts (ledger, artifacts) but nothing turns them into a hand-off when an attempt ends without one. Pi's own `reset(handoffNote)` and `control: { handoff }` are the primitives to build it on. |

## A conflict with our own design

The design says "any required compaction is explicit and versioned, never an incidental consequence of asking a question" ([design-proposal.md](design-proposal.md), section 6A). `PiAdapter` leaves Pi's automatic compaction at its default, which is **on**: compaction happens on Pi's thresholds whenever a generation is prepared, including on an inquiry branch. So the adapter as built deviates from the design. The owner decided (2026-10-21, "Let's use pi's"; see [the G01 record](g01-decision-record.md), decision 12): **use Pi's own compaction**, automatic, as built, and record the deviation from section 6A. The three options considered were these, and the choice is open to correction: (a) the controller owns every compaction through the `beforeCompact` hook, so each one is recorded, versioned, time-limited and uses the configured summariser; or (b) turn automatic compaction off and have the controller compact explicitly through the port at its own thresholds (then nothing but our own budget stops an overflow); or (c) accept automatic compaction as a recorded deviation from the design. **C07 follows (c)**: it does not build a controller-owned compaction; it bounds Pi's with explicit timeouts and retries, keeps the budgets, resume guard and hand-off, and uses the `beforeCompact` hook for the short summary limit and the fallback summariser, because Pi has no setting for either (compaction shares the generation's stream settings). So C07 is (c) plus a thin piece of (a).

## Requirements for card C07

Each is a testable rule; the test uses the scripted offline model with a small context window (the offline harness already takes a `contextWindow`).

1. **A context budget per model.** The routing record (R01) carries each route's window. Startup context must be at most **25%** of the window, and startup plus likely tool output plus the reply reserve at most **60%**. The startup figure counts everything in the first call, including Pi's system prompt and every tool's schema and description, not only the text we write, and is measured from the provider-reported usage of a real first call. These are estimates (about 3 characters per token, checked against the provider's reported usage) and configurable; they are enforced at dispatch, not hoped for.
2. **One startup builder.** The first prompt is built only by a controller builder that orders items by priority, cuts older and machine-written items to a head and tail (the Paperclip fix), always keeps the newest items, the human's words, the permissions and the current goal whole, and records what it cut with a link to the full original (an artifact). A prompt that cannot fit even after cutting is refused with a visible blocker, never sent.
3. **Resume guard.** An attempt never continues a conversation whose stored size is over 60% of the target model's window. It starts fresh from the continuation record (C04) plus retrieval, using Pi's `reset(handoffNote)`, and says so.
4. **Bounded summariser with a fallback.** Set the model stream timeout and retries explicitly (no SDK default); give summarisation its own short hard limit (for example 120 s) through Pi's own settings where they can enforce it and otherwise through the `beforeCompact` hook (compaction itself stays Pi's, by the owner's decision above); a restart in the middle of the hook must neither duplicate nor lose the summary. On timeout or failure: summarise with a different configured route (a larger-window or authorised cloud model) if there is one; otherwise do not hang: end the attempt as `context_overflow` and start a fresh one from the continuation record. The summariser must be configurable separately from the working model.
5. **Tighter tool output limits.** Lower Pi's per-tool limit (50 KB or 2,000 lines) through each tool's `outputLimits`, including the tools MCP servers contribute, to a default sized to the model's window (about 16,000 characters on a 131k model), with the remainder paginated or kept in an artifact and referenced; count images and other non-text results against the budget; state dumps and echoed reports go through the same limit.
6. **Hand-off from durable facts.** When an attempt ends without its own hand-off (it died, timed out, overflowed), the controller writes one from the ledger, artifacts, checkpoint and last known state (Pi's `control: { handoff }` and `reset(handoffNote)` are the primitives), and attaches it to the task, so the next attempt or the owner reads facts, not a lost message.
7. **Overflow is its own failure class.** A run that fails for context reasons is recorded as `context_overflow` (not a generic error) and handled by bounded retries from a fresh start, with a visible blocker when they are used up (S07 machinery).
8. **Inquiry branches respect the budget.** If the context at a task's latest boundary is over the inquiry model's budget (in particular when a compaction landed after an unanswered input and the branch would pay for the uncompacted prefix), the inquiry uses the latest compaction boundary plus retrieval (and says it did), instead of forking the whole thing.

## What stays uncertain

- The 25% and 60% limits and 3 characters per token are the Paperclip team's estimates from their transcripts. They are a sensible start, not a measurement of NimbleNewt's content; C07 must measure against real prompts.
- Nothing here has run on a real local model; the stall is inferred from Pi's source and documentation, not reproduced.
- Pi's compaction behaviour could change with a runtime upgrade; the pinned version (1.3.0) and the G03 compatibility gate are what hold it still.
