# Provisional defaults awaiting the owner's review

Written 2026-10-22. The owner said: "Use sensible defaults and then review them with me afterwards, don't delay coding because of defaults." Each item below is a default chosen by an AI session, not a decision by the owner. Work goes ahead on these; the owner reviews the list once and anything changed is a small edit to a setting, not a redesign. The defaults are chosen to be safe, reversible and configurable.

| Item | Default used | Why | Where it lands |
|---|---|---|---|
| **First-release scope (MVP)** | One owner, chat-driven, several projects; Pi Durable as the only harness; Linux and macOS sandboxes; PostgreSQL or SQLite storage; approvals policy with the three profiles; reviews, conversations, notifications, catalog, workspace bridge; **meetings with rosters, quorum and ballots (M01-M06)**. Windows launcher (A03b), browser UI beyond settings and approval views, and simulation mode come after the first end-to-end run. **Owner decision 2026-10-22: M06 is in the first release (the system cannot function properly without ballots); everything else in this row confirmed.** | The first end-to-end run is the milestone that turns tested parts into a working product; everything else can follow it. | Order of the remaining cards |
| **Retention** | Keep everything by default (history, activity records, artifacts, audit) with no automatic deletion. Owner-set limits per kind later, changed by chatting with the supervisor; deletion is always an owner action and is itself recorded. **Owner decision 2026-10-22: confirmed; tiered retention (K06b) is an optional feature after the first release.** | Deleting by default is the harmful direction; disk is cheap. | K06, K06b |
| **Backup** | A scheduled local backup of the database and the data directory (daily), keeping the last 7 daily and 4 weekly; full recovery backup is separate from configuration export. Secrets are left out unless the owner turns on encrypted backup (K01b): public-key encryption, unlocked by a passcode or a recovery file, scope 'secrets only' or 'everything'. **Owner decision 2026-10-22: the first release has this simple backup plus K01b; the full configurable system (K01c) comes before 1.0; backup scope tiers (K01d) are optional after the first release.** | Matches the documented separation of export and recovery backup. | K01, K01b, K01c, K01d |
| **Recovery objectives** | After a crash with the disk intact, every committed database operation survives and workspace files are as of the last write the system had flushed to disk (an agent's own edits in its checkout are not atomic); after losing the disk and restoring from backup, up to 24 hours of database changes are lost, and unpushed workspace work is lost unless work-in-progress branch backup (P02b) is on or the checkouts are on a separately backed-up disk (the nightly backup covers the database, Pi state and artifacts, not checkouts). Code itself is not in the database: it lives in git checkouts on disk, and pushed code is its own backup. **Owner decision 2026-10-22: confirmed with this wording; optional work-in-progress branch backup (P02b) added for after the first release.** | The database already commits per operation; the daily backup bounds the rest; the standby (K04) closes the gap for the database only, not workspace files. | Recovery cards, P02b |
| **Backup deletion** | Deleting a project or record does not delete it from existing backups; backups age out by their own schedule. The owner can ask for a purge of named backups. Backups older than an owner-set number of days are deleted automatically (default about 35 days). The delete confirmation says how long the item stays in backups. **Owner decision 2026-10-22: confirmed; automatic deletion of backups older than X days; no crypto-shredding planned.** | Predictable and simple; purge is explicit. | K01, K01c |
| **Notification delivery** | Three levels: Notice (inbox and activity only, a count in the daily report), Needs you (waiting on the owner; one view, count in every chat reply) and Urgent (interrupts at once: safety stop, blocked critical path, failing backups, a sandbox escape attempt, a credential used from the wrong task or host, a protected path touched, a failed integrity check or repeated denials over a threshold, controller or host down, and any Needs-you item that has stopped work or waited past the owner-set time, default 24 hours). The daily stand-up report is the digest (09:00 UTC plain digest only when no stand-up is scheduled); no quiet hours until the owner sets them (Urgent ignores them); external channels only when configured. **Owner decision 2026-10-22: levels named Notice, Needs you, Urgent; a Needs-you item that stops work becomes Urgent; the digest is part of the daily meeting.** | The owner sees what needs a decision in one place without being interrupted by routine questions. | U11, U11b |
| **Meeting quorum and voting** | Roster fixed per meeting; majority quorum; simple majority passes; ties fail; the owner's presence can veto nothing but is always reported; seconding required only for motions that change policy, grants or budgets. | Matches the card defaults (majority quorum, ties fail) and keeps routine meetings short. | M06 |
| **Amendments, points of order, sealed positions** | The chair may accept amendments before a vote; any participant may raise a point of order and the chair rules; sealed (secret) positions are off. | Keeps meetings brief and auditable; secrecy adds machinery for little gain. | M05, M06 |
| **Agents building candidate releases of NimbleNewt itself** | Off. Only the owner starts such work, in a separate project, and a result is never installed without the owner's explicit step. | Self-modification is the highest-risk use; it must be an explicit owner decision. | Improvement cards (B-series) |
| **Simulation mode** | A dry-run flag on a task: every effect is planned and shown but not performed, and no money is spent. After the first end-to-end run. | Useful, but not needed to reach the first run. | Later card |
| **Default cleanup deadline** | A finished task's checkout, scratch and sandbox leftovers are removed 14 days after the task is done; anything quarantined is kept until the owner releases or removes it. | Frees disk without touching anything the owner might want. | Cleanup cards (P-series) |
| **Model thinking in replay** | Not shown (as the documents say); only the visible messages and tool calls. | Matches the documents. | Replay (C-series) |
| **Supported filesystems** | Linux: ext4, xfs, btrfs; macOS: APFS; Windows: NTFS. Case-insensitive and normalising behaviour is handled in the workspace bridge. Network filesystems are not supported for the data directory. | What CI and the workspace tests cover; databases need reliable locking and fsync. | F04h environment check |
| **Linux distributions** | What CI runs (Ubuntu LTS) plus Debian stable and the current Fedora as expected to work; others are unsupported unless overridden (F04h). | Matches the "refuse unless overridden" rule. | F04h |
| **Standing-rule numbers** | 3 approvals, 30-day grant, 90-day look-back, 30-day quiet period; the strict-to-derived question after every 3 approvals; 7-day trial. | Decided as provisional on 2026-10-22. | Policy settings |
| **Task credentials** | Issued by the owner (later the dispatcher); no automatic expiry beyond the task's end; a task credential holds the agent's project-wide grants in that project. | See T01/A10b notes. | H12 |
