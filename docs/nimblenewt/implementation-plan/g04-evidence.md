# G04 evidence: supporting durable engine integration (2026-10-22)

Card G04 asks whether the selected architecture (design proposal section 3: D2, an embedded TypeScript controller with interchangeable SQLite and PostgreSQL stores, Pi behind the conversation adapter) keeps acknowledged requests and protected effects when the worker and the controller die. Everything below runs the production code: the S09 slice (`@nimblenewt/controller/testing`: `ProjectService`, `AssignmentService`, `InboxService`, `EffectService`, `ArtifactService`, `RecoveryPoints`, `ConversationBridge`, `Reconciler`) and S08 `WaitService`, over the real controller databases, with the production Pi adapter (F05/F06, `piConversation`) on durable JSONL storage and the offline scripted model. No network (tests run under `scripts/offline-guard.mjs`). There is no state machine of the test's own: the glue (`g04-fixture.ts`, `g04-wait.ts`, `g04-worker.ts`, `g04-child.ts`) builds services, starts and kills processes, and counts.

- Code under test: implemented in the commit that adds this file (the lead appends the hash). Base before the commit: `HEAD` of `wip/G04` (main at the time of the merge) plus the working tree.
- Databases: SQLite (`SqliteStorage`), SQLite on a worker thread (`SqliteWorkerStorage`) and PostgreSQL (`PostgresStorage` on the embedded server the other tests use). The in-memory reference store is not a real database and is not used.
- Reproduce: `npx tsc --build`, then for each file `node --import ./scripts/offline-guard.mjs --test --test-timeout=600000 packages/integration/dist/<file>.test.js` (files below); add `NIMBLENEWT_G04_EXHAUSTIVE=1` in the environment for the exhaustive run.

Two kinds of run exist. Each part makes its own uncrashed run first. The real-kill files are not skipped on win32; if the QA job shows they cannot work there, the Chaos-crash tests (faults, waits, the controller-crash test) remain the Windows coverage and this record must say so. Temporary directories are removed on test failure and when the process ends (including a timeout).

## The path

One fixed list of commands (create project and task, assign, deliver, inbox admits the attempt, the worker starts the task, the controller's bridge submits the work to Pi once, the protected effect `git-push` is intended, claimed, applied by an idempotent target and settled, the artifact is published, the recovery point is recorded, the task is completed, the attempt finished, events delivered). Running it again after any death completes it exactly once. It has 127 numbered boundaries (before and after every storage write or claim, the bridge's three, the target's two, the blob folder's four); 41 of the boundary pairs are `applyOperation` commits. `g04-fixture.ts` records the audit type behind each commit, so every report names the operation ("84 after artifact.publish").

After every death the final state must equal the uncrashed run (`signature`: every aggregate with revision, audit counts per command type, blob files), the S09 `check` must hold (exactly one project, task, generation, attempt, recovery point; the effect `confirmed` and applied once in the outside world and reached once at the target; every message delivered once; no open blocker), Pi's transcript must hold the model's answer once and the task as one user message, and the recovery point's checkpoint must verify in the runtime.

## Ambiguous commits and rollbacks, all three databases (`g04-faults-*`)

The production `FaultInjectingStorage` (F04c) is armed at the Nth `applyOperation` of the whole path, for each of the 41 operations: a rolled-back transaction (`retryable`), an ambiguous commit that did commit (`after` + `uncertain_commit`), an ambiguous commit that did not (`before` + `uncertain_commit`), and six rollbacks in a row (more than the budget of 5). Results on SQLite, SQLite worker and PostgreSQL alike: the single faults were absorbed 41 of 41 times each (commit protocol resolves by stable ID; the final state is byte-identical to the clean run, nothing applied twice). The six-in-a-row burst surfaced: 19 absorbed (failed scan-cursor saves and similar are retried by the next pass by design) and 22 finished by the same process's next reconciler pass after leases ended; none needed a restart. The only difference from the clean state is the `delivery-failures` counter (a delivery really failed and was retried), which is tolerated in the burst case only.

## Real connection loss on PostgreSQL (`g04-connection-postgres.test.ts`)

A relay (`FaultProxy`, F04d) between the controller and the embedded server cuts the connection immediately before or after an exact statement of the whole path (587 statements, one pooled connection). 218 cuts: before and after each of the 59 COMMITs, plus before and after every 11th other statement. A cut after COMMIT is the real ambiguous commit. All 218 end in the clean run's state: 107 COMMIT cuts absorbed by the commit protocol, 9 finished by the next pass after leases ended, and 2 restarts (the cuts at the epoch acquisition in `startProcess`, which by design needs a new start); for other statements 84 absorbed, 14 next pass, 2 restart. No run applied anything twice or lost an acknowledged operation.

## A kill inside a protected tool the model calls (`g04-tool-*`, added 2026-11-19)

Before this, the protected effect always ran from the worker's own code, so a kill in the middle of a tool the Pi model calls was not proven. The `g04-tool-*` files close that gap for the generation-service route that a tool bridge write takes (card L05d).

- **The setup.** The same controller services and the same three databases as above, the real Pi adapter on durable storage, and a scripted model that calls one tool, `push`, and then gives its final answer based on what the tool returned. The tool does what the controller's bridge does for a write. It records the call in a generation and completes that generation. It admits the call as an effect, using the bridge's own command ID (`bridgeCommandId("bridge", attempt, call)`, now exported). Then it runs the effect through the ledger against the idempotent target. It takes its replay setting from the production bridge tools (`BRIDGE_REPLAY`). Since the follow-up below, that setting is `"safe"`, so after a crash Pi presents the interrupted call again with the same call ID. The second test uses no replay setting, so the interrupted call is not presented again.
- **Kills.** The child process is killed with a real SIGKILL at each of the 16 boundaries of the tool's route. The route runs from the model's call through begin, record, complete, the admission, the claim, the target's two steps and the settlement, to the answer the tool gives back. As in the main path, the database is read before any command runs and a new process finishes the path. Every boundary is killed on every run, with no sampling (times below). The child writes the label it dies at just before the SIGKILL, and the test checks it is the boundary the uncrashed run numbered, so a kill that lands elsewhere (a route that took other steps in the child) fails instead of passing unnoticed.
- **Checked every time.** No acknowledged operation is lost. The target is reached at most once and applies at most once, and the ledger holds at most one effect. The model is never told "pushed" unless the push was applied. A settled effect matches the outside world. The task finishes with one task message and one final answer, which the recovery point keeps. All of these held on SQLite, on SQLite on a worker thread and on PostgreSQL (2 tests per file, 32 kills per file; on this Linux machine with Node 22 the files took 23 s, 31 s and 27 s).
- **What happened before the follow-up (2026-11-19, branch `card-g04-s1`).** The bridge tools did not say they were safe to present again, so after a crash Pi told the model the call was interrupted and never presented it again. Per boundary: from the model's call to just before the admission (8 boundaries) nothing was pushed and no effect existed; after the admission and before the claim (2) the admitted effect stayed `intended` for good; after the claim (4) the effect stayed started and unsettled with no blocker, whether or not the push had been applied; after settlement (2) the push was confirmed but the model was told it did not finish. With the tool declared replay-safe, all 16 boundaries ended exactly like the uncrashed run. Three implementation gaps followed from this:
  1. **An effect that was admitted but never started was never closed.** The production reconciler left any effect that had not started to "its owner's attempt", and the interrupted call was never presented again.
  2. **A started bridge effect was never settled and no blocker was raised.** The production composition (`api/start.ts`) gives the reconciler no bridges (`bridges: {}`), so an unsettled started effect was only counted (`effectsUnbridged`).
  3. **The model was told an applied push "did not finish".** A model that then tried again would make a new call with a new call ID, and so a second push.

- **The follow-up fix (branch `card-g04fix-s1`, 2026-11-19).**
  - **Gaps 1 and 3: an interrupted bridge call is presented again under its own call ID.** Every bridge tool now declares `replay: "safe"` to Pi (`BRIDGE_REPLAY` in `pi-adapter/src/bridge.ts`). After a crash Pi runs the interrupted call again with the same call ID, and the controller answers it from its records: the admission is found by its command ID, and the effect ledger finishes it. A done effect answers with its recorded result, a never-started one runs now (once), and a started one is reconciled with the target instead of being run blindly. The worker keeps the bridge's call ID for such a call: `seed` is told which calls in the stored conversation have no result (`AdapterConversation.openToolCalls`), and it is told before the hold is released (`worker/process.ts`), so the call reaches the controller under the ID it had before the crash and not under a new number. This is proven end to end with the real bridge tools and a real SIGKILL in `pi-adapter/src/restore.test.ts`, including a provider that reuses a call ID. The G04 tool test's own `push` tool uses Pi's call ID directly.
  - **A restarted controller is not refused as busy.** An effect claim now records the primary epoch it was taken under. A claim from an older epoch belongs to a controller that is no longer the primary, so it is given up at once instead of after the 5-minute lease. Recovery still treats it as an executor that vanished: the target is asked, or re-run with the same key if it honours one, or the effect becomes uncertain. Without this, a call presented again right after a restart would be answered "busy", and a model might then make a new call.
  - **Gap 2 (and gap 1 when a call is never presented again): the reconciler closes or reports a bridge call's effect.** `EffectService.closeUnbridged` handles effects of kind `bridge` (the tool bridge's admitted calls, which no reconciler bridge can run or ask). While the attempt that admitted the effect still holds the task, the effect is left to that attempt. Once the attempt has lost the task, nothing will present the call again. An effect that never started is then closed as `failed` (nothing was done). One that started under a claim its executor never gave back is marked `uncertain`; that stops every later run, and the owner is told by an `effect_uncertain` blocker. Nothing is ever run.
- **What happens now (asserted per boundary on SQLite, SQLite worker and PostgreSQL).**
  - **First test, the production setting** (the interrupted call is presented again): all 16 boundaries end exactly like the uncrashed run. The push is applied once and confirmed, the model is told "pushed", and no effect is left open.
  - **Second test, a call that is not presented again** (a tool that is not replay-safe, or a conversation whose interrupted work was abandoned):

| Kill at | Outcome after the restart |
|---|---|
| from the model's call up to just before the admission (8 boundaries) | nothing pushed, no effect, the model is told the call did not finish |
| after the admission, before the claim (2) | nothing pushed; once the attempt ends, the effect is **closed as failed** |
| after the claim, before the target applies (2) | nothing pushed; once the attempt ends, the effect is **marked uncertain and the owner is told by a blocker** |
| after the target applied, before settlement (2) | pushed once; once the attempt ends, the effect is **marked uncertain and the owner is told by a blocker** (never pushed again) |
| after settlement (2) | pushed once and confirmed; the model is told it did not finish, because the call was not presented again (this is the setting the production bridge no longer uses) |

  - **Invariants added to every run.** No effect is left `intended` once the path has finished. An `uncertain` effect has an open `effect_uncertain` blocker. A `failed` effect never started. The call is recorded as `admitted` exactly when the ledger holds its effect (`ToolState.call` is now asserted).
- **ASSUMPTION:** the scripted model still never retries by itself, so the safety check measures the controller and not a model's choice. With the fix, a model has no reason to retry a push that happened, because it is told "pushed".
- **ASSUMPTION:** a call is presented again by the same attempt (the local worker restarted with `start.recover`). If the controller gives the task to a new attempt, the old attempt's calls are not presented again, and its effects are closed or reported by the reconciler as above.
- **ASSUMPTION:** a target that cannot be asked is not guessed at. A started bridge effect whose attempt is gone becomes `uncertain` even if the push did not happen (boundaries 80 and 81), because only the operation's own service could say. The owner checks and resolves it with `effect.resolve`.

**Mutation checks of the follow-up (each restored afterwards).** (a) `reconcile.ts`: the new closing was switched off. The second test then failed on SQLite at boundaries 78 to 83 ("left open"). (b) `effects.ts` `closeUnbridged`: a started effect was closed while its attempt still held the task. The first test then failed at 80 to 83 (marked uncertain before the call was presented again), and the `closeUnbridged` unit test failed on all four backends. (c) `bridge.ts` `seed`: open calls were ignored. The bridge unit test failed (the presented call got a new number). (d) `effects.ts`: the epoch rule was removed. The older-epoch claim unit test failed on all four backends. (e) `adapter.ts` `openToolCalls` matched results by call ID only (its first version). The end-to-end bridge crash test failed: the interrupted write was presented again under a new `d:` ID.

**Not covered by this slice.** The tool bridge service itself (`ToolExecutionService`: the credential, the binding of the call to what the model wrote, the pause gate) is not inside the killed process. Its admission behaviour is covered in-process by the L05d tests. Also not covered: the real out-of-process Pi worker (H12b), a model that retries, and macOS/Windows (Linux only). In production the generation is begun, recorded and completed from the model stream before the tool runs; here those steps sit inside the tool. So 7 of the 16 boundaries (the call itself and before/after begin, record and complete) leave the controller's database as a kill while the stream is recorded would, but not Pi's: in this test Pi's durable log already holds the started tool call, so after the restart Pi tells the model it was interrupted. What Pi does after a kill in the middle of the model stream itself (before any tool runs) is not measured here, and the first row of the table must not be read as covering it. The other 9 boundaries (from just before the admission to the tool's answer) are where the production bridge runs.

**Mutation checks (SQLite file; each change was restored afterwards).** (a) In `effects.ts`, reconciliation was changed to ignore a target's "applied" answer and run the effect again. The replayed test (since the follow-up the first test, the production setting) then failed at boundaries 82 and 83 (the target was reached twice). (b) In `effects.ts`, the claim was changed so that it no longer marks the effect as started. Both tests then failed at 82 and 83: the target was reached twice, and the push was applied while the ledger said the effect had never started.

**First review (2026-11-19).** The outcome sentence of each kill is now built entirely from the state (what was pushed, what the model said, which blockers are open), so the per-boundary comparison also checks the "no blocker" and "nothing pushed" claims instead of assuming them. The sweep asserts the exact list of the 16 route steps in order, so a step that disappears or moves out of the tool fails the test rather than going unkilled. A new invariant: the target is never reached without an effect in the ledger. Reviewer mutation checks on the built files (SQLite file, each restored): (c) the tool used a new call ID on every run (as a model that calls again would): both tests failed, 2 effects in the ledger and the target reached twice; (d) in `effects.ts` a target's "not_applied" answer for a started effect settled it as confirmed: the replayed test failed at 80 and 81 (confirmed but nothing applied, the model told "pushed"); (e) the reconciler opened an `effect_uncertain` blocker for a started effect it has no bridge for (the shape of a gap-2 fix): both tests failed on the changed outcome, so the record of gap 2 is live.

**Second review (2026-11-19).** Two checks added. The child now writes the boundary label it dies at to stderr just before the SIGKILL, and the parent fails the kill unless that label is the one the uncrashed run numbered (before, a child whose route took other steps would have died elsewhere unnoticed). A new invariant: the model is told "pushed" only if the ledger holds the effect as confirmed (before, a settlement that was answered but not written passed in the uncrashed run, since only the outside world was compared). The note on the 7 stream boundaries now says that Pi's side differs from a kill in the middle of the model stream. Mutation checks on the built files, SQLite file, one at a time, each file restored and checked byte-identical by SHA-256: (f) the ledger ran the target again for an effect that had already started (double push): the replayed test failed at 82 and 83, the target reached twice; (g) the target's success was answered as confirmed without writing the settlement (lost confirmation): both tests failed in the uncrashed run on the new invariant; (h) a started effect was settled as confirmed without asking the target (false "pushed"): the replayed test failed at 80 and 81, the model told "pushed" with nothing applied; (i) the child reported the previous label: every one of the 32 kills failed as "died elsewhere". **Second review of the follow-up (2026-11-19).** The kill sweep did not exercise the epoch rule: the slice harness gives effect claims a lease of 1 ms and the restart advances the clock by 10 minutes, so the dead process's claim had always expired. Mutation check on the built `effects.js` (restored byte-identical): with the epoch rule removed, both SQLite tests fail at "after effect.claim" (the effect is left open, the model told it did not finish); before this change the same mutation passed the sweep.

## Mutation checks (each made named tests fail; restored afterwards)

Five checks were run by the implementer against the exhaustive files, before the sampling was added: `commit.ts` uncertain commit rethrown (2 of 4 fault tests fail); `waits.ts` no deadline timer (3 of 3 fail); `bridge.ts` random request ID (2 of 2 worker-kill tests fail, the model is asked twice); `bridge.ts` no reviewed `recover` step (in-flight worker kill fails); `effects.ts` reconcile answer `applied` ignored (the kill test fails: the target is reached twice). The reviewer ran three further mutants against the DEFAULT sampled set and all were caught: `commit.ts` an uncertain commit with the operation absent treated as success (caught by the faults "ambiguous commit that did not commit" tests); `effects.ts` a started effect re-executed instead of reconciled; and `inbox.ts` the message's own attempt not recognised (both caught by kill-sqlite, kill-postgres and the faults burst test; the process files too when run). The five implementer checks were not repeated on the sampled set.

## Classification

No failure was found in the architecture or in the controller or adapter code. Two defects were found in the new test support while writing this and fixed: the PostgreSQL fault relay (`proxy.ts`) delayed every statement ~25 ms through Nagle's algorithm (a 587-statement path took 16 s and the first run of the cut test timed out): `setNoDelay` on both sockets, covered by the connection test; and a first driver judged "finished" by the absence of an error, whereas a reconciler pass that meets a storage error counts it and returns, so the state is now what decides. No production file changed.

## What this proof does not show

- A SIGKILL only ever lands between storage calls (at a numbered boundary), never inside a transaction or a commit, never mid-fsync. In-commit uncertainty is covered only by the injected faults and the PostgreSQL connection cuts.
- The kill that takes the controller and Pi together is a real SIGKILL; the "controller dies, worker lives" case is an in-process crash (the `Chaos` seam) with a real worker process, accepted as the evidence for that case; the controller side has no process boundary there.
- SQLite has no connection to lose; its fault coverage is the injected storage faults and the kills. Lock contention (`SQLITE_BUSY` under a second writer) is covered by F04, not here. No SIGKILL of the PostgreSQL server itself (`crashAndRestart` exists in the test server and is used by F04); here the server survives.
- Power-loss or host-crash durability (fsync behaviour, Pi's synchronous NORMAL default) is not tested: processes die, the operating system does not.
- In the main path the protected effect is run by the worker's code, not by a Pi tool. A kill during a protected tool the Pi model calls is now covered by the separate `g04-tool-*` files (next section), through the generation-service route a tool bridge write takes, not through the whole tool bridge service.
- The wait scenario uses owner commands and the reconciler; it is not coupled to a model answer, an inquiry (H04) or the scheduler's task start. The "interactive control" mechanism (chat requests with expected revisions) and the "pause and loss of authority" watchdog, placement, versioning and primary-recovery rows of section 3 are not exercised.
- The throughput targets of section 3 (4 attempts, 32 active-agent-equivalent workload, 100 idle hosts, latency and pool pressure) belong to the F04 workload qualification, not to this card.
- The model is scripted; provider failures and network faults are out of scope.

**Kill harness (slice 5, 2026-11-21).** Every real-kill file now uses one check, `killProblem` in `g04-fixture.ts`: the child must have died by its own SIGKILL, not finished, not hung, and must have reported the uncrashed run's labels up to and including the boundary (the whole list, since labels repeat; slice 5 review). Before, only the tool files checked the label; `g04-kill` and `g04-wait` checked "killed and not finished". A child that does not reach its boundary within `CHILD_DEADLINE_MS` (120 s) is killed by the parent and reported as hung, instead of leaving it to the 300 s per-test limit. `g04-harness.test.ts` tests both with real child processes, and that a result is taken only once the child's output is read to the end (slice 5 review) (probe scenarios that open no database). Mutation: an extra step in the main path child fails `g04-kill-sqlite` as "died elsewhere" at all 18 misplaced kills of part 1; with the old check the same breakage was caught at only 6 of them, under a wrong reason.

## A kill inside the model stream before the tool runs (`g04-stream-*`, slice 6, 2026-11-21)

The tool section above says what it does not show: there the generation is begun, recorded and completed inside the tool, so a kill in the middle of the model stream itself (Pi's side, before any tool runs) was not measured. The `g04-stream-*` files measure it.

- **The setup.** The same controller services, the same three databases and the real Pi adapter on durable storage. The model is a scripted OpenAI-style server that streams (no network): with no tool result it calls `push` (ID `p1`), after a tool result it answers by what the result says. Pi's calls go through the production model relay (`ModelRelay`) with the production stream tap (`streamTapFor`), as in a real attempt: the tap begins the generation when the call is sent, records the tool call before Pi may see it (its arguments, then its end with the reply's finish) and completes the generation when the reply ends. The `push` tool does only what the production tool bridge does: it admits the recorded call (`admitCall`, the bridge's command ID) and runs it through the ledger. The answer after the tool result is a second model call and so a second generation, which supersedes the first (the uncrashed run ends with generation 1 `interrupted`, its call `admitted`, and generation 2 `finished`).
- **Two orders of a reply's end.** Pi stores the reply and the controller completes its generation at about the same moment, and either can come first. The production relay passes the reply's last piece on and only then completes the generation (`relay.ts`), and the bridge waits up to 3 s for a generation that is still streaming. Each run fixes one order, so its boundaries are the same every time: `recorded first` (the generation is completed before Pi stores the reply and calls the tool) and `read first` (Pi has stored the reply and called the tool before the completion begins). One file per engine and order.
- **Kills.** A real SIGKILL at each of the 18 boundaries from the first model call's `generation.begin` to the tool's answer (the begin, two records, the completion, the tool called, the admission, the claim, the target's two steps, the settlement, the answer), every boundary on every run, checked with the shared `killProblem`. The database is read before any command runs and a new process finishes the path.
- **Checked every time.** The tool slice's invariants (never pushed twice, never told "pushed" unless applied and confirmed, nothing left open, the path finished with one answer), and two more: the call is admitted in at most one generation, and no generation is left `streaming`.

| Kill at (in the run's order) | Outcome after the restart |
|---|---|
| before the begin (1) | pushed once, the model told "pushed"; Pi asks the model again |
| after the begin, through the second record (5) | the same; the cut generation is superseded by the new reply's (its call dropped or withdrawn) |
| recorded first: before or after the completion (2) | the same; Pi asks again, or presents the call again when it had stored the reply first (this differed by engine and run; the result does not) |
| recorded first: the tool called (1) | pushed once, the model told; the call presented again |
| read first: the tool called, and before the completion (2) | **nothing pushed, the model told it was not run** (the gap below) |
| read first: after the completion (1) | pushed once, the model told; the call presented again |
| the admission to the tool's answer (9, both orders) | pushed once, the model told; the call presented again and answered from the ledger |

- **The gap found (read first, 2 boundaries).** When the controller dies after Pi has stored the whole reply and before the generation is completed, the generation stays `streaming` and nothing will complete it (the relay that streamed it died with the controller; no recovery step completes a generation). After the restart Pi presents the call again, and the bridge refuses it as still streaming ("it was not run"). Nothing is pushed, nothing is wrongly reported and nothing is left open: the next model call begins a new generation, which supersedes the stuck one and withdraws its call. But the result is not the uncrashed run's: the model is told the push did not run and must decide to make it again. The sweep pins this outcome at exactly these two boundaries (`expectedResult` in `g04-stream-suite.ts`), so a fix flips them and must update the expectation.
- **Mutation checks** (built controller `generation.js`, each alone, restored byte-identical by SHA-256, SQLite files): (a) the admission looking at the oldest generation first: both sweeps fail at 5 boundaries (the cut generation's dropped or withdrawn call is found, nothing pushed); the older `g04-tool-sqlite` sweep passes with the same mutation, as it has only one generation; (b) a streaming generation not superseded by a new one: both sweeps fail ("generation 1 is left streaming"); (c) the admission accepting a call from a streaming generation: the read-first sweep fails at the two pinned boundaries (pushed once instead of the pinned outcome), so the pin is live.
- **Times** (Linux, Node 22, through `/tmp/nn-slot.sh`): about 15 s a file on SQLite, 17 s on SQLite on a worker thread, 19 s on PostgreSQL. The SQLite and PostgreSQL files are in `scripts/slow-tests.json`; the worker-thread files are heavy (`NIMBLENEWT_G04_HEAVY=1`).
