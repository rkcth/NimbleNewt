# Standby replication and recovery (card K04)

This guide is for the person who runs a NimbleNewt installation with a second PostgreSQL server (a standby). It is optional. An installation without a standby has none of this and nothing here runs.

## What is and is not covered

- **Database failover** is making the standby's database writable. NimbleNewt asks PostgreSQL to do it (`pg_promote`), and only when the standby holds everything the recovery manifest lists and the checks below pass.
- **Controller promotion** is deciding which controller may use that database, and keeping the old controller out. That is a separate step and is not done by the database failover: after a database promotion the controller's epoch and holder are exactly as they were, and no controller is authorized by it. The controller promotion (below) fences the old controller first and then names the new one. The recovery login, the recovery chat and consent are still to come (card K05). There is no automatic controller failover in the first release.
- NimbleNewt does not copy the log or speak PostgreSQL's replication protocol. The standby is set up and kept running by you, with PostgreSQL's own streaming replication; NimbleNewt only asks PostgreSQL questions (who is connected, how far behind) and asks it to promote.

## Asynchronous or synchronous

- **Asynchronous**: a commit is answered when the primary has it. If the primary is lost, the newest writes can be lost. The loss window is how far behind the standby was. `measureLag` reports it in bytes not yet on the standby's disk (lost with the primary) and bytes on disk but not yet applied (kept).
- **Synchronous**: a commit is answered only when the standby has it on disk, so a write the controller was told succeeded survives losing the primary. If the standby is down, writes wait. The controller sees such a write as uncertain and asks again by its operation ID, so it is applied once. `synchronousSettingsText` prints the server setting; you apply it, NimbleNewt never edits the server's settings.

`verifyStandbyInstallation` compares what you configured with what runs (a standby of this primary, streaming, in the configured mode) and says in words what is wrong.

## The recovery manifest

A database copy does not carry the artifact files, and a copy that lags does not carry the newest workflow state. The recovery manifest is a small folder (`manifest.json`, `aggregates.jsonl`, `blobs.jsonl`) that lists the counters, every record with its revision and every artifact file (digest and size). Write it from the primary's store, not from the standby (a manifest written from the standby only describes the standby, so it would pass against it). Write a fresh one often (after every backup is a good time) and keep it, with the artifact files, where the standby's host can reach it. The standby host needs its own copy of the artifact files; PostgreSQL does not send them.

A promotion checks only what the manifest lists. Anything written after the manifest was written is not checked, so an old manifest checks little and a manifest written from an empty store checks nothing; the result's notes give the manifest's time. The manifest's checksums show that it was not damaged or edited by accident since it was written. They are not a signature: anyone who can write the folder can write a new, consistent manifest, so keep the folder writable only by the account that runs NimbleNewt. The manifest does not record which installation it came from, so do not point a promotion at a manifest of another installation.

A promotion is refused, with the standby left as it was, when: the manifest is missing, was changed or is not in the form NimbleNewt writes; the node is not a standby; the old primary's address is left out (give it, or say that it is not known); an address has no host (it would otherwise be completed from the PostgreSQL environment variables and local defaults, which may name another server); the old primary still answers and is not itself in recovery, even if it is only read-only by default, or it is not the primary this standby copies; another standby you name answers and is not in recovery (it was already promoted); the standby has received more than it has applied and does not finish; any listed record is missing or at an older revision; the counters are behind; any listed artifact file is missing, has a different size or different bytes. There is no override. If something was removed on purpose after the manifest was written (retention, orphan clean-up), write a new manifest. An old primary that does not answer is not proof that it has stopped: the result then says so in its notes, and making sure it stays stopped is up to you (fencing comes with card K05).

The old primary and the other standbys you name are asked twice: before the checks and again just before the promotion, because the checks can take minutes. A node can still come back in the moment between that last question and the promotion, and a standby you did not name is never asked. Only fencing the old primary closes that gap. With more than one standby, name the others every time, and promote one at a time.

If the answer to the promotion request is lost, the result says the outcome is not known: the standby may have been promoted. Check the node's role before doing anything else, and do not point the controller at a different node meanwhile.

A new manifest replaces the old one in the same folder. If the machine stops during that swap, the folder holds no manifest and a promotion is refused until a new one is written. A mix of old and new files does not match the checksums and is refused the same way.

## The manifest on a schedule, and only from the primary

The controller can write the manifest itself. It does so when it is started with a manifest folder (the `recovery` start option: `manifestDirectory`, and `everyMs`, the time between writes, default 15 minutes, from one minute to one day). The dispatcher's regular rounds write it; a controller started without the dispatcher writes none. There is no entry for it in the configuration document yet.

Only the controller that holds the current epoch writes. It checks the epoch before it reads anything, again just before the new files are put in place, and once more afterwards; the snapshot the manifest is made from must carry the same epoch. A manifest never goes back: one already in the folder with a newer epoch, or the same epoch and higher counters, is kept. That also covers an old primary that is still running on its own copy of the database after a failover, where its epoch still looks current: the newer manifest in the folder stops it. The check reads the watermark from `manifest.json` even when the manifest is damaged, so a damaged newer manifest still stops an older writer. A `manifest.json` whose watermark cannot be read at all is never replaced: move it aside and the next round writes a new one. If the epoch moved while the new manifest was being put in place, the controller takes its own manifest away again (only if the file there is still its own), so the folder holds no manifest rather than an older one. The last look at the folder is taken right before the swap, and the files the swap displaces are kept aside until it is done: if another controller put a newer manifest (or one that cannot be read) in place in that moment, it is put back and this write is refused. The new `manifest.json` itself goes in only where none is: one another controller put there in the same moment is kept when it is newer (this write is refused) and replaced when it is older, and a write whose files no longer match afterwards is reported as failed, not written; a promotion refuses such a folder until the next round. Give the folder as an absolute path to the folder itself: a folder that is a symbolic link, or a manifest file in it that is a link or a folder, is refused and left as it is. Once a controller finds it is no longer the primary it never tries again until it is restarted. A store restored from an older copy meets a newer manifest in the folder the same way and stops writing; the status answer says so.

Ask in chat for the database the controller runs on (for example "is the recovery manifest up to date?"), and the answer says how often the manifest is written, when the latest was written, its epoch and counters, how many records and artifact files it lists, how many audit entries and deliveries were written since (a promotion checked against it cannot vouch for those), and why the last write did not go through, if it did not. Only the owner sees it. The answer reads `manifest.json` only; its other files are checked when a promotion or a restore report reads them.

## Promoting a controller

When the controller that used a store is given up for lost, `promoteController` hands the store to another controller. It runs against the store the new controller will use: the same SQLite file or PostgreSQL schema, or a database promoted as above. Give it the recovery manifest folder, the artifact store the new controller will use, and the holder name the new controller will be started with (the `holder` start option). That name must differ from the old controller's, or a returning old controller could not be told from the new one.

It works in this order, and stops at the first thing that fails:

1. It checks, changing nothing. Someone must have used the store before (a store nobody has used needs no promotion), and no database transfer may hold it. The manifest in the folder must be whole and written under the epoch of the controller being replaced. A manifest from an earlier epoch is stale, because the controller may have written things it does not list, and it is refused. A manifest from a later epoch than the store means the store is an older copy, and that is refused too. The store must hold every record the manifest lists, and the new controller's artifact store must hold every file.
2. It fences the old controller. It takes the epoch from the one it checked, but only if it has not moved (so a controller that started in the meantime wins, and nothing is fenced). The epoch's holder then names the promotion and the epoch it replaced. From that moment the store refuses every write of the old controller: commands, deliveries, timers, recovery manifests, and taking the store back at its old epoch. The old controller's dispatcher meets the fence at its next round, stops for good and ends the workers it runs.
3. It records the fence in the store (`controller-authority`, audited as `controller.fenced`).
4. It writes a new manifest from the store, which nobody else can change now, and checks the new controller's artifact files against it. So the decision is made on a manifest written after the fence, not one the old controller left behind. Work the old controller did after its last manifest is covered as well.
5. Only then does it name the new controller (audited as `controller.promoted`).

From then on a start on that store is refused unless it uses the name the promotion gave. A returning old controller is refused, and so is any other name. If the promotion stops after the fence (an artifact file the new controller lacks, a full disk), the store stays fenced and no controller may start, the intended one included. The record says why. Fix what it names and run the promotion again: it still knows which controller the first fence replaced, and its name, even when the stopped run recorded nothing. No option skips the fence or a check.

An old controller that is still running after the fence cannot get the store back from inside either. Moving its database, rolling a move back and restoring a backup are refused once the store's epoch is no longer the one it started with. A backup restore it staged before the fence is not swapped in either. The restore records the epoch it was prepared at, and the start that would swap it in first reads the live database's epoch. If another controller or a promotion has taken the database since, nothing is moved and the restore is recorded as failed (the start says why). The start then goes on to its own checks, which refuse the old controller. Cancel the restore, and prepare it again on the controller that now holds the database if it is still wanted. A live SQLite file that cannot be read as a controller database is still restored over, because a damaged database is what a restore is for.

A backup restore does not change who may control the store. The latest backup was usually made before the promotion, so it has no record of the promotion and still names the old controller. When the new controller restores it, the restored database takes three things from the running database: the promotion record, the holder and the epoch. It never gets an epoch lower than the running one. Everything else, the records and counters, comes from the backup. So after the restore the old controller is still refused, and the new one carries on. The audit entries of the promotion are not in the restored data (they were written after the backup), but the record they describe is. If the backup was made at a later epoch than the running database, for example another installation's backup restored into a fresh one, the backup's own record, holder and epoch are kept. If the running database holds a promotion, that backup must hold the same promotion or a later one. Otherwise the restore is refused, because it could let the controller that promotion replaced start again (for example a backup the old controller made on its own copy of the database after it restarted there). A promotion that fenced the database but stopped before its record was written counts too. To go on, restore a backup made on this database since the promotion. To use the refused backup's data anyway, restore it with a new installation that has its own new, empty data folder and database. Do not empty or replace the running one: it keeps the promotion. In the new installation the backup is restored as it is, and the running database is not changed. The new copy is a separate store that this promotion does not guard, so the controller the promotion replaced could start on it, as on any other copy of the database (see the partition item under "What is not here yet"). If the running database has no promotion record, the restored one has none either, even when the backup has one. The preview says when a promotion record is kept. If the running database's record cannot be read, the preview and the restore are refused and nothing is changed. If another promotion happens after the restore was prepared, the restore is not swapped in (see above).

### Workers stay stopped until they are reconciled

When the new controller first starts after a promotion, it holds its workers before anything runs. It writes down which attempts were still running under the old controller: the worker host, the placement, the worker sessions they were held in, their lease, and whether the worker had already sent a result. That list is kept as evidence and is not deleted when the hold ends. While the hold stands:

- No attempt starts, new or waiting, on any worker. The dispatcher's start check gives the reason.
- A result a worker sent to the old controller is not taken as new work. It stays with the attempt's placement. The attempt ends when its lease runs out, and a replacement is admitted, which starts once the hold is over.
- An offer the old controller made is not taken up. The new controller ends it as lost and admits a replacement.
- A worker that reconnects and still holds one of the listed attempts waits for your decision, even if you set reconnecting workers to take their attempts up again by themselves. Approve or stop it as for any reconnected worker ("which reconnected workers are waiting for me?", then approve or stop the one named).

A worker host is reconciled once every listed attempt on it is: the attempt ended (its lease ran out, it was stopped, or it no longer runs on a worker), or its worker took it up again in a session with the new controller after you approved it. Once every host is reconciled, the hold is released and work starts again. A worker that never comes back holds nothing for long: its attempts end when their leases run out. A restart of the new controller keeps the hold as it was, and a later start does not hold again for the same promotion. If the record of the hold cannot be read, nothing starts until that is resolved.

Ask in chat for the database the controller runs on ("are the workers still held after the promotion?"). The owner's answer says whether work is held, which hosts are not reconciled yet and which of their attempts are still open, and how many results of the old controller were kept as evidence.

Ask in chat for the database the controller runs on ("was the old controller fenced?"). The owner's answer gives the last promotion, the epoch fenced, the controller named (or why none was) and the manifest it was decided on.

## SQLite and backups

SQLite has no standby. Its recovery is the last good backup; `reportRestoredStore` compares the restored store with a manifest written before the loss and says how many audit entries, records and artifact files the backup does not have. Backups are unchanged by all of this: a backup made beside a standby restores into any backend with no standby and no manifest.

## Measuring what a failover cost

After a failover, `measureLoss` compares the writes the controller was told succeeded with what the new primary holds, and reports how many were lost and the stretch of time they cover. A write whose answer never came is uncertain, not failed: ask for it again by its operation ID on the new primary.

## What is not here yet

- Apart from the scheduled manifest, the hold on workers after a promotion, and the status lines (the manifest, the last controller promotion and the workers it holds), nothing in this guide can be reached from chat, the status page or the API yet. Card K05 still adds the recovery chat, the separate recovery login and endpoint, and the consent step. Database promotion, controller promotion, loss measurement and the restore report are building blocks until then.
- The controller promotion fences through the store. An old controller still running on its own copy of the database after a database failover (a partition) is not reached by that fence. Its recovery manifests are stopped by the newer manifest in the folder, but its own database still accepts its writes.
- The manifest folder is a start option, not yet an entry in the configuration document, and copying the folder and the artifact files to the standby host is still yours to arrange.
- There is no automatic failover. Nothing promotes a standby by itself.
- It has been tested with both servers on one machine, talking over the local loopback address. A standby on another host, a slow or broken network (including one that is neither up nor down), separate clocks, TLS and connection poolers have not been tested.
