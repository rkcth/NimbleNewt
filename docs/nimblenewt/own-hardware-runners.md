# Running checks on the owner's own machines

Some checks only mean something on real hardware: the OS sandbox and containment checks (cards A03, A04, G05), the real-OS parts of the QA checkpoints and the final qualification (D04). GitHub's hosted runners are virtual machines without the owner's OS builds, permission settings or sandbox features. This page describes the way the project can run checks on the owner's Mac and Windows machines: **self-hosted GitHub Actions runners**, started by hand. Status: **not set up yet.** The runner workflow ([own-hardware.yml](../../.github/workflows/own-hardware.yml)) is a probe; it does not contain sandbox checks yet. The other route, used for the earlier Windows research, is SSH with a dedicated key the owner names for the purpose.

## The risk, stated plainly

The repository is public, and a runner executes whatever a workflow tells it to, on a personal machine. GitHub advises against self-hosted runners on public repositories for this reason.

- **The guards in `own-hardware.yml` (manual start, `main` only, this repository only) protect only that file.** A pull request from a fork can edit *any* workflow file, such as `ci.yml`, to say `runs-on: [self-hosted, nimblenewt-mac]`, and the run uses the edited file. If that run is approved or not blocked, the fork's code runs on the owner's machine with the runner account's access.
- Therefore: in the repository settings (Settings, Actions, General, "Fork pull request workflows from outside collaborators") choose **Require approval for all outside collaborators**, and **never approve a run from a fork pull request without reading its diff, especially anything under `.github/workflows/`**. Where a pull request is not needed, consider turning fork pull request workflows off altogether.
- **Keep the runner offline unless a run is wanted** (the owner chose on 2026-10-22 to keep the runners on while development is active; see the note at the end, and the two settings above and below then matter more: the fork pull request approval setting and a protected `main`; the owner should confirm both are on, since the project's token cannot read them). Do not install it as an always-on service. Start it by hand (`./run.sh` on the Mac, `run.cmd` on Windows) for an "Own hardware" run and stop it afterwards, or register it with `--ephemeral` so that it accepts one job and then unregisters itself.
- **Whoever can push to `main` can run code on the runner.** Protect `main` (Settings, Branches): require a pull request or restrict who can push, and keep pushes to the reviewed-commit path (the project pushes with a single dedicated deploy key, only after an AI review approves the change).
- A **dedicated, non-administrator account** for the runner is the stronger setup, because then the code can read nothing of the owner's (SSH keys, browser profiles, documents). It is a recommendation, not a requirement: if the owner prefers to run it under their own account, the controls above are what stand between a mistake and their files, so they matter more, and the runner folder should still sit outside the profile folders that hold personal data.
- The runner registration token is a secret that lasts one hour. Do not paste it anywhere, including into a chat with an AI session.

## Setting up a runner (each machine)

1. Install Node 22 and Git on the machine, as for a normal checkout. On Windows, Git for Windows must be installed (the default folder `C:\Program Files\Git`, or anywhere if its `git.exe` is on the PATH of the runner's account). The workflow's `bash` steps must run under **Git Bash**, not the `bash.exe` in `C:\Windows\System32`: that one is the WSL launcher, and with it the runner's script path loses its backslashes (`/bin/bash: C:actions-runner_work_temp...sh: No such file or directory`) and no test starts (this happened in run 44453704944). Each Windows job therefore starts with a step, "Use Git Bash for bash steps", that finds Git for Windows' `bin\bash.exe` and puts that folder first on the PATH for the rest of the job; it fails with a clear message if Git Bash is missing. (A `shell:` line that names `C:\Program Files\Git\bin\bash.exe` directly does not work, because the runner splits that line at its first space.) An optional extra, not needed with that step: put `C:\Program Files\Git\bin` ahead of `C:\Windows\System32` in the PATH of the runner service (or of the account that starts `run.cmd`), so that a plain `bash` there is Git Bash too.
2. Decide on the account (see above) and the work folder, which the account owns. Install the runner outside the owner's own profile (a dedicated account's folder, never under the owner's home), and remember that the artifacts a job uploads are public on a public repository: the Windows Sandbox job uploads only a summary and a redacted failure detail, and anything a future job uploads must be checked the same way.
3. In GitHub: the repository, Settings, Actions, Runners, **New self-hosted runner**. Choose the machine's operating system and architecture. GitHub shows the download commands and a `config` command that contains the one-hour token.
4. Run the download commands in that folder. Run `config` as shown, adding the label for the machine: `--labels nimblenewt-mac` (or `nimblenewt-windows`, `nimblenewt-linux`) and, if wanted, `--ephemeral`. Accept the other defaults.
5. Start it by hand (`./run.sh` or `run.cmd`). In Settings, Actions, Runners, it should show as **Idle**. A sandbox check that needs a signed-in desktop (Windows Sandbox did, in the earlier research) needs the runner started in an interactive session with the owner present, which is what a hand start gives.
6. **The Windows Sandbox job (`Windows Sandbox (real)` in **Own hardware**) should have the runner started interactively with `run.cmd`, by the account signed in at the console**: open a command prompt on the console desktop as that user and run `run.cmd` there. Do not run it as a service (`svc.cmd`, or "run as service" during `config`), from a remote desktop session, or as another account. With the dedicated runner account recommended above, that account is the one signed in at the console for this job. Run 44501483353 got "Access is denied" from `wsb start` (`0x80070005 (E_ACCESSDENIED)`, exit 2147942405). Its cause is not known: the job log shows the runner ran under the owner's own account (its home folder was the owner's profile), and the shared folders were granted to the console user without error, but whether the runner ran as a service, and what else differed from the research, was not recorded. Running as a service is not refused as such: the research of 2026-10-16 started Windows Sandbox from SYSTEM in session 0 while the owner was signed in, and saw the same error from a mapped output folder the sandbox could not use. So an access-denied start is reported with two facts about the process (in the active console session; the console user) and, unless both are yes, "start the runner interactively with run.cmd as the console user (not as a service)", followed by the shared-folder cause. The lines after that reason list every mapped folder (guest path, host path, read-only or writable) with its access list read back by `icacls` while the job's grants are still in place, and the real-sandbox test's redacted detail keeps the last 40 host calls with their arguments (the exact `.wsb` configuration and the account each grant names). The real-sandbox summary records the same facts as "runner in the active console session" and "runner is the console user". None of this has run on Windows yet. Run 44607130723 (runner elevated and interactive) passed the client checks and then `wsb.exe list --raw` timed out inside the job (a gRPC timeout to localhost, then Cancelled), though it answers when run by hand. Every `wsb list` now goes through one function (`windows-list.ts`): a first call of 120 s and at most two retries of 60 s; when none answers, the health reason (and the redacted detail) has one line with each call's outcome and duration, the Windows Sandbox server processes (id and start time) before and after, and which proxy, profile, temporary-folder, session and GRPC_* environment variables are present (names only, never values). A list that does not answer still means no capacity: no sandbox starts.

## Using it

With the runner idle: Actions tab, **Own hardware**, **Run workflow**, branch `main`. The probe checks out the repository, installs from the lockfile, records the machine (OS, architecture, Node) and runs the test suite once. The result is in the job summary and in the `own-hardware-*` artifact. Then stop the runner.

**Leftover Windows Sandbox test folders.** The real Windows Sandbox tests work in `%ProgramData%\nn-wsb-real-XXXXXX` and `%ProgramData%\nn-wsb-host-XXXXXX`. Each run records the folder it makes in the runner account's own `%LOCALAPPDATA%\NimbleNewt\wsb-records` (one small `.json` per folder; it stays between jobs, unlike the runner's temporary folder) and puts the same random token in the folder's `.nn-wsb-token`. The job's step "Release leftovers of the Sandbox runs" (`scripts/wsb-cleanup.mjs`) stops the leftover sandboxes, restores the saved access lists and removes only folders it has a matching record for, owned by the same account. A folder with the name but no matching record (one made before records existed, one whose run stopped between making the folder and writing its record, or one another account made) is left alone, and the job summary's cleanup line counts it as "not recorded or not trusted and left alone". The step's own file `wsb-cleanup.txt` names each one, but it is under the job's temporary folder, which the runner empties when the job ends. To deal with them by hand: list them with `dir /q %ProgramData%\nn-wsb-*` (the `/q` column shows each folder's owner); leave alone any folder whose owner is not the runner's account; for one that is the runner's, close any Windows Sandbox window still open, then for each `control*\jobs\<job>\acl.json` in it run `icacls "<parent>" /restore "<file>"` for each entry it lists (the restore the cleanup does), and finally delete the folder and its record, if any, in `%LOCALAPPDATA%\NimbleNewt\wsb-records`.

## Taking a runner away

Settings, Actions, Runners, the runner, **Remove** (or `./config.sh remove` with a removal token). Then delete its folder, and the account if one was made for it.

2026-10-22: the owner has the runners on for now (not started by hand for each run) and will switch them off when active development stops. Only `own-hardware.yml` targets them and it starts by hand from `main`; no other workflow uses a self-hosted label (checked 2026-10-22). Keep it that way: a workflow that names `self-hosted` in a pull request could run on the owner's machine, so a new workflow must not use the runner labels without the owner's approval.

## Collecting the Y02 checkpoint evidence (card Y02)

On each machine (a checkout of the commit being judged, clean, built) run `node scripts/y02-checkpoint.mjs run --out DIR`. It builds, runs the scenario set named in `scripts/y02-scenarios.json` with the sandbox required, and writes `DIR/y02-scenarios-<platform>.json`. Also run `node scripts/containment-evidence.mjs run --out DIR` (card G05) and `node scripts/qa.mjs --runs=5`, and copy the QA record to `DIR/qa-evidence-<platform>.json`. Gather the three platforms' files in one folder, add `ci-runs.json` (the run ids of the exhaustive and QA workflows per platform; format in the implementation notes) and read the evidence. Then `node scripts/y02-checkpoint.mjs digest --dir DIR --platform P` prints the digest that your sign-off (or recorded waiver) for platform P quotes in `y02-signoff.json`; any later change to that platform's files makes the digest differ and the sign-off stops counting. `node scripts/y02-checkpoint.mjs gate --dir DIR --commit SHA --out verdict.json` names every blocker and writes a deterministic verdict. The gate uses no network; it proves the files are consistent and bound to the commit, not that the runs happened.

On Windows set `NIMBLENEWT_REAL_WINDOWS_SANDBOX=1` before `run`, or the real Windows Sandbox tests skip and their scenario fails. A test that skips only because it does not apply on that OS (for example "Linux only") is counted as not applicable when `scripts/y02-scenarios.json` names its exact reason for that platform; it never counts as a pass, and any other skip fails the scenario. A scenario whose only problem is skipped tests is run up to three times, and the report records the attempts. If the CPU-pacing test still says the host gave its busy loops too little CPU, close other work and run again on a quiet machine. The macOS and Windows reasons were read from the test sources and have not yet been run: if a first run there shows a skip the map does not name, check that the test really does not apply on that OS before adding its reason.
