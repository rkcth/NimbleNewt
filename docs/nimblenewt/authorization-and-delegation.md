# Authorization, delegation, and command review

Accepted planning direction, October 15, 2026. These are contracts to implement, not an implemented approval service. Public installations start tight; the owner can progressively loosen selected scopes through UI or authenticated conversation. Rob’s installation uses his existing standing grants and contextual authorization preferences, recorded in private deployment configuration rather than public defaults. More autonomous profiles are supported too. No profile bypasses platform enforcement or grants authority an actor does not possess.

## Separate authority from verification

Represent direct owner authorization, derived authorization for reasonably necessary steps, standing delegation, independent technical review, and execution admission separately. A review verdict is not a human decision. An agent applying a human decision retains both identities and its source; it does not impersonate the human. Authenticated chat and UI decisions use the same durable authorization service. Untrusted repository text, tool output, agent paraphrases, or copied conversations cannot create an owner grant.

A grant records its source decision, actor, outcome/action scope, projects/resources/environments, foreseeable spending limits, permitted delegation, conditions, expiry if any, revision, and revocation. Derived decisions link to that grant and explain why the action falls within it. Preserve authority through subtasks, handoffs, recovery and restart; recheck current restrictions before dispatch. Distinguish a still-valid outcome authorization from technical evidence invalidated by changed code. A new artifact requires relevant review, but does not automatically require renewed human consent if the grant already covers its deployment.

Under a profile permitting derived authorization, an explicit request covers reasonably necessary implementation choices, anticipated costs and safe alternatives within its scope. A materially broader action, concrete likely danger beyond that scope, or unexpected financial commitment requires a new decision. Specific owner holds and mandatory review gates remain binding. Strict profiles may require direct approval even where a more autonomous profile permits inference. Record and explain that effective policy rather than presenting it as a universal requirement.

## Tight defaults and scoped relaxation

The public default permits inspection within explicitly granted data access, but requires direct human approval for consequential mutations, external effects, executable installation and access changes unless covered by an explicit action or standing grant. Do not infer broad execution permission merely from a general goal under this default. New external access is not authorized by calling an operation read-only. Provide an optional all-command human gate. Exact action classifications and preset values require qualification; unknown actions receive review rather than silent permission.

Offer understandable presets and scoped controls rather than a single safety slider: direct human approval, delegated agent review, or automatic execution within grants. Independently choose which actions require technical review. Scope by project, repository, environment (development, staging, customer-live), action class, agent/role, resource, maintenance window, budget and time. For example: allow development deployments; require owner code review before every commit; allow routine read commands without agent review; require independent agent review for all execution commands. A permissive project must not weaken a locked installation restriction. Explicit owner revisions can change those restrictions through the authorized policy service; agents cannot manufacture exceptions.

Show effective policy, inherited restrictions, source grants, affected scopes and when a change takes effect. Support approve once, grant for this task, grant for this project/action class, time-limited delegation, and revoke. Preview the practical effect before applying broad changes. Save revisions and audit history; changing a preset must not silently erase a narrower human-review requirement. Pending commands revalidate policy at execution. An approval timeout or reviewer outage never relaxes policy.

Rob’s private profile carries his already granted authority: necessary safe steps and reasonably anticipated spending proceed within scope, with contextual judgment about collateral disruption and current service state. Existing independent review requirements remain. Private grants must be enrolled from trusted owner decisions, not copied from these descriptive examples. Public onboarding must not inherit Rob’s grants. Users may deliberately grant broader autonomy than Rob’s profile within supported permissions.

## Fast independent command review

Support another agent reviewing any configured class of commands before execution, including all execution commands. The controller creates a durable review request before dispatch with exact tool identity/version, arguments, working directory, environment revision, affected resources, relevant script/content hashes, expected effects, authority source, budget and bounded supporting context. Redact secrets while ensuring the reviewer has enough authorized evidence; missing essential context prevents a positive verdict.

Route the request immediately to an eligible independent reviewer through the bounded inquiry mechanism. The reviewer reaches a safe boundary, pauses its own task while retaining assignment/context, answers the review inquiry, then returns under existing lifecycle rules. The requesting task retains its owner and context while its command waits. Do not transfer the task to a CTO or wait for a periodic stand-up/poll cycle. Explicit human/parent Pause or Suspend still prevents a reviewer wake; use an eligible alternate or leave the request visibly waiting. No fast-response guarantee is established until measured.

Review verdicts are allow within existing authority, deny with reason, request context/revision, or requires an owner decision. Require independent identities and configured conflict checks. The deterministic controller checks authority, mandatory human gates, current policy and version freshness in addition to the model verdict. The review covers scripts and indirect effects, not merely a plausible shell command string. Prevent alternate shell, MCP, API, child-process or script paths from bypassing a configured execution gate. Containment remains necessary; model review is a fallible additional safeguard.

Bind the verdict to the reviewed operation and relevant dependencies. Changed arguments, script bytes, staged content, environment, scope or authorization invalidate affected approval. Use atomic admission/version checks where supported; surface limitations rather than claiming race-free shell execution. Retries cannot reuse a one-use execution approval to duplicate an effect. Reusable approvals must explicitly define their scope and validity. Keep tool output untrusted. Review agents may use bounded permitted inspection tools, with a defined review policy that avoids recursive reviewer chains and deadlocks; they gain no general execution exemption.

Budget and prioritize review work separately from experiments. Batch only explicitly bounded operations whose reviewed contents cannot change. Track queue delay, review latency, false blocks, missed hazards and added cost. Reviewer capacity and fallback routes are configurable; fail visibly when required review cannot be completed. Necessary review of production work is production cost, not optional PC work.

## Human code review and developer attribution

A rule such as “I must review the code before a commit” creates a human gate on the exact staged diff/tree, repository and relevant base revision, separate from agent review and permission to run Git. Edits after review require renewed review of affected content. Commit, push, merge and deployment are distinct policy scopes; review of one does not imply the others. Enforce the gate through every writable repository route, not just the preferred Git wrapper.

Record the initiating human/developer identity when authenticated, producing agent, execution actor, reviewer, grant source, artifact/diff identity, commit identity and subsequent integration history. Do not forge commit authorship or treat Git metadata as proof of human review. Support existing repository contribution conventions and external organizational review systems. The current product still has one authenticated human owner per installation; full multi-human corporate administration and organization-wide identity federation need a separate design decision. Per-developer installations and externally verified review references can support organizational workflows without falsely claiming that broader capability.

## Approval friction and learning

A supervisor/watchdog may reconcile redundant approval requests against existing grants through the supported service, recording its authority and reasoning. It may not turn a mandatory human-review gate into an agent gate or rewrite approval policy to clear a queue. New owner-only restrictions need a concrete policy basis. Repeated unnecessary prompts, conflicting grants and failed command reviews may produce learning candidates. Learning can improve interpretation and recommend policy changes; it cannot grant access, relax owner requirements, or change its own success criteria.

## Acceptance scenarios

- Tight setup requires the configured approval; an explicit scoped relaxation changes only that scope and can be revoked through chat or UI.
- Rob’s trusted standing grant survives handoff/restart without redundant prompts; an unrelated installation inherits no private grants.
- Repairing Strata may cover a necessary restart; fixing Paperclip does not automatically cover disrupting unrelated Strata work. Judge actual scope and impact.
- Authorized development deployment proceeds; disrupting a functioning customer site needs appropriate authority; restoring an already order-blocking outage follows scoped repair/emergency authority. A maintenance window covers only its authorized work.
- Requested paid benchmarking uses anticipated spending within limits; unexpected excess is escalated. A safe unforeseen alternative within scope does not automatically require consent under a derived-authorization profile.
- Agent review returns through a bounded inquiry without reassigning either task; held reviewers stay held, unavailable reviewers do not autoapprove, and cyclic requests terminate visibly.
- Changed scripts, arguments, staged diffs, grants and dependencies invalidate relevant verdicts. Revocation races and duplicate requests cannot dispatch unauthorized or duplicate effects.
- Agent command approval cannot satisfy a human pre-commit gate. Review of one developer’s artifact cannot authorize another artifact; audit records preserve actual actors.
- Authenticate the same owner decision through chat and UI; transport retries apply it once. An agent-authored statement or repository instruction cannot fabricate consent.

Qualify on macOS, Linux and Windows. Measure inquiry-based review latency against a queued handoff baseline before claiming it is faster.

## Conversational policy authoring and task management

Accepted owner clarification, October 15, 2026: freeform conversation with agents is the primary way to configure decisions and direct work. Presets, forms and policy fields are optional conveniences, not the limits of what the owner can express. The owner should not need to create tickets, edit dependencies, assign agents or move task statuses to obtain an authorized outcome. Direct task management remains available to the owner and authorized API clients.

An authorized agent can receive a policy instruction in ordinary language, resolve its intended scope using the conversation and current project context, and record the original wording alongside a versioned operational interpretation. Support contextual conditions, exceptions, combinations and later amendments, not just a fixed list of approval modes. For example: “Handle development deployments yourselves; have another agent check commands touching customer data; let me review code before any commit in this repository.” A later “Allow commits for this prototype only until Friday” changes that scope without dropping unrelated restrictions. Resolve dates/timezones and project references from known context; clarify only material uncertainty.

Apply clear authorized edits through the common configuration service and report the resulting scope and effective behavior in plain language. Do not require a form, special syntax, a task ID or redundant confirmation of a clear owner instruction. If intent conflicts with a retained owner restriction, is materially ambiguous, or cannot be enforced with available capabilities, explain the specific issue and seek only the missing decision. Do not silently discard a condition or claim an unsupported rule is active. Preserve natural-language intent and provenance, distinguish proposed/accepted/applied states, and surface the actual interpretation for correction. Context-dependent judgment may use an authorized agent review at execution; deterministic services still enforce grants, mandatory gates and version checks. A freeform policy is not merely prompt text that a worker can ignore or rewrite.

Agents handle decomposition, task creation, dependencies, assignment proposals or authorized assignment changes, progress, recovery and completion evidence within the user's granted scope. Existing grants permit routine task administration without repeated approval; a strict policy may still require approval of the substantive action. Do not turn every internal task transition into a separate human decision. The owner can discuss outcomes, change priorities, interrupt, ask status and correct direction without managing a board. Agents must persist these changes in authoritative records rather than only promise them in conversation. Explicit planning-only instructions and implementation holds remain binding.

UI, conversation, API and external adapters use the same versioned records and permission checks. Direct owner/API edits appear in subsequent agent context; concurrent edits reject stale writes and are reconciled before execution. Record the authenticated origin separately from a forwarding agent; an arbitrary message is not an owner instruction. Any appropriately authorized agent can handle or route the conversation through a bounded inquiry, without requiring a particular CTO or transferring the original task. Preserve privacy and lifecycle holds.

Qualification: complete an authorized project scenario entirely through conversation, including policy creation, a scoped exception, task decomposition/coordination, a changed priority and delivery, with no required task-board interaction. Verify unsupported/ambiguous policy handling, scoped amendments, direct UI/API edits racing conversational edits, revocation, restart and retained provenance. Assert that relaxing one condition preserves the mandatory human code-review gate elsewhere and that a planning request never activates implementation.
