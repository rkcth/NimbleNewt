# Release installation and maintenance windows

Public NimbleNewt can install an authorized released version during a configured maintenance window using a separately controlled updater. Developing NimbleNewt source and producing candidate builds is an optional deployment-specific workflow, described in [Our NimbleNewt development deployment](development-workflow.md); normal users do not need it. A candidate that cannot start or pass activation checks automatically returns to the previous known-good release. This is a design proposal, not an implemented updater or a guarantee that every failure can be repaired by switching binaries.

## Keep development separate from activation

The public installation consumes a verified release artifact from an explicitly trusted source. It does not need to build NimbleNewt or let its agents modify NimbleNewt source. In our development deployment, a separate authorized pipeline turns reviewed agent patches into candidate artifacts. Neither path edits the running installation. Version the code, dependencies, adapter mappings, configuration schema, and data migrations together. Require independent review and the existing platform, recovery, and compatibility checks for affected behavior.

A scoped release-management permission can schedule an exact reviewed artifact under the user's policy; it is distinct from `toolbox.manage` and ordinary coding access. A standing maintenance policy can authorize routine updates without asking the user every time. Changes outside that policy need the appropriate decision-maker's approval. Bind authorization to the artifact digest, migration plan, and target installations, not a branch name or mutable download URL. Verify both artifact integrity and authorized publisher provenance; a matching hash alone does not establish who authorized the artifact. Signing/trust-store implementation remains to be chosen. Retest/review a changed artifact rather than activating whatever happens to be latest when the window opens.

## Recovery must work without NimbleNewt or a model

Use a small deterministic launcher/updater outside the NimbleNewt controller and agent workers. It maintains separate current and candidate release directories, a durable update journal, and the last known-good version. It can start, stop, check, and revert releases even if NimbleNewt cannot import its code or start its UI. Do not overwrite executable files belonging to a running release.

Protect the updater, artifact verification, health-check policy, and release authorization from ordinary agent writes. Give it only the narrow host permissions its job requires, not an arbitrary command interface available to agents. Updating this recovery component is a separate administrative procedure; a routine NimbleNewt release cannot replace its own recovery mechanism. Keep a local recovery/status path available when the main UI is down.

Implement launcher/service and filesystem operations for macOS, Linux, and Windows. A durable active-release record must resolve to either the previous release or the candidate after interruption, never an installation assembled from parts of both. Verify the actual platform behavior rather than assuming one shell command or symlink swap works everywhere.

### The release launcher program (built as a program and a library, card K02a; service units below)

`scripts/nimblenewt-launcher.mjs --root RELEASE_ROOT [--entry controller.js] [--switcher pointer|symlink] [-- controller arguments]` runs the controller of the release the pointer names, as a child process with `NIMBLENEWT_RUNNING_RELEASE=<release id>` in its environment. It is separate from the release-update tooling that stages releases; it is not part of any release. It reads only the pointer, the release directory and `launcher-state.json`; it never opens the database, so it runs when the database cannot. Its decisions are the existing ones (`Launcher.prepare()`, `watch()`); the supervisor library (`packages/controller/src/release/supervisor.ts`) adds the process handling:

- A start the controller never confirms inside the startup window is stopped (SIGTERM to the child's process group, SIGKILL after `--grace-seconds`, default 10) and the launcher falls back to the last known good. The last known good is never quarantined.
- One launcher per release root: it holds a lock the operating system frees when it ends, and the controller inherits it (POSIX), so a launcher killed outright whose controller runs on does not let a second launcher start a second controller (the second exits 5 until that controller is gone).
- Signals go to the controller's process group only, and only while that group still has a member (a group ID cannot be reused while it has one). What a controller that crashed left running in its group (a database it started, say) is stopped before the next start.
- The controller's exit code: 0 after its start was confirmed is a stop on purpose (the launcher exits 0 and starts nothing); 0 before that is a failed start; 75 asks for a restart; anything else is a crash.
- A controller that exits otherwise is started again through the same decision (an unconfirmed start is judged failed there). Restarts slow down: the n-th short run in a row waits `initial * 2^(n-1)` ms up to a maximum; a run of `--stable-seconds` (default 60) resets the count; after `--give-up-after` (default 20) short runs in a row the launcher writes an Urgent notice for the owner (told at the next start that can deliver it) and exits 4.
- Stopping the launcher before the controller confirmed its start records the start as interrupted, not failed: it runs again with a full window next time (a reboot during a first, slow start does not block the installation). A launcher that loses power or is killed outright cannot record this, and its unconfirmed start is judged failed at the next launch, as before.
- The window is measured on a clock that does not jump, so a wall clock set while a release starts neither fails a healthy start nor stretches the window.
- Exit codes: 0 stopped (SIGTERM, SIGINT or SIGHUP, repeated signals included; or the controller stopped on purpose), 1 usage or unexpected error, 2 blocked (nothing safe to run; the owner decides), 3 no release is active, 4 crash loop, 5 the release root is held by another launcher or by a controller a killed launcher left running. A service manager should not restart it on 0, 2, 3 or 4 (nothing changes until the owner acts; a crash loop was already slowed 20 times) and may restart it on 1 and 5 after a delay.
- Liveness heartbeat (on by default; `--heartbeat off` turns it off): each controller start gets a private file under `<root>/run` (directory 0700, file 0600, a random per-start name and token) and beats into it from a timer, so the file only moves while its event loop turns. Once the start is confirmed (the last known good at once), a counter that stands still for `--heartbeat-stale-seconds` (default 120, at least 30, never below 6 beats of `--heartbeat-interval-seconds`, default 5) means hung: the controller is stopped with the same SIGTERM, then SIGKILL ladder, the owner is told ("stopped responding and the launcher restarted it"), and the same release starts again. A hang never sets a release aside or changes the last known good; it counts as a short run, so a controller that keeps hanging ends in exit 4 like a crash loop. A pause of the launcher, a sleep of the machine or a clock jump starts the count again instead of judging; a heartbeat file that cannot be read is never a hang; a release without a heartbeat (older) is left alone unless `--heartbeat-first-beat-seconds` (at least 300 and at least the stale limit) says a first beat must come. On a full disk the controller overwrites its record in place, so it is not taken for hung. A clean stop keeps beating until it is done.
- Known gap: a controller whose event loop turns but whose work is stuck (a deadlocked wait, a wedged worker thread) is not found by the heartbeat.
- Logs (stderr) name release IDs, process IDs, exit codes, signals and the launcher's own reasons; never the environment or the controller's output.

Not built: running the launcher on a real macOS or Windows machine (the process-group stop is POSIX; Windows uses `taskkill /T /F` on the child's tree, then `child.kill()`, and the controller does not inherit the lock there), and the updater's activation of a release the controller never staged (below).

### Service units (generated, never installed by NimbleNewt)

`node scripts/nimblenewt-service.mjs print --platform linux|darwin|win32 --root RELEASE_ROOT [--environment-file FILE] [--log-dir DIR] [--name NAME] [-- controller arguments]` PRINTS a service unit for the launcher and the exact steps to install it. It writes no file and installs, enables and starts nothing; you read the unit and run the steps yourself (`--unit-only` prints just the unit text). The generator is `packages/controller/src/release/service-units.ts`.

- **Linux:** a systemd USER unit (`~/.config/systemd/user/<name>.service`, `systemctl --user`). **macOS:** a launchd LaunchAgent (`~/Library/LaunchAgents/local.<name>.plist`, `launchctl bootstrap gui/$(id -u)`). **Windows:** a Task Scheduler task registered for the logged-on user with ordinary rights (`Register-ScheduledTask -Xml`); it is a task, not a Windows service. `--windows-user DOMAIN\user` is required: a logon trigger without a user fires at every user's logon and needs an administrator to register.
- **Runs as you, never as root.** No `User=`, no `UserName`, no elevated run level; the printer refuses to run as root.
- **No secrets in a unit.** The environment comes from a file you keep (`EnvironmentFile=` on systemd; `node --env-file=FILE` in the launchd and Windows commands, which have no such setting); only its path is written. Controller arguments that look like a credential (`--token=...`, an `sk-` key, an address with a password) are refused. The step list sets the file to mode 600.
- **Restart policy follows the launcher's exit codes** (`SERVICE_RESTART`, derived from `SUPERVISOR_EXIT`; a test fails if they drift): systemd uses `Restart=on-failure` with `RestartPreventExitStatus=2 3 4` (0 stopped on purpose, 2 blocked, 3 no release, 4 crash loop stay down until you act; 1 usage or unexpected error and 5 second launcher are restarted after 30 s, at most 5 starts in 10 minutes). launchd (`KeepAlive` with `SuccessfulExit` false, 60 s throttle) and Task Scheduler (3 restarts, 1 minute apart) cannot tell codes apart: they leave an exit 0 alone and retry any other failure within those bounds.
- **systemd hardening:** `NoNewPrivileges`, `RestrictSUIDSGID`, `RestrictRealtime`, `LockPersonality`, `UMask=0077`, and `KillMode=mixed` so the launcher stops its controller in order (what is left in the unit after the launcher exits, including a controller orphaned by a launcher crash, is killed). No `PrivateTmp`, `ProtectSystem`, `ProtectHome` or other file-system namespacing by default: in a user unit they make systemd put the service in its own user namespace, and where unprivileged user namespaces are restricted (Ubuntu 23.10 and later, AppArmor's `unprivileged_userns` profile) bubblewrap cannot create one inside it, so the controller's sandbox fails (measured with `systemd-run --user`: the bubblewrap health probe is healthy without them and fails with either). `RestrictNamespaces`, `SystemCallFilter` and `MemoryDenyWriteExecute` are never set (the sandbox needs namespaces, Node's JIT needs writable code). `--protect-system full|strict` (with `--read-write-path` directories writable under `strict`) is an opt-in for systems without that restriction; check that the sandbox still starts.
- **Strict inputs.** Every path must be absolute and already normalised (no `.`, `..`, doubled or trailing separators), and no value may hold a control character, a line break or a Unicode line separator. Values are then escaped for the format they land in (XML in the plist and the task, the systemd command-line quoting that also doubles `%` and `$`, the Windows command-line rules), and shell steps quote with single quotes. The few systemd paths that sit unquoted in a directive (environment file, log directory, read-write paths) must be plain (no spaces, quotes, backslashes or `$`). On Windows `< > : " | ? * %` are refused.
- **Logs:** systemd appends to `<log-dir>/<name>.log` (or the journal), launchd to the same file; rotate it yourself. Task Scheduler keeps no output; use the launcher's own records.

### The updater (a library and a program; it stages and announces, it does not activate)

`node scripts/nimblenewt-updater.mjs stage --root RELEASE_ROOT --source DIR --digest SHA256 [--announce [--switch]]` installs a release that is already built and authorised, from a source directory on this machine (the layout `release.stage` leaves: the files plus `MANIFEST.json`). No network, database or model is used. The library is `packages/controller/src/release/updater.ts` (`stageRelease`, `announceRelease`, `installRelease`).

- The caller names the manifest's digest out of band, from whoever authorised the release; a different manifest is refused. The source is checked before anything is copied: plain directory and manifest (links refused), safe file names (the `release.stage` rules, including that no file may be named for the launcher or the updater), and `verifyReleaseDirectory` finds every listed file with the right size and digest and nothing else (an unmanifested file, a link or a special file is refused).
- It copies the listed files without following links, hashing as it goes, into `releases/.tmp-<id>-...`, writes the manifest bytes, verifies the copy again, makes it read-only and moves it into place with one rename. Until the rename there is no `releases/<id>`, so a crash leaves nothing the launcher could run; the next run sweeps the leftover once it is older than an hour.
- It never overwrites. An existing `releases/<id>` that verifies against the same digest counts as already installed (so a repeat after a crash goes on to announce); any other is refused and left alone.
- `--announce` calls the launcher's own `Launcher.expect` (the release and its manifest digest, with the worker protocol range from `compat.json`), after verifying the installed directory again. `--switch` also writes the pointer. Without it the pointer is unchanged. A running launcher keeps its controller until that exits or restarts, then follows the pointer.
- Limits: this does not run the maintenance sequence (quiesce, checkpoint, quarantined activation, verification, revert), does not touch the controller's activation record or approvals (so a pointer moved with `--switch` shows as `diverged` in `release.status` until the controller activates a release itself; the launcher runs the new release normally, but the record's "current" and "previous" still describe the old one, so `release.rollback` goes back from the old one, and a `release.activate` interrupted before its pointer write is left `unresolved` for you instead of being resolved automatically; the program prints this warning), and does not fetch or check where the source came from. Use the controller's `release.stage` / `release.activate` when the controller is running; use this program where it is not.
#### The controller entry the launcher runs (`scripts/nimblenewt-controller.mjs`)

A release's `controller.js` is meant to run this entry. **No release builder exists yet**: nothing turns this tree into a release, and a release today holds at most 100 named files (`RELEASE_LIMITS.artifacts`), far fewer than `scripts/` plus the built packages and their dependencies, so a release cannot yet carry the program it runs. What works now (and what the tests do) is a one-line `controller.js` that imports `main` from an installed checkout's entry by absolute path and sets `process.exitCode = await main(process.argv.slice(2))`. With that, the release's digest covers only the one line: activating or rolling back such a release changes nothing about the code that runs (that is the checkout's), so it is fit for trials, not for real updates. Packaging releases (the builder, a larger or archive-based artifact set) is a separate card. By hand: `node scripts/nimblenewt-controller.mjs --data DIR`.

- It reads the configuration `nimblenewt init` wrote (`DIR/nimblenewt.config.json`, or `--config FILE`; it never writes a starter one), starts the controller with the same `launch` as `nimblenewt.mjs start` (worker host included when the owner turned it on), opens no chat and runs until told to stop (SIGTERM, SIGINT, SIGHUP): it closes the controller, then exits 0. Options: `--data`/`NIMBLENEWT_DATA`, `--config`, `--serve`, `--allow-unsupported-environment`, `--local-host-environments` (below), `--release-root`, `--release-switcher`; `--help`. An unknown option, an option given twice, an abbreviation and a missing value are errors (exit 1). `~` is not expanded by the entry (only by a shell, and not in the `--data=~/x` form).
- **Which release it is.** The launcher puts `NIMBLENEWT_RUNNING_RELEASE=<id>` (and, since this entry, `NIMBLENEWT_RELEASE_ROOT` and `NIMBLENEWT_RELEASE_SWITCHER`, so both programs use the same root and pointer kind; the controller's own default pointer kind differs from the launcher's) in the child's environment. The entry maps them to `StartOptions.releases` (`root`, `switcher`, `runningRelease`). `NIMBLENEWT_RUNNING_RELEASE` without a release root is a start error (a start that could never be confirmed). Under the launcher (with `NIMBLENEWT_RUNNING_RELEASE`) the process runs in the release directory, so a relative `--data`, `NIMBLENEWT_DATA`, `--config`, release root or configuration `installation.dataDir` is refused (it would name a folder inside the release: a new, empty installation for each release), and a `--release-root` or `--release-switcher` passed after the launcher's `--` must match what the launcher set. With only a release root (by hand) release staging and activation are on and this process is no release's controller. With neither, no release wiring.
- **Confirmation.** `startController` confirms the start itself (the last known good release) when the activation record names the running release as current; the entry then logs `start confirmed: <id> is the last known good release` only when the launcher's record shows this start (the open start attempt) confirmed, the same test the launcher makes before it takes an exit 0 as a stop on purpose, or `start NOT confirmed ...` otherwise (unless the owner confirms the release, the launcher will count that start as failed).
- **Exit codes** (`CONTROLLER_EXIT`): 0 stopped on purpose after the controller was closed, 75 restart me, 1 could not start or could not close (a close that has not finished after 60 s is given up; under the launcher its own grace, 10 s by default, usually ends the process first). A second stop signal only logs `already stopping`. Once the code is decided the process exits with it within 5 s even if something still holds the event loop. An uncaught error is Node's exit 1 (a crash to the launcher). 75 is returned when the owner's database move or rollback asks for a restart (`transfer.restart`), and only when this process runs under the launcher and the configuration lists database transfer targets; by hand the owner is told to restart it themselves, as before.
- **Heartbeat.** `NIMBLENEWT_HEARTBEAT_FILE`, `_TOKEN` and `_INTERVAL_MS` (set by the launcher) reach `startController` through the environment given to `launch`; nothing else is needed.
- **Secrets** are never printed and never taken from arguments. Provider keys and the database address are found by the NAME in the configuration: first in the operating system's secret store, then, for a name the store lacks, in `NIMBLENEWT_SECRET_<NAME>` (upper case; `-` written `__DASH__`, `.` written `__DOT__`) in the environment, which is how a service manager supplies them. The owner's credential is only ever read from and written to the store, and a provider key, database address or transfer target named like it (`nimblenewt-owner-token...`, any letter case) is refused at use, so the owner's token is never sent to a model server or a database (this applies to `nimblenewt.mjs start` too).
- **Environment changes (`--local-host-environments`, or `NIMBLENEWT_LOCAL_HOST_ENVIRONMENTS=1`; also accepted by `nimblenewt.mjs start` and `status`). Off by default.** The worker host then installs approved package requests into `<data>.environments` (an offline mirror under `<data>.environments/mirror`; no network). Without it approved changes wait pending. It only has an effect once the owner has turned the worker host on (`host.local.set`), counts from the next start, and the same limits apply (Linux only; its note: the local host cannot read a session back).
- **Workspace folders.** The configuration's `installation.workspaces` folders (a relative path is the data directory's; `~` is not expanded and a note says so) get the same start-up file system check as the data directory, for both programs; an explicit `start.workspaceRoots` from code wins. A folder on an unsupported or network file system refuses the start like the data directory would; the refusal is followed by a line naming the configured folders and the three ways out (move it, remove it from the configuration, or `--allow-unsupported-environment`). A folder that does not exist yet is judged by its nearest existing parent.
- The worker host's tool runner (`hostScriptRunner`) is composed by `scripts/local-host.mjs` for both programs; the host now refuses to start (and says why) when the runner reports it cannot run any tool.

Not built: service-manager units (launchd, systemd, Windows service), running it on macOS and Windows (the process-group stop is POSIX; Windows uses `taskkill /T /F` on the child's tree, then `child.kill()`, and the controller does not inherit the lock there), and the updater program.

### Who may release, what a signature covers, and what the owner's word binds (card K02)

- **`release.manage`** is a grantable action, separate from `agent.manage`, the catalog actions and `*`: only a grant that names exactly `release.manage` for all projects counts (a `*` or `release.*` grant, a grant for one project, and a task credential do not). Only the owner makes grants. A holder may stage, remove a staged release, verify, read the status and the trust root, attach signatures, activate and roll back. A holder activates only what the owner has approved (whatever the owner's approval setting says about the owner's own activations). Approving, submitting, settings, the trust root, confirming a start, resolving a switch and acknowledging notices stay the owner's. Candidates are submitted and approved by the owner alone, so an agent-built candidate cannot stage or activate itself.
- **Signed artifact sets.** The owner trusts Ed25519 public keys (`release.trust.add`; the chat refuses anything shaped like a key, so the key goes in a file in `<release root>/trust/` and the chat names the file). Once any key is trusted (or `release.trust.require` is true), staging, activating and rolling back need a valid signature from a trusted key over `nimblenewt-release-v1`, a line break, the candidate ID and a line break (the ID is the digest of the manifest that names every artifact's SHA-256). Signatures are attached with `release.signature.attach` (a value or a file in `trust/`), checked when attached and again at every use, so removing a key withdraws what only it signed. With no key and no setting the installation uses digests alone, as before. The private key never reaches the controller. The separate updater takes `--trusted-keys FILE --signature-file FILE`: a signature over `nimblenewt-release-digest-v1`, a line break, the staged manifest's digest and a line break, checked before anything is copied.
- **Migration plan and target installations.** A candidate's manifest may carry `migrationPlan` (the SHA-256 of the plan) and `targets` (installation names). A release with a plan is activated only by a word that quotes the plan's digest (the chat fills it from the candidate's record and shows it); a release with `targets` is staged and activated only on an installation whose `releases.installationId` is one of them (with targets and no name configured it is refused).
- **Database schema.** `compat.json` may add `schema: { min, max }`, the database schema versions (the number of the last applied migration) the release can run on. The controller records the highest version it has opened in the launcher's file as soon as the database is open. The launcher refuses to fall back to a last known good whose range ends below that version (it blocks and tells the owner a snapshot taken before the upgrade must be restored), and activation or rollback to such a release is refused. A release that states no range is not checked.
- **Not part of this card:** the maintenance window, its scope and the Prepare-to-Commit sequence are K07; the Pi runtime upgrade path is G11.

## Maintenance sequence

1. **Prepare:** acquire and verify the exact authorized release before the window. Candidate building, if used by a development deployment, has already happened in a separate pipeline. Test migrations and recovery using isolated copies and fake services without production credentials. Check space for release artifacts and consistent state backups.
2. **Quiesce:** block ordinary dispatch, inventory jobs, and Suspend affected workers without releasing assignments. Preserve each worker's prior lifecycle state. Wait for bounded cleanup and settled/reconciled effects. If safe suspension cannot finish in the window, defer the update and report why; do not silently Force Stop.
3. **Checkpoint:** stop all relevant state writers and create a consistent snapshot of data, artifacts, configuration, and required secrets references. Retain the old state for activation rollback. Any input acknowledged during downtime must be persisted in an independent compatible inbox; otherwise report temporary unavailability instead of acknowledging and losing it.
4. **Activate under quarantine:** start the exact candidate against its prepared state with ordinary agent scheduling and external side-effect dispatch disabled. Apply migrations only under exclusive ownership. Keep the previous version stopped so there is never a second active writer.
5. **Verify:** the updater checks startup within a deadline, state readability, command/adapter registration, a local administration request, and a bounded fake task/checkpoint/restore cycle. Check migration invariants and prior ownership/lifecycle state. A live process or a self-reported healthy flag is insufficient. Keep evaluation credentials and effects isolated.
6. **Commit or revert:** if checks fail or startup times out, terminate the candidate and its children, restore the compatible pre-activation state and previous release, and verify that release before reopening dispatch. If checks pass, record successful activation and follow the authorized resume policy. Previously paused, suspended, or stopped work stays that way; previously running work resumes only as covered by the maintenance authorization and after current-policy checks.

Persist progress before each consequential transition. After an updater crash or host reboot, recover from the journal and observed process/state identity; do not guess based on which process answers first. Keep candidate failure logs and notify the user. Quarantine a failed artifact so a repeated maintenance timer cannot create an update/rollback loop. If the previous release also fails, retain snapshots and enter bounded recovery mode with a clear status rather than repeatedly launching workers against uncertain state.

If maintenance is cancelled or deferred after a gate has been applied, record which gates belong to that update. Clear only those gates under the authorized return policy after readiness checks; do not erase a human's earlier or concurrent Pause/Stop request. Report any workers left suspended and why, rather than leaving them silently idle or automatically waking all of them.

## What automatic rollback can safely mean

**Before production dispatch resumes**, reverting code and its matching pre-update state is the intended automatic path: the candidate has not been allowed to create production effects. Preserve separately accepted inbox entries and maintenance decisions through that rollback. Recovery tests must verify this boundary.

**After production resumes**, reverting a database snapshot could erase new task completions, user decisions, or knowledge of external effects. Do not automatically rewind that state. Prefer backward-compatible, additive schema changes so the previous release can run against current data during a defined rollback period. Post-activation automatic code rollback is allowed only for a tested compatible version/state pair and after reconciling active operations. Delay destructive migrations until that period closes, or classify them as separately authorized maintenance with a specific recovery plan.

If compatibility cannot be guaranteed, fail closed on new work and enter recovery mode rather than label a stale snapshot restoration safe. A watchdog should distinguish release defects from provider outages or unrelated host resource failures; rolling back healthy code will not fix exhausted model credits. Repeated crash/health thresholds and probation duration are settings. Passing startup checks also cannot prove the absence of later semantic bugs, so keep independent verification, observation, and a way to stop rollout.

## UI, conversation, and validation

Expose maintenance windows with timezone, duration, target scope, trusted release source/channel, exact version, authorization, preparation limits, health deadlines, rollout status, rollback eligibility, and failure history through chat and UI. A window is permission to attempt an eligible update, not permission to discard unfinished work. A delayed window should not silently cause deployment at an unrelated time.

Test at least: broken imports/startup, migration failure, hung workers, missing dependencies, command collisions, disk exhaustion, updater termination at every transition, reboot during activation, previous-release failure, and a candidate that fails only after dispatch resumes. Verify no duplicated effects, no lost acknowledged input, no double ownership, preserved Pause state, and a functioning recovery path on macOS, Linux, and Windows. These are required future experiments; the existing harness tests do not test this release system.
