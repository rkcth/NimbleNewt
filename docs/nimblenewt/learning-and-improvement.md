# Learning and improvement lifecycle

Accepted planning direction, October 15, 2026. Connect the existing P/PC, evidence, toolbox, authorization and recovery contracts through one durable lifecycle. This is not an implemented learning service or permission to activate the development backlog.

## From observation to monitored adoption

Use observation → candidate → triage → bounded experiment → evaluation → scoped adoption → monitoring → retain, revise or withdraw. Each transition records actor, evidence, disposition, authority and linked tasks; rejected/deferred candidates retain reasons. A useful negative experiment can finish without adoption.

User corrections, repeated equivalent failures, successful recoveries, recurring friction and unnecessary approval stalls can generate candidates through durable event hooks. Deduplicate deliveries and retain original observation identities so copied reports do not count as independent evidence. Apply configurable thresholds, batching and triage budgets; do not start a model reflection for every tool call. A candidate is a hypothesis, not a proven lesson. A direct owner correction updates the applicable authoritative decision immediately; generalizing it into a lesson is separate.

Version lessons with supporting/contradicting evidence, applicability and exclusions, source tasks/observations, software/environment and assumption dependencies, evaluation status, author, supersession and retirement. Distinguish facts, agent interpretations and authorized instructions. Permission-filtered retrieval must not spread private project evidence. Changed dependencies mark affected evidence stale without erasing history; record unknown coverage honestly.

Experiments specify baseline, representative evaluation cases separate from development examples, acceptance criteria, cost/time/concurrency limits, stopping conditions and adoption scope. Measure accepted outcomes, regressions, recovery reliability and maintenance cost, not activity counts. Record exact skill versions actually supplied/used and linked outcomes; success after use alone does not establish causation. Specify review dates or event/usage triggers and withdrawal thresholds for adopted changes, with bounded monitoring costs and explicit insufficient-evidence states.

Adoption requires existing authorization and relevant independent review; PC funding alone grants neither publication nor deployment. Preserve immutable versions and required artifacts. Deprecation/merging must retain dependencies needed by paused work where allowed; revoked or unsafe versions require blocked continuation or authorized migration and revalidation. Withdrawal changes future selection and reconciles affected tasks; it must not rewind completed external effects or discard current decisions.

## Budget and authority

Use production-and-capacity.md for experiment, reflection, triage and monitoring budgets and protected delivery/improvement shares. Necessary verification of current production stays in P; shared overhead attribution must be explicit. No quota-driven proposals or unbounded improvement catch-up debt. Follow authorization-and-delegation.md: automatic adoption is scoped policy, not self-granted authority. Learning cannot silently weaken user acceptance criteria, independent review, access restrictions or approval rules. Proposed policy changes go through the authorized configuration service.

## Qualification

Test correction-to-candidate capture, duplicate/replayed observations, contradictory evidence, stale dependencies, cross-project privacy, bounded triage storms, baseline regressions, insufficient evidence, monitored withdrawal and paused-task version retention. Show that a redundant prompt can resolve under an existing grant while a mandatory human gate remains enforced. Test recovery at every lifecycle transition and verify accepted outcome criteria cannot be rewritten by the experiment under evaluation.
