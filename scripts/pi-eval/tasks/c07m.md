ACCEPTANCE DETAILS:
- The first call names the records by ID with the operation that reads them, in one bounded bracketed paragraph placed after the task text and rules and before the route view: the hand-off the task arrived in (read with handoff.get), the note the previous attempt left (read with a new query operation `context.handoff.read` taking `noteId`, of the same family as context.spill.read), and the task's open blockers (IDs, type, who can resolve, quoted summary). Each read that fails is reported and left out, never guessed.
- `ContextEnforcementService.latestHandoffFor(principal, taskId)` answers the latest note as `{ id, attemptId, source }` on the dispatcher's gate; `readHandoff(principal, noteId)` gives the whole note to whoever may work on the task and reads a note it may not show like one that does not exist. `HandoffService.latestForTask(taskId)` gives the hand-off record's ID, phase, from and to. context.handoff.read returns its documented fields only; the blockers line does not point a task credential at status.ask.
- The paragraph is counted on top of the rules reserve in the route view's room (summed, not max), including the composed route move.
- The paragraph builder lives in packages/controller/src/dispatch/handoff-brief.ts and exports `HANDOFF_BRIEF_LIMITS = { blockers: 5, summary: 160, resolver: 40, chars: 1500 }` (at most 5 blockers listed, a 160-character quoted summary, 40 for the resolver, 1500 characters for the whole paragraph) and `handoffBrief(facts)`.
- The three todo checks of the C07l test in dispatch/first-call-hops.test.ts (hand-off named, open blocker named, controller note given) pass on every backend and lose their todo. Run `npm run api:docs:write` after adding the operation.

CONTRACT (the acceptance tests check exactly these; names, fields and wording here are binding):
- `dispatch/handoff-brief.ts` exports `HANDOFF_BRIEF_LIMITS` (exactly `{ blockers: 5, summary: 160, resolver: 40, chars: 1500 }`) and `handoffBrief(facts: { taskId: string; handedIn?: { id: string }; note?: { id: string; attemptId: string; source: "attempt" | "controller" }; blockers?: { id: string; type: string; summary: string; resolver: string }[] }): string`. An absent field means there is nothing of that kind.
- `handoffBrief` returns `""` when there is only `taskId`; otherwise exactly `"\n\n[" + text + "]"` where `text` starts with `What the controller hands you` and is at most `chars` (1500) characters. With `handedIn` the text contains its ID and `handoff.get`; with `note` it contains the note ID, the note's `attemptId` and `context.handoff.read`, and the result differs between `source` "attempt" and "controller" (it says who wrote it). Blockers: the first `blockers` (5) are listed, each with its ID, its type, its summary through `quoted()` (so a plain summary appears as `"<summary>"`, credentials redacted, cut to fit) and its resolver through `quoted()` (a plain one appears as `"owner"`); every listed ID stays even when summaries must be shortened to fit; when more are open the text contains `<number not listed> more`. No `[`, `]` or line break taken from any fact value (IDs and types included) appears raw in `text`. The text never mentions `status.ask`.
- The order's `content` of every attempt start is: task title/description, then the rules note, then the `handoffBrief` paragraph, then (on a route move) `\n\n[The owner's decisions...` route view. Nothing to hand over: no paragraph at all.
- `DispatcherDeps` (dispatch/dispatcher.ts) gains `handedIn?: (taskId: string) => Promise<{ id: string; phase: HandoffPhase; to: { kind: string; id: string } } | undefined>` (api/dispatch-compose.ts wires it to `HandoffService.latestForTask`), and `DispatcherDeps.context` may provide `latestHandoffFor`. The hand-off is named only when its `phase` is `"transferred"` and `to` is the agent this attempt runs as (`agent:<to.id>` is the attempt's `agentId`). The note named is `context.latestHandoffFor(dispatcher principal, taskId)`, and only when its `attemptId` is not the starting attempt's own. Blockers are the task's open ones (subject `{ kind: "task", id: taskId }`), oldest first.
- A `handedIn`, `latestHandoffFor` or blocker read that throws: the attempt still starts, only that part is left out, and the thrown error is passed to the dispatcher's `onError` option.
- `ContextEnforcementService.latestHandoffFor(principal, taskId): Promise<{ id: string; attemptId: string; source: "attempt" | "controller" } | undefined>`: exactly those three fields of the task's latest note (the head `latestHandoff` reads); owner, host or service only (an agent gets DomainError `forbidden`); a task that does not exist is `not_found`.
- `ContextEnforcementService.readHandoff(principal, noteId): Promise<{ id: string; taskId: string; attemptId: string; source: "attempt" | "controller"; endedBecause: string; text: string } | undefined>`: exactly those six fields, `text` with credentials removed; whoever may work on the task (as `latestHandoff` judges it) reads it; an unknown note, an ID that is not a `hof-` note ID, any malformed string, or a caller who may not work on the task all resolve to `undefined` (never throw).
- `HandoffService.latestForTask(taskId): Promise<{ id: string; phase: HandoffPhase; from: Owner; to: Owner } | undefined>` (exactly those four fields): the task's latest hand-off, prepared (`"ready"`) or finished (`"transferred"`); `undefined` when the task was never handed over. Reachable as `controller.services.handoffs`.
- State API query `context.handoff.read` with args `{ noteId }` answers `{ item: { id, taskId, attemptId, source, endedBecause, text } }` (`readHandoff`'s result); `undefined` is error `not_found`. An attempt's own task credential may call it and `handoff.get`.
- Route move room: the `promptChars` the composed controller passes to `ContextEnforcementService.routeMoved` is the task text's length + `PROMPT_NOTE_RESERVE_CHARS` + the paragraph's exact length as it appears in the call (including its leading `\n\n`).
