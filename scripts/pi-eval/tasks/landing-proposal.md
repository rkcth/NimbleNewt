OWNER RULE: free-form chat means the owner says what they want in ANY words and the LLM interpreter picks the operation. No magic words/phrases; never tell the owner to say a particular word; no keyword scans of owner text to decide intent. Only ID-invention guards (foreignValue/wholeWord) are fine.

PROBLEM: packages/controller/src/chat/commands.ts has saysMainAutomatic, a phrase gate on the owner's words for choosing the `main-automatic` landing (integration.set / integration.default.set / project.create), and its refusal message in chat.ts tells the owner what to say. The same pattern was removed for flaky release approval (git log "flaky approval"): the operation became a proposal showing the owner exactly what would happen in plain language, and the owner's confirmation of the shown proposal is the consent; the model's own flag is dropped.

WHAT TO BUILD:
- The landing change becomes a shown proposal that states plainly the consequence; no keyword gate; no message tells the owner what to say. Export from chat/commands.ts a table `LANDING_MEANS: Readonly<Record<string, string>>` with one plain sentence per landing name; the `main-automatic` sentence says the work lands on main by itself with no human step (the words "main by itself" and "no human step" appear in it). The proposal line puts ` (from now on, <sentence>)` before the fields, and the meeting-decision question that offers landings uses the same table.
- When the proposal is for `main-automatic`, it shows the checks that gate landing, and those same checks are the ones pinned and enforced when the owner confirms (checks given as bare text are judged before they are shown). Proposal values are escaped and cut between whole characters; landing proposal lines cannot be forged by text in names.
- Delete saysMainAutomatic and chat/landing-words.test.ts; add tests with ordinary natural sentences: never applied without confirming the shown proposal; proposal/refusal text has no instruction to say a phrase. Refusals that taught a word (e.g. `(for example: topic staging server)`) say `in your own words` instead.
- Docs: `npm run api:docs:write` if operations text changed; notes entry in docs/nimblenewt/implementation-plan/implementation-notes.md with "superseded" notes on old phrase-gate entries.

CONTRACT (the acceptance tests check exactly these; names, fields and wording here are binding):
- `chat/commands.ts` exports `LANDING_MEANS: Readonly<Record<string, string>>` with a sentence for every name in `LANDINGS` (policy/integration-policy.ts); `LANDING_MEANS["main-automatic"]` contains `main by itself` and `no human step`. `describe(op, args, labels)` (existing export, returns the proposal line) for `integration.set` contains ` (from now on, <LANDING_MEANS[landing]>)` before the fields; the `integration.default.set` and `project.create` (landing inside `args.integration`) lines also contain the chosen landing's `LANDING_MEANS` sentence.
- `describe` never puts a raw line break, U+2028/U+2029 or bidirectional override (e.g. U+202E) on the line, from any value at any depth (including the `project.create` `integration` object, its keys, and an unknown landing); a cut value or line never ends in half a surrogate pair or half an escape.
- Chat (ChatService.submit outcomes; `preview` is the outcome's `string[]`, read joined with spaces): a `main-automatic` command for `integration.set`, `integration.default.set` or `project.create` is `status: "proposed"` for ANY owner sentence (a vague one, a denial, a negation); nothing changes until an `apply_proposal` of it (then `"applied"`); a `discard_proposal` gives `"discarded"`. Its preview contains `main by itself` and `no human step` and names, as whole words, each check that will gate the landing: the project's own `requiredChecks` (`integration.set` without checks), the installation default's (`project.create`, `integration.default.set`), or the checks given. Confirming then sets/pins exactly those: if the project's checks change before confirming, the proposal is not applied; a project created from the draft has exactly the shown checks; a default set from it holds only checks the preview named.
- `requiredChecks` given as a single check name as bare text (`"tests"`) means `["tests"]`; any other non-list, a list with a name not in `CHECKS` (`tests`, `review`, `qa`, `docs`, `director`), or an empty list for `main-automatic` is `status: "refused"` before anything is shown. A `project.create` `integration` section with a field other than `landing`, `integrator`, `requiredChecks`, `refreshRounds`, or a value the policy does not take (an `integrator` with a newline), is refused. (`"default"` as a section value still means "not sent".)
- With `integration.default.set { forbidMainAutomatic: true }` on, the `main-automatic` proposal is still shown and its preview says the lock (`forbid` or `lock`) means it will be refused (a word starting `refus`); confirming it gives `status: "refused"` and the landing stays unchanged.
- No outcome (proposal, preview, refusal) hands the owner wording to copy: none matches `for example`, `e.g.`, `only set when` or `say the word/that word/a phrase/the phrase/exactly` (saying `in your own words` is fine).
- The chat `project.create` question for `landing` (an `asked` outcome) offers each landing as an option starting with its name and containing its `LANDING_MEANS` sentence.
