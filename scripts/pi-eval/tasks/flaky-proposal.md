RULE FROM THE OWNER (Rob): free-form chat means the owner says what they want in ANY words and the interpreter works out the operation. The code must never require magic words or phrases, and must never tell the owner to say a particular word.

PROBLEM: packages/controller/src/chat/chat.ts refuses a release.approve of a flaky candidate unless saysAcknowledgeFlaky(words, ...) (chat/commands.ts) finds acceptance wording in the owner's sentence, and the refusal message tells the owner to say "...approve it with acknowledgeFlaky". That is a magic-phrase gate.

TARGET DESIGN: the interpreter proposes the approval; the proposal (propose mode) shows the owner the exact failed attempts being accepted (expectedFailures, as computed by chat from the gate, not from the model); the owner's confirmation of that shown proposal is the acceptance. Keep: expectedFailures bound to the failures shown, and the drift check in release/release.ts approve; an approval of a flaky candidate can never apply without that shown proposal being confirmed (never applied at once). Remove: the saysAcknowledgeFlaky keyword scan as a gate (delete the function and its tests), and the "acknowledgeFlaky" hint in any message, the interpreter prompt and docs (docs/nimblenewt/api-v1.md; run `npm run api:docs:write` if operations.ts text changes). Refusal/proposal text describes the situation in plain language only. Keep the check that the candidate ID is one the owner actually named (foreignValue/wholeWord) - that guards against invented IDs. release.approve drops the interpreter's own acknowledgeFlaky flag and expectedFailures list on every path, and is refused when no candidate is named.

Tests (chat/release-words.test.ts, chat/release-owner-words.test.ts): a flaky approval in ordinary words ("yeah ship it, I've seen those two failures are just noise") yields a proposal listing the failures, not a refusal; it is never applied without confirmation; a non-flaky approval behaves as before; no user-visible message contains "acknowledgeFlaky".

CONTRACT (the acceptance tests check exactly these; names, fields and wording here are binding):
- chat/commands.ts no longer exports `saysAcknowledgeFlaky`; `foreignValue(args, words, "", RELEASE_ID_KEYS)` keeps its whole-word ID check (returns undefined only when the owner's words name the ID as a whole word).
- Through `ChatService.submit` (scripted interpreter, any store), a `release.approve` command with a `candidateId` the owner named gets outcome `status: "proposed"` with a `proposalId`, whatever the words and whatever `acknowledgeFlaky`/`expectedFailures` the interpreter sent; nothing is approved until an `apply_proposal` of that proposal gives `status: "applied"` (a `discard_proposal` gives `"discarded"`).
- The proposal's step args (`(await chat.getProposal(ownerToken, proposalId)).steps[0].args`) are the chat's own reading of `release.gate`: `candidateId`; `expectedFailures` = the IDs of the gate's earlier failures (`[]` on a clean gate, never the interpreter's list); `acknowledgeFlaky: true` exactly when a platform is flaky (not `true` on a clean gate).
- For a flaky gate, the outcome's `preview` (joined with spaces) contains `linux x64 passed only after 1 earlier failure` (the existing release.gate note wording), the failed attempt's ID, a sentence matching `/gate.*(differ|chang).*confirm/i` saying the approval is refused if the gate differs when the owner confirms (the preview contains `refuse`), and never an attempt ID the interpreter invented.
- A gate that changes between proposal and confirmation: the confirmation outcome is `status: "refused"` with a `message` that mentions the gate or the failures (`/gate|failur/i`); nothing is approved; proposing again shows the new failed attempt's ID and its confirmation applies.
- `release.approve` with no `candidateId`: `status: "refused"`, no `proposalId`, nothing approved. A candidate ID not in the owner's words is still refused.
- No outcome the owner gets (proposal, refusal, applied, answer, including the `release` status view answer for a flaky candidate) contains the text `acknowledgeFlaky` anywhere (`JSON.stringify(outcome)`).
