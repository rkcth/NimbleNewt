CARD M03h part 1 (see docs/nimblenewt/implementation-plan/task-plan.md, section "M03h"): owner chat reach for stand-ups. Build ONLY: (a) chat operations to prepare a stand-up now, read a stand-up's brief, and add a statement for an agent; (b) a stand-ups status view (kind "standups") showing a project's stand-ups in the chat's status answers. Not in this part: usage sink, owner questions raised by a stand-up.

OWNER RULE: free-form chat means the owner says what they want in ANY words and the LLM interpreter picks the operation. No magic words or phrases; never tell the owner to say a particular word; no keyword scans of owner text to decide intent. Only guard against invented IDs (the existing foreignValue/wholeWord owner's-words check). Owner controls must appear in CHAT_OPS (chat/commands.ts) and STATUS_KINDS (status/status.ts); the interpreter prompt is generated from them; the status.ask summary in api/operations.ts must name every status kind (a test checks) - run `npm run api:docs:write` after. Agent-written text shown to the owner must be quoted with quoted() from status/explain.ts. Look at how existing stand-up/meeting operations and an existing chat reach (e.g. the capacity or release view) are done and copy that shape. Mutating ops use mode "propose" unless clearly harmless to apply at once.

ACCEPTANCE DETAILS:
- `StandupService.overview(viewer, projectId, { includeEnded?, limit? })` returns `{ items, more, ended } | undefined`: every stand-up the project has set up (from the schedules, so one that has not met yet is shown, unlike `recent`), active/paused/ended, schedule, duration and window, roster, meeting count, next meeting and how the last ended (with revisions cited); ended ones counted and left out unless asked for; the one with a meeting ahead first; paged by limit with `more`. The right to it is the right to read the project's meetings. It reads every planned meeting.
- The `standups` status view: two lines per stand-up (the schedule with its title quoted, then its meetings); a long roster cut to ten plus a count.
- Chat reaches a stand-up by the title it has now (a renamed stand-up is still reached by its title, ahead of its meeting's old title), including one waiting for its first meeting; stand-ups are told apart by schedule, not title; stand-up titles in the chat's choices are quoted.

CONTRACT (the acceptance tests check exactly these; names, fields and wording here are binding):
- `StandupService.overview(viewer: Principal, projectId: string, options?: { includeEnded?: boolean; limit?: number }): Promise<{ items: StandupSummary[]; more: boolean; ended: number } | undefined>` in standups/standups.ts; export `type StandupSummary` from standups/index.ts. `limit` default 20, a whole number 1 to 50, else DomainError `invalid_command`; a malformed projectId is `invalid_command`. `undefined` for a viewer without the project-meetings read right; a readable project with none gives `{ items: [], more: false, ended: 0 }`.
- `StandupSummary` fields: `scheduleId: string`, `revision: number` (the schedule's), `title: string` (the schedule's current title), `state: string` (`active`/`paused`/`ended`), `time: string` (`HH:MM`), `timeZone: string`, `recurrence: string` in words: exactly `daily`, `weekly on Mon, Wed` (short weekday names Sun..Sat, ascending from Sunday = 0, joined by `, `) or `once on 2026-11-02`; `window?: { from: string; to: string }`; `durationMinutes: number`; `roster: string[]` (the schedule's principal refs); `occurrences: number` (meetings it has made); `endsOn?: string`; `nextAt?: string`, `nextOccurrenceId?: string`, `nextRevision?: number` (its earliest planned meeting, from ALL pages of the planned meetings); `lastAt?: string`, `lastState?: string`, `lastOccurrenceId?: string`, `lastRevision?: number` (its latest meeting only once that is no longer `planned`; a planned one is the next, never the last). Order: stand-ups with a meeting ahead first (soonest first), then the rest by title (case-insensitive). `more` = items were cut by the limit; `ended` = ended stand-ups left out (0 with `includeEnded: true`, which lists them with state `ended`).
- `StandupService.recent` items (and the `standup.recent` API result items) also carry `scheduleId: string`.
- Status: `StatusDeps.standups` gains optional `overview?(viewer, projectId, page?: { limit?: number; includeEnded?: boolean }): Promise<{ items: readonly <item>[]; more?: boolean; ended?: number } | undefined>` whose item has the StandupSummary fields (plain `string`/`number` types, same optional ones); `recent` stays. `STATUS_KINDS.standups` with keys `projectId`, `limit`; request `{ kind: "standups", projectId: string, limit?: number }`; `limit` 1 to 25 (default 10) else `invalid_command`, any other key or a malformed projectId `invalid_command`; the limit is passed to `overview` as `{ limit }`. The answer is `undefined` when there is no `overview` dep, when `overview` answers `undefined`, or (owner) when the project does not exist. The `status.ask` summary names `` `standups` ``.
- Lines, per item in the order given: line 1 starts with `quoted(title)` (e.g. `"Friday \"review\""`) and contains the state, the recurrence words, the time, the zone, `<durationMinutes> minutes` (e.g. `30 minutes`), the window's from and to when there is one, and the roster names (the first ten only; a longer roster then says `and <n> more`, e.g. `and 2 more`; an empty roster names no one); it cites `meeting-schedule` (id scheduleId, revision) and `project`. Line 2 contains `nextAt` when there is one, else `nothing is planned`; `lastAt` and `lastState` when there is a last meeting, else `not met yet`; the count as `<n> meeting`/`<n> meetings` (`1 meeting`, `0 meetings`, `5 meetings`); `endsOn` when set; it cites `meeting` (id) for the next and the last meeting, and `project`. After them: when `more`, a line containing `more stand-ups`; when ended > 0, a line containing `<ended> ended` (e.g. `1 ended`, `2 ended`). No items: exactly one line, saying `No stand-up is set up in this project.` when ended is 0, else containing `<ended> ended` (e.g. `3 ended`). Every line cites `project` (id projectId).
- Chat: a status intent `{ kind: "standups", limit? }` without projectId uses the focused project. Stand-ups are named (`meetingTopic` of `standup.prepare` / `standup.add-statement` / the `standup_briefs` status) by the current title of a non-ended stand-up (read from the schedules, e.g. `standup.list`) before a meeting's own title, and told apart by scheduleId. Named stand-up (not ended) with no meeting to work on: refused (no proposal, no question), the message names it by its quoted title (`"Morning sync"`) and no other stand-up; for `standup_briefs` it also says it has no meeting yet. No words and no stand-up has a meeting: refused naming every running stand-up quoted. Words that fit no stand-up in `standup_briefs`: refused, repeating the owner's words and listing the project's running stand-ups by quoted title. A project with no running stand-up (none, or only ended ones): refused, the message contains `no stand-up` and never an ended stand-up's title. A `standup.add-statement` for an agent with no brief there: refused with a message containing `no brief`. When several fit, the question's options show the titles quoted. A prepare proposal's preview names the meeting by its stand-up's current title and the meeting's start time.
