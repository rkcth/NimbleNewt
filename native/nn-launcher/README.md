# nn-launcher: the native Windows launcher

Starts ONE program inside a low-privilege AppContainer and a Job Object, makes and takes back the container's folder permissions, and prints ONE JSON line. It is the program behind the native Windows sandbox backend of the worker (card A03b). It is Windows only: on Linux and macOS it prints a failing line saying so, and the worker reports the Windows backend unavailable there.

It fails closed. If the container, a required grant, the job or the attribute list cannot be made, nothing is started; it never falls back to a child that is not confined.

## What the product build does

| Command | What it does |
| --- | --- |
| `run` | Makes this run's OWN container profile (below), grants the container its folders (`--grant MODE:PATH`, hard: a failure stops the run; `--grant-soft`, recorded and skipped), starts `--exe` with `--cmdline` in the container and a Job Object (kill-on-close always on; `--memory-mb`, `--active-processes`, `--ui-limits`, `--timeout-ms`), with standard input read from the FILE named by `--stdin file:PATH` and standard output and error written to the FILES `--stdout` and `--stderr`, then revokes every grant and reads each folder back. |
| `check` | Read only. For each `--grant` path, how many entries for the container are still on it (`clean`); the container SID is DERIVED from `--name` (nothing is made, the profile may be gone already); `--sid` is an optional cross-check that must equal it. Whether a private window station can be made is no longer asked here for a per-run name (`info` asks it). |
| `revoke` | Removes the container's entries (the SID derived from `--name`, optionally cross-checked with `--sid`) from each `--grant` path (for a run that died). Other entries first, sealed names last, and the seals only when everything else is clean. Makes no profile. |
| `info` | Makes a throw-away per-run profile exactly as a run does (the record first, then the profile), prints its SID, makes and closes a private window station and desktop for it (`windowStation` is `private`, `windowStationOk`), and deletes the profile again (`profileDeleted`, `profileGone`). When the station cannot be made `info` fails with stage `grant` and a message starting `window objects:`, so a host with the problem says why before any run. |
| `delete-profile` | `--name N --sid S --profile-record P`: deletes the per-run profile N and reports `profileDeleted` and `profileGone`, but ONLY with proof: N has the per-run form, the record file P holds N and the SID that N derives to, and S is the same. Anything else is refused with stage `profile` and nothing is deleted. Used by the backend's sweep and by its own check after a run. |

Grant modes in the product build: `ro`, `rx`, `modify`, `modify-root` (modify without the right to delete the folder itself: the workspace) and `seal` (a protected name: read and execute only, nothing else, DACL protected). Options `--aap-policy none|optout` and repeatable `--capability NAME` choose the plain AppContainer or the LPAC form (the measured configuration: policy `optout` with only `registryRead` and `lpacCom`); there is never a network capability or a loopback exemption. `--env NAME=VALUE` is repeatable and the child gets exactly that environment.

Exit code: the child's; 124 when the time limit ended the job; 125 when the launcher itself failed. The JSON line is authoritative (`ok`, `stage`, `error`, `childStarted`, `childExitCode`, `timedOut`, `leftoverProcesses`, `allGrantsRevoked`, and one entry per grant with `applied`, `revoked`, `entriesLeft`). Its field names are pinned against the TypeScript parser by `packages/worker/src/sandbox/windows-native-contract.test.ts`. The `tool` field is the protocol identifier `nn-appc-launcher` (kept from the experiment so no recorded run changes meaning); it is not the file's name.

## One container profile per run

Every run has its own profile, named `NimbleNewtRun-` and sixteen lower-case hex digits (64 random bits chosen by the backend; 30 characters, inside the 64 and the pattern `[-_. A-Za-z0-9]+` that CreateAppContainerProfile allows). The product accepts no other name for any command and has no default name. `run`, `info` and `delete-profile` need `--profile-record PATH`, a file in the supervisor's control folder.

- `run` derives the SID from the name, writes the record whole and create-new (`nn-run-profile v1`, then `name SID`; a temporary file of its own is flushed and hard-linked to the record's name, so a kill leaves no record or a complete one, never a half-written one), THEN makes the profile (an existing one is never adopted), checks that the profile got the derived SID, makes the private window station for it, grants, starts, revokes, closes the window objects and the job, and deletes the profile and checks that it is gone, only when every grant is revoked and read back; otherwise it keeps the profile and says so (`profileKept`) so the supervisor can revoke by SID and delete. The line carries `containerSid`, `profile` (`created`), `profileDeleted` and `profileGone`.
- The "gone" check is `GetAppContainerFolderPath` on the SID after `DeleteAppContainerProfile` (called a second time if the first fails: Microsoft says the status is then undetermined). The documentation does not say what it returns for a deleted profile; the reading used is that it fails. NOT MEASURED. If it still succeeds, `profileGone` is false and the backend fails the run with the typed reason `profile`.
- A crash leaves the record (and maybe the profile): the backend's sweep revokes by SID (`revoke --name N --sid S`) and calls `delete-profile`, which deletes only with the record's proof. The launcher never lists profiles and never scans the registry.
- Every DACL read-modify-write (`change_ace`, grant or revoke) is taken under one machine-wide named mutex, `Global\NimbleNewtAclWrite` (the global namespace: an unprefixed name is per Terminal Services session, so a launcher started from a signed-in session and the worker's session-0 launcher would hold different locks; Microsoft requires SeCreateGlobalPrivilege only for file-mapping and symbolic-link objects, not mutexes), because several launchers may run at once (`maxConcurrentRuns` in the backend, default 1) and all of them write the same program folder's DACL. The mutex has the creator's default security: a launcher of another account cannot open it and fails that grant or revoke, and any local account could create the name first and stop every grant (a refusal, never a weaker run). Nothing has run two launchers at once.

## Window station (what a service needs)

A Windows service runs in session 0 on a non-interactive window station (`Service-0x0-<logon id>$`, desktop `Default`). A child in an AppContainer that is given no window station of its own takes that one, the container's SID has no access to it, and every program that loads user32 (node, powershell) ends with 0xC0000142. Measured on the owner's PC (run 45650543163, build 26200, runner service, elevated): the same programs work when the container has access to a window station AND a desktop, and an entry on only one of them fails.

So every `run` makes a window station and a desktop for that run (`privdesk.rs`): a station named `nn-ws-<64 random bits>` and the desktop `nn-d` in it, each CREATED with its final access list, given in the creating call: the launcher's own token user and SYSTEM with every right of the object type, and ONE explicit allow entry for the container's SID (station mask 131967, desktop mask 131583: the masks the experiment gave the container and measured; no smaller mask was tried). No access list is written afterwards, so the objects never exist with a default one (Microsoft documents the default for a NULL descriptor two different ways: "grants GENERIC_ALL access to all users" on the CreateWindowStation page, "from the primary or impersonation token of the creator" on the window-station security page) and there is no moment between creation and a write. The experiment made its station with the default list and then added the container's entry; the container's own entry is the same. The station is made with CWF_CREATE_ONLY, so a station that already has that name is never opened. The access list is read back and checked against an allow list: exactly one allow entry for the container with the measured mask and no flags, and every other allow entry for SYSTEM, Administrators, OWNER RIGHTS or the launcher's own token user or owner; anything else (a logon-session SID included) (Everyone, LOCAL, Users, Domain Users, ALL APPLICATION PACKAGES, another account, container or capability) stops the run and is named in the message; a NULL access list is refused. `STARTUPINFO.lpDesktop` is `station\desktop`. The desktop is closed, then the station, when the run ends. The launcher's own process window station is changed only for the single CreateDesktopW call (that call makes the desktop in the calling process's station) and is put back at once, checked, and again by a guard on every other path. The service's own station and desktop are never opened, never named and never written; WinSta0 (the interactive station) is never touched. Microsoft documents that only members of Administrators may name a window station, so under a non-administrator account the creation is expected to fail (an access-denied error says so in the message; not yet measured). If any step fails the run stops with stage `grant` and a message starting `window objects:` (the backend maps that stage to its `grant` failure) and nothing starts. Interactive sessions use the same code. What the container sees is only its own private station: it has no clipboard or atom table shared with the user, and a program that needs a visible window (a GUI program such as wscript hung in every working mode of the measurement) is not supported and not needed by node, npm or git.

## What is not in it

The measuring options of the experiment are not in the product build: grants `deny-write` and `deny-strong`, `--win32k-off`, `--no-kill-on-close`, `--keep-profile`, the NUL device and pipes for standard handles, `--dump`, and the commands `grant`, `dump` and `open-test` (plus the hang diagnosis). `delete-profile` IS in the product now, but only for a per-run profile with the launcher's own record (the experiment's unproven delete of any name stays experiment-only). The product build refuses each at the argument check ("not in this build"), and the code of `open-test` and the hang diagnosis is compiled out. They exist under the cargo feature `experiment`, which only `experiments/windows-appcontainer/launcher/` turns on, so the experiment keeps working from the same source.

## Build, release, install

- Build and release (locked dependencies, pinned toolchain, reproducible build (identical once, for one pair of folders on one runner image; not shown more widely), the hash record, signing): [RELEASE.md](RELEASE.md).
- The one-time administrator install (account, folders, access lists, uninstall, verify): [../install/README.md](../install/README.md).
- Reproducibility: the hosted job builds the launcher a second time from another folder and compares the two files (`scripts/pe-diff.mjs`; a report, not a gate). One hosted run (2026-11-25) printed `identical` for one pair of folders on one runner image; nothing claims more than that yet. What is and is not measured, and how the unsigned hash and the signed file relate, is in [RELEASE.md](RELEASE.md).
- Dependency licenses: `cargo-licenses.json` is checked against `Cargo.lock` by `npm run licenses:check`.
- Tests: the command line (`src/args.rs`, the only platform-neutral part) has Rust unit tests for both builds: `cargo test --locked` (the product build refuses every experiment-only option, mode, input and command, and misspelled, abbreviated or joined forms are unknown) and `cargo test --locked --features experiment` (the experiment build accepts them). They run on Linux, macOS and Windows; the hosted Windows step runs both.

## Not proven yet

Per-run profiles (make, delete, the "gone" check, the cost), the ACL mutex and two launchers at once have not run on Windows: the code compiles for Windows (`cargo check --target x86_64-pc-windows-gnu`) and the pure parts (names, records, the proof rule, the command line) have Rust unit tests. Reproducibility (two builds of one commit giving one hash) is not shown: the hosted job now builds twice from two folders and reports the comparison, but no hosted run has printed its result yet. The private window station fix is unit tested for its rules on every platform and compiles for Windows, but the Win32 calls themselves ran only in the experiment's `new-station` mode (own-hardware run 45650543163); the product's own code path is first run by the own-runner G05 step after this change. Launching from the service account in Session 0 with nobody signed in (also after logout and reboot), a non-administrator account, Windows Home, the controller's channel across the container boundary (built as a file relay in the supervisor, tested only with a simulated launcher; how a real container treats its two files is unmeasured), and everything on the owner's own hardware. Only a hosted interactive administrator session on Windows Server has run this program.
